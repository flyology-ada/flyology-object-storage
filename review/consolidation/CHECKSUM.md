## CHECKSUM: S3 checksums, CRC combination, policy, streaming engine, xxHash bridge and trailers (CHECKSUM-1, CHECKSUM-2)

The area covers `src/flyology-object_storage-s3-checksums.ad?`, `-s3-checksum_crc.ad?`, `-s3-checksum_policy.ad?`, `src/flyology-object_storage-checksum_engine.ad?`, `src/flyology_object_storage_xxhash.c`, `vendor/xxhash/`, `docs/architecture/s3-checksums.md`, `tests/src/s3_checksum_corpus.adb` and `tools/generate_s3_checksum_corpus.py`, with the PutObject and document checksum preflights in `src/flyology-object_storage-server-s3_applications.adb`, the pinned botocore model `review/baseline/service-2.json` and the qualification documents read as the contract.

### CHECKSUM-1: PutObject answers `InvalidRequest` where the pinned model documents `BadDigest` for an SDK-algorithm / value-header mismatch

**Severity:** P2 (the discovery report also said P2).

**Location:** `src/flyology-object_storage-server-s3_applications.adb:14812-14821`, the branch inside `Checksum_Value_Header_Count = 1` that answers 400 `InvalidRequest` "The checksum algorithm and value header differ" when the SDK algorithm header names a different algorithm than the value header, with the selector set at `:14786-14802`; the same shape in `Put_Object_Annotation` at `:15553-15562`; the 18 sites that do emit `BadDigest` (`:1986`, `:3864`, `:5263`, `:5345`, `:8243`, `:8255`, `:10191`, `:10206`, `:10403`, `:10418`, `:13129`, `:13810`, `:15935`, `:16468`, `:17689`, `:17721`, `:18017`, `:18026`); `shapes.PutObjectRequest.members.ChecksumAlgorithm` documentation in `review/baseline/service-2.json`; the existing assertion at `tests/src/s3_server_application_corpus.adb:6428` (fixture at `:6334-6341`, message at `:6431`); `docs/qualification/put-object.md:33`.

**Repro:** `tests/repros/src/repro_checksum_1.adb`, exit status 1, two failed expectations; control 1 shows the identical request with a matching selector is accepted with 200, and control 2 shows a genuine value/content mismatch on the same operation is answered `BadDigest`.

**What is wrong:** When a PutObject request carries both `x-amz-sdk-checksum-algorithm: <A>` and a value header `x-amz-checksum-<B>` for a different algorithm B, the preflight answers 400 `InvalidRequest`, while the pinned model's documentation for `PutObjectRequest.ChecksumAlgorithm` says Amazon S3 fails that request "with a BadDigest error". The consequence is purely which `<Code>` a caller or a conformance harness keyed on the error code observes: the status is 400 either way, the object is not stored either way, and botocore raises `ClientError` for both. It is deterministic and reachable by any client that sets both headers inconsistently. The model gives UploadPart a different rule — an individual checksum makes S3 ignore the algorithm parameter — which the server implements separately, so the PutObject branch is not a shared-policy consequence.

**Notes:** Two sub-claims partly refute the finding and are why it stays P2 and rests on prose only. First, `BadDigest` is not a shape anywhere in the pinned model, and PutObject's modelled `errors` list is exactly `InvalidRequest`, `InvalidWriteOffset`, `TooManyParts` and `EncryptionTypeMismatch`, so the code the server emits is PutObject's own modelled error and `BadDigest` appears only inside documentation strings. Second, the model's error table defines `BadDigest` as "The Content-MD5 you specified did not match what we received", a content mismatch, which is exactly the meaning this server reserves it for; reserving `BadDigest` for a real digest mismatch and `InvalidRequest` for a malformed header combination is a defensible reading of the same document. `Put_Object_Annotation` uses the same mapping but is a Flyology extension with no model text. An existing test pins the current code at `tests/src/s3_server_application_corpus.adb:6428`, so a change would need that assertion edited; no documented deliberate deviation exists in `docs/qualification/put-object.md` or `docs/compatibility/s3.md`. A fix is a maintainer decision because it changes an externally visible error code.

### CHECKSUM-2: Operations the model marks `requestChecksumRequired` reject every stock SDK request, because the server demands Content-MD5 and ignores the `x-amz-checksum-<alg>` group the SDK sends instead

**Severity:** P0 (not in the discovery report; found by the stock-client probe this area required). This is the same defect as SERVER-1, which is the primary finding; it is counted there, not here.

**Location:** `src/flyology-object_storage-server-s3_applications.adb:10352-10370` (`Put_Bucket_Versioning`'s Content-MD5 precondition, which runs before the branch at `:10376-10412` that reads the document and calls `Verify_Document_Checksum`); `:8013-8019` (`Put_Bucket_Tagging`, same precondition); `:17683` (DeleteObjects, "DeleteObjects requires one valid Content-MD5 header"); `:5033-5140` (`Verify_Document_Checksum`, which already parses and verifies the whole `x-amz-sdk-checksum-algorithm` / `x-amz-checksum-<alg>` / `x-amz-trailer` group for all ten algorithms); the 27 operations carrying `httpChecksum.requestChecksumRequired: true` in `review/baseline/service-2.json`, and `DeleteObjectsRequest`, which has no `ContentMD5` member at all.

**Repro:** duplicate of SERVER-1; it nonetheless contributes its own evidence — `tests/repros/src/repro_checksum_2.adb`, exit status 1, two failed expectations, and the stock-client probe `tests/repros/python/checksum_boto3_probe.py`, exit status 1 on cases (e) `delete_objects` and (f) `put_bucket_versioning`. SERVER-1's own evidence is aws-cli v2.36.34.

**What is wrong:** Since botocore 1.36 the default `request_checksum_calculation` is `when_supported`, so a stock AWS SDK satisfies an operation's `requestChecksumRequired` trait by sending `x-amz-sdk-checksum-algorithm: CRC32` together with `x-amz-checksum-crc32`, and sends no Content-MD5 at all. The server's preflight for those operations requires exactly one syntactically valid Content-MD5 and returns 400 `InvalidRequest` before reaching the verifier that already implements the checksum group. Every one of the 27 `requestChecksumRequired` operations is therefore uncallable from a current boto3, aws-cli v2 or any other modern SDK using default settings; it is fully deterministic, since the guard is a pure header check with no timing or backend dependence. The only workaround is setting `request_checksum_calculation=when_required` *and* passing `ContentMD5=` by hand, which is impossible for `DeleteObjects`, whose pinned request shape has no `ContentMD5` member — so `DeleteObjects` is unreachable from a stock SDK under any configuration. Object-path checksums are unaffected: the probe's `put_object`, `create_multipart_upload`, `upload_part`, `complete_multipart_upload`, `head_object` and `get_object` calls were all accepted.

**Notes:** SERVER-1 is the primary finding and carries the disposition; this entry exists to record the boto3-side evidence and the `DeleteObjects` sharpening. Wire evidence: boto3/botocore 1.43.89 on Python 3.13.7, resolved from PyPI by `uv run --python 3.13 --with boto3` with nothing installed system-wide, driven against the repository's prebuilt `tests/bin/s3_memory_server` (not rebuilt, no Docker); the exact captured request headers and the exact 400 response bodies are in the verification report. The requirement is *described* in `docs/compatibility/s3.md:638`, `docs/qualification/bucket-versioning.md:47`, `docs/qualification/bucket-tagging.md:51` and `docs/qualification/delete-objects.md:11`, but always as Content-MD5 *plus* the checksum group and never as an acknowledged interop boundary, so it is not a documented limitation; those documents and their corpora would need updating alongside any fix. The probe also settled two open discovery questions in the crate's favour, recorded under coverage evidence below.

## Coverage evidence: CHECKSUM

- `Checksum_CRC.Make_Table`, `Update` and `Finish`: reflected table-driven CRC with all-ones init and final XOR for CRC32 (0xEDB88320), CRC32C (0x82F63B78) and CRC64NVME (0x9A6C9329AC4BC9B5, verified as the bit reflection of 0xAD93D23594C93659); the corpus "123456789" vectors encode the published check values.
- `Checksum_CRC.Combine`, `Matrix_Square` and `Matrix_Times`: zlib `crc32_combine` generalised to 64 bits, verified against an independent polynomial combiner up to 2^63-1, with a correct zero-length operand, 32-bit masking and correct loop variants; the corpus's large-length expected values were reproduced by a different method.
- `Checksums.Encode_Base64`, `Decode_Base64` and `Wire_Core.Valid_Base64`: exact encoded length per algorithm, standard alphabet only, required padding, zero unused pad bits, no whitespace; the decode loop was traced for 4, 8, 16, 20, 32 and 64-byte digests.
- `Checksums.Composite`, `Full_Object`, `Encode_Object` and `Decode_Object`: raw big-endian part digests concatenated in manifest order (which completion requires to be strictly ascending and, for composites, consecutive from 1), the `Combine` left-fold using each right part's stored size, the exact `-<N>` suffix including `-1`, and strict suffix and part-count rejection on decode.
- `Checksum_Policy` and `Checksum_Engine`: the multipart algorithm matrix, `Default_Type`, `Ordinary_Object_Supported`, and the `Valid_*`/`Matches_Stored_Object_Digest`/`Multipart_Object_Value` predicates, including that the multipart-only `Policy.Supported` gate is never reached for direct-put full-object digests.
- `Checksums.Context` state machine: `Initialize` resets, `Finish` is non-destructive for every algorithm, and `Update` after `Finish`, `Reset`, empty slices and arbitrary chunk boundaries (210 corpus combinations) are correct; no per-context byte counter exists to overflow.
- xxHash bridge: the vendored header is v0.8.3 as claimed, the struct size and alignment are checked at every reset, `XXH3_128bits_reset` is literally `XXH3_64bits_reset` so sharing it is correct, NULL is passed only with length 0, and the canonical byte orders match the `xxhsum` oracles the corpus generator uses.
- Server trailer path: `x-amz-trailer` must name exactly the SDK algorithm's header, a value header and a trailer cannot be combined, trailer access happens only after `Finished`, the trailer value is canonical-validated and compared with the streamed digest, and the response echoes the backend-computed value with `x-amz-checksum-type`.
- Stock-client probe (boto3 1.43.89, exit status 1 on the two `requestChecksumRequired` cases only): `put_object` with defaults and with an explicit algorithm, `create_multipart_upload`, two `upload_part` calls, `complete_multipart_upload`, and `head_object`/`get_object` with `ChecksumMode=ENABLED` over three keys all returned 200, with the composite `-2` value surfaced and 10,485,760 bytes streamed without a validation error.
- Two discovery questions settled by that probe: over plain HTTP with a seekable body botocore sends a plain body with a precomputed checksum header rather than `aws-chunked`, so the 501 trailer boundary was never exercised; and botocore sends no object-level checksum header at all on `CompleteMultipartUpload`, only `x-amz-checksum-type: COMPOSITE` plus per-part elements, so the server's raw-form requirement is never exercised by boto3.

## Observations not counted: CHECKSUM

- The server requires the raw Base64 (no `-N`) in `x-amz-checksum-<alg>` on CompleteMultipartUpload and the typed client strips the suffix; botocore never sends the header at all, so the requirement remains unverified against a client that does (aws-cli/CRT).
- XXHASH128 byte order follows xxHash's canonical big-endian (high64, low64) form; no AWS-published vector exists in the repository and whether AWS uses the same order is from memory and unverified.
- The C bridge checks `_Alignof <= 64` but not that the actual storage address is 64-byte aligned, so correctness relies on GNAT honouring `Alignment => 64` for the stack-allocated `XXH_Storage`; low confidence, no evidence of a failure.
- UploadPart echoes the backend-computed `x-amz-checksum-<alg>` even when the client sent no part checksum (`s3_applications.adb:12717-12721`), where the model says the header is present only when provided; confirmed harmless with the stock client.
- Trailer-borne checksums are reachable only with plain HTTP/1.1 chunked trailers because `aws-chunked` is answered 501 (PutObject `:14882-14886`, UploadPart `:12618-12622`); a documented capability boundary, narrowed by the probe to non-seekable or non-plain-HTTP bodies. See SERVER-5 for the diagnostic on the modern sentinel.
- Ranged GetObject on a full-object-CRC object returns the full-object checksum header with the 206 while composite values are suppressed on ranges; AWS behaviour for ranged responses is from memory and unverified, and stock SDKs skip validation on 206.
- `Request_Source.Read` rejects any request whose trailer block contains more than the one declared checksum trailer; a strictness choice, not a rule in the model.
- CompleteMultipartUpload accepts and validates an `x-amz-checksum-algorithm` request header the pinned model does not define for that operation (`s3_applications.adb:13048-13060`); a lenient extension.
- Policy values not counted: the CRC64NVME/FULL_OBJECT default for PutObject and CreateMultipartUpload without a selection, the 5 GiB PutObject and maximum part-size caps, the 10,000-entry caps in `Hash_File`, and `Maximum_Checksum_Length = 96`.
- Not reviewed: the HTTP crate's own chunked-trailer parser (outside this repository; only the accessor contract and the `Finished`/`Body_Done` coupling were read), and SQLite schema handling beyond the `Multipart_Object_Value` call site and `Checksum_From_Columns`.
