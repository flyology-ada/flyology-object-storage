### S3-DOMAIN-A-1: ListObjectVersions decoder rejects every `Version` whose `StorageClass` is not `STANDARD`

**Severity:** P1 (the discovery report also said P1, at Medium confidence, because the claim that real servers emit non-`STANDARD` classes there was memory). The verifier settled that part against a live server and kept the severity: it is a wrong result — an exception — on valid input through a reachable path, and it is not P0 only because `docs/compatibility/s3.md:67` ends the ListObjectVersions row with "no external interoperability claim", so no documented contract is broken. Were that disclaimer absent it would be P0 by the interop clause, since a stock server's valid 200 response is refused outright.

**Location:** `src/flyology-object_storage-s3-versions.adb:798-805` (`Storage_Class_Field` calls `Valid_Enumeration (Value, Version_Member_Shape (5))` and raises `Malformed_Version_Listing` with "invalid ObjectVersion storage class"); `:354-361` (`Version_Member_Shape` resolves output member 6, `Versions`, then that list's member shape, then member N of `ObjectVersion`); `:364-380` (`Valid_Enumeration` returns False for anything outside the list and False when the shape carries no enumeration, with no permissive fallback); `:893-918` (`Finish_Version` additionally makes `Has_Storage_Class` mandatory at `:900`); `:1202-1216` (the server-side `Validate_Version` applies the same one-value enumeration, so the in-house server can never emit a page that would trip the decoder); the sibling that accepts all fifteen classes for the same object, `src/flyology-object_storage-s3-listings.adb:648-653`; the only decode path, `Parse_List_Object_Versions` at `versions.adb:1126-1150`; the client mapping to `Invalid_Response "malformed ListObjectVersions response"` at `src/flyology-object_storage-client-low_level.adb:2226-2229`; the existing assertion of the wrong behaviour at `tests/src/s3_list_object_versions_corpus.adb:335-341` (`Expect_Bad (Page ("...<StorageClass>GLACIER</StorageClass>..."), "accepted unmodeled storage class")`) with the vector table that pins it, `tests/corpora/list-object-versions/members.tsv:30` ("Require exactly one pinned ObjectVersion storage class value."; the discovery report names `vectors.tsv:12`, LOV-RS-006, as the matching row); the documented contract at `docs/qualification/list-object-versions.md:90-91` ("exact pinned storage class") and the matrix row `docs/compatibility/s3.md:67`.

**Repro:** `tests/repros/src/repro_s3_domain_a_1.adb`, exit status 1, five failed expectations; the live half is `tests/repros/src/repro_s3_domain_a_minio_probe.adb`, exit status 1, three failed expectations.

**What is wrong:** `Finish_Field` validates every `<Version>/<StorageClass>` against the pinned one-value `ObjectVersionStorageClass` enumeration, so a page in which any single version reports a different class raises `Malformed_Version_Listing` and the client turns it into `Invalid_Response`: the entire page is lost, not just the offending entry, and there is no cursor with which to skip it. The pinned model is unambiguous — `ObjectVersion` member 5 is `StorageClass` with shape `ObjectVersionStorageClass`, which is `{"type": "string", "enum": ["STANDARD"]}`, while `ObjectStorageClass`, used by `Object` member 7, has fifteen values — and so is the AWS S3 API Reference, whose `API_ObjectVersion.html` StorageClass entry reads "Type: String / Valid Values: `STANDARD`", so the one-value enumeration is not a botocore artifact and the discovery report's "documentation artifact" argument does not hold. The finding rests on the pinned MinIO instead. That server accepts `x-amz-storage-class: REDUCED_REDUNDANCY` on PutObject with 200 (and rejects `STANDARD_IA`, `GLACIER`, `ONEZONE_IA` and `INTELLIGENT_TIERING` with `InvalidStorageClass`), and its `GET /bucket?versions` returns 200 with `<StorageClass>REDUCED_REDUNDANCY</StorageClass>` inside `<Version>`. Anyone calling `Client.Objects.List_Versions_Page` against MinIO therefore loses every listing of a bucket holding such an object; on AWS the same happens to lifecycle-transitioned versions. It is fully deterministic. The program decodes a minimal `ListVersionsResult` with one version once per storage class through `S3.Versions.Parse_List_Object_Versions`, runs the same five classes through `S3.Listings.Parse_List_Objects` to show the crate accepts them there, then replays the exact `ListVersionsResult` body MinIO returned (1157 bytes, verbatim) and asserts both versions decode: `STANDARD` passes as the control, `REDUCED_REDUNDANCY`, `STANDARD_IA`, `GLACIER` and `INTELLIGENT_TIERING` are each `REJECTED, malformed ListObjectVersions XML: malformed S3 XML document`, all five decode through the ListObjects v1 path (`decoded, objects=1`), and the MinIO body is rejected the same way. Live, the probe reports `List_Versions_Page flyology-review-domain-a-versions: raised Invalid_Response: malformed ListObjectVersions response`.

**Notes:** This finding and S3-DOMAIN-A-7 both break ListObjectVersions against MinIO and must be fixed together: fixing S3-DOMAIN-A-1 alone leaves the operation just as unusable, because `Versions.Validate` rejects every untruncated MinIO page before any storage class is reached. The probe isolates them by listing a second MinIO bucket holding only a default-class object, which still raises. Neither has ever been exercised by CI, for the reason given in the area introduction: `Require_Durable_Version_Routing` (`tests/src/s3_implementation_corpus.adb:3310-3333`) is the only implementation-corpus caller of `List_Versions_Page` and returns unless the implementation is a Flyology backend. The strictness is contract drift the maintainer chose, not an accident — `docs/qualification/list-object-versions.md:90-91` and `tests/corpora/list-object-versions/members.tsv:30` state it as intended — but the only place it is disclosed to a user is the matrix row's "no external interoperability claim", which does not name storage classes. A fix needs a maintainer decision: either the decoder accepts any non-empty `StorageClass` text, or it validates against the fifteen-value `ObjectStorageClass` used by the sibling codec; either choice widens a publicly observable acceptance domain, and the second also changes `Validate_Version` on the server side. `tests/src/s3_list_object_versions_corpus.adb:335-341` and `tests/corpora/list-object-versions/members.tsv:30` assert the current behaviour and must change with it. `Finish_Version`'s requirement that `StorageClass` be present at all (`versions.adb:900`) is a second, smaller drift from a model that marks the member optional, and AWS documents `ObjectVersion.StorageClass` as `Required: No`.

### S3-DOMAIN-A-2: ListObjects v1 decoder rejects a truncated page that carries `NextMarker` without a delimiter

**Severity:** P0 (the discovery report said P1, at High confidence). The verifier corrected it upward. Unlike ListObjectVersions, `docs/compatibility/s3.md:65` makes an explicit external interoperability claim for ListObjects v1 — a "native/lightweight six-server oracle" — while the crate cannot read the first page of an ordinary undelimited listing from any of the three pinned third-party servers. That is an interop-breaking protocol violation of a claimed contract, and the CI lane that would have caught it is switched off rather than fixed.

**Location:** `src/flyology-object_storage-s3-listings.adb:1093-1094` (`Effective_Delimiter : constant Boolean := Value.Has_Delimiter and then US.Length (Value.Delimiter) > 0;`, so an echoed empty `<Delimiter/>` cannot rescue the case); `:1108-1116`, the raise, `Value.Has_Next_Marker /= (Value.Is_Truncated and then Effective_Delimiter)` … `raise Malformed_Listing with "inconsistent S3 next marker";`; `:1144-1163` (`Parse_List_Objects` always calls `Validate`, with no bypass); the client mapping at `src/flyology-object_storage-client-low_level.adb:1694-1695` (`Decode_List_Objects_Response` converts it to `Invalid_Response`); the client's existing marker fallback at `src/flyology-object_storage-client-objects.adb:403-415`, which already derives the marker from the last key when `NextMarker` is absent; the oracle-mode switch-off at `tests/src/s3_implementation_corpus.adb:258-274`, where `Check_List_Objects_V1_Pagination` returns `False` for the three `*-next-marker-without-delimiter` modes (the skip at `:262-270`) and `True` when the variable is unset, driven from `tests/scripts/test-minio.sh:66-67` (`FLYOLOGY_LIST_OBJECTS_V1_ORACLE_MODE=minio-2025-next-marker-without-delimiter`), `tests/scripts/test-rustfs.sh:71` and `tests/scripts/test-seaweedfs.sh:78`; the qualification paragraph `docs/qualification/list-objects-v1.md:54-58`; the matrix row `docs/compatibility/s3.md:65`; the existing assertion of the wrong behaviour for the final-page variant at `tests/src/object_storage_test_cases.adb:9597-9599`.

**Repro:** `tests/repros/src/repro_s3_domain_a_2.adb`, exit status 1, two failed expectations; the live half is `tests/repros/src/repro_s3_domain_a_minio_probe.adb`.

**What is wrong:** `Listings.Validate` treats "AWS only sends `NextMarker` when a delimiter was requested" as a wire rule and raises when a truncated page carries the element without a non-empty `<Delimiter>`. The pinned model imposes no such constraint — `ListObjectsOutput` has no `required` list and `NextMarker` is a plain optional string — and the rule the model's own documentation carries is advice to a client, not a constraint on a server: "This element is returned only if you have the `delimiter` request parameter specified. If the response does not include the `NextMarker` element and it is truncated, you can use the value of the last `Key` element … as the `marker` parameter". The AWS API Reference for ListObjects says the same and lists no error for it. MinIO, RustFS and SeaweedFS all emit `NextMarker` unconditionally: against the pinned MinIO, three keys with `max-keys=1` and no delimiter return 200 with `<IsTruncated>true</IsTruncated>` and `<NextMarker>k1[minio_cache:v2,return:]</NextMarker>` and no `<Delimiter>`, while the same request with `delimiter=/` returns the same `NextMarker` plus `<Delimiter>/</Delimiter>`. So a Flyology client paging any bucket with more than `max-keys` objects and no delimiter against those servers loses the very first page and pagination never starts; this is the common case, not an edge case, and it is deterministic. The program puts four documents through `S3.Listings.Parse_List_Objects` — the verbatim MinIO page with `delimiter=/` (control, `decoded, objects=1 truncated=TRUE has_next_marker=TRUE next_marker="k1[minio_cache:v2,return:]"`), a truncated no-delimiter page without `NextMarker` as the Flyology server emits it (control, `decoded`), the verbatim MinIO page without a delimiter, and a minimal synthetic equivalent, the last two both `REJECTED, inconsistent S3 next marker`; the two MinIO bodies differ by exactly one element. Live, the probe reports `List_V1_Page max-keys=1 delimiter=/: kind PAGE_AVAILABLE status 200` against `List_V1_Page max-keys=1 no delimiter: raised Invalid_Response: ListObjects response is invalid or exceeds the XML limit`.

**Notes:** The repository already knows about the behaviour and has switched the check off rather than fixed it, which is what makes this P0 rather than a documented limitation. The switch-off lives in two places that must be retired with the fix: the three Docker scripts set the oracle-mode variable (`tests/scripts/test-minio.sh:66-67`, `test-rustfs.sh:71`, `test-seaweedfs.sh:78`) and `tests/src/s3_implementation_corpus.adb:258-274` reads it, `Check_List_Objects_V1_Pagination` returning `False` for the three `*-next-marker-without-delimiter` values at `:262-270` so the subcase is skipped, while `docs/compatibility/s3.md:65` still advertises the six-server oracle and `docs/qualification/list-objects-v1.md:54-58` records the exclusion in prose. The fix itself is small and needs no new public value: accept `NextMarker` whenever the page is truncated and keep rejecting it on a final page; the client's fallback at `client-objects.adb:403-415` already handles both shapes. `tests/src/object_storage_test_cases.adb:9597-9599` asserts the final-page rejection and stays correct, but the truncated no-delimiter case has no test and should gain one. Refutations that failed: an echoed empty `<Delimiter/>` does not satisfy `Effective_Delimiter`; the model does not impose the rule; and the failure is not confined to a later page, since the first page of a three-key bucket with `max-keys=1` is already rejected.

### S3-DOMAIN-A-3: Lifecycle and Notifications serializers reject U+007F that XML 1.0, their own parsers and the Replication serializer accept

**Severity:** P2 (the discovery report also said P2). It needs an unusual byte in a configuration value and produces a clean exception before any request is sent; no data is lost and no server sees a bad document. The verifier found no reachable caller that would hit it accidentally.

**Location:** `src/flyology-object_storage-s3-lifecycle.adb:789-790` (`if First in 16#20# .. 16#7E# or else First in 16#09# | 16#0A# | 16#0D#`) and `src/flyology-object_storage-s3-notifications.adb:503-504` (identical range), against `src/flyology-object_storage-s3-replication.adb:828-829`, which is one byte wider (`16#20# .. 16#7F#`), and the shared escape boundary at `src/flyology-object_storage-s3-xml.adb:221-226`, which rejects only `Character'Pos (Item) < 32` other than TAB, LF and CR; the raise sites `src/flyology-object_storage-s3-lifecycle.adb:852-863` (`Malformed_Lifecycle "invalid lifecycle XML text"`, raised at `:854`) and `-notifications.adb:566-577` (`Malformed_Notification "invalid bucket-notification XML text"`); the comment that justifies the range at `lifecycle.adb:770-773`; the crate's own key domain, `Valid_Object_Key` at `src/flyology-object_storage.adb:479-490`, which rejects only NUL.

**Repro:** `tests/repros/src/repro_s3_domain_a_3.adb`, exit status 1, two failed expectations.

**What is wrong:** Two of three otherwise identical UTF-8 validators stop the single-byte range one code point early, at 0x7E instead of 0x7F, so a lifecycle or notification configuration containing DEL in any text member (`ID`, `Prefix`, tag `Key`/`Value`, `Id`, filter values) can be read from a server but never written back. The stated rationale does not apply: the comment says the validator "keeps the serializer from emitting bytes the matching parser must reject", but U+007F is not a C0 control, XML 1.0's `Char` production includes it, the matching parser accepts it, and the same value survives `Replication.Serialize` and every `XML_Writers`-based codec. The program parses a minimal valid configuration for each of Lifecycle, Notifications and Replication and hands the parsed value straight back to `Serialize`, once with a plain ASCII `ID`/`Id` and once with U+007F: the three plain-ASCII cases round-trip, replication with U+007F round-trips (`Parse accepted (210 bytes)`, `Serialize produced 258 bytes`) and is the key control, while `lifecycle ID with U+007F` and `notifications Id with U+007F` both parse (`Parse accepted (139 bytes)`, `(195 bytes)`) and then fail at `Serialize` with `invalid lifecycle XML text` and `invalid bucket-notification XML text`. A final case shows the boundary is not about control characters at all: U+0080, an actual C1 control, serializes through Lifecycle without complaint.

**Notes:** Whoever hits it is a caller round-tripping a configuration whose prefix or tag came from an object key containing DEL, which the crate's own `Valid_Object_Key` permits. It is deterministic. No existing test covers U+007F: `tests/src/s3_put_bucket_lifecycle_configuration_corpus.adb` and `tests/src/s3_bucket_notification_configuration_corpus.adb` exercise C0 controls and invalid UTF-8 only. The fix is to change `16#7E#` to `16#7F#` in the two bodies, matching `replication.adb:828`; no public value changes and no maintainer decision is needed beyond accepting the widened byte range. Refutations that failed: `S3.XML.Escape_Text` does not reject DEL, so the validators are not a harmless front-run; the key domain does not exclude DEL; and all three validators carry the same "raw C0 controls" comment, so the divergence is not deliberate.

### S3-DOMAIN-A-4: four response decoders require the botocore output *shape* name as the XML root

**Severity:** P1 (the discovery report also said P1, at Medium confidence because the AWS wire root names were memory). The verifier settled the names from the AWS S3 API Reference and kept the severity: the decoders cannot read a response from the only provider that implements the operations, which is a wrong result on valid input through a reachable path (`client-low_level.adb:9277`, `:9319`, `:9577`, `:16793`). It is not P0 because `docs/compatibility/s3.md:36-40` ends each of those rows with "external interoperability are not claimed", so nothing documented is violated on the client side — although `docs/qualification/list-directory-buckets.md:14` positively documents the non-AWS root `<ListDirectoryBucketsOutput/>` as the Flyology server's contract.

**Location:** the four `Root_Name` generic actuals at `src/flyology-object_storage-s3-inventory.adb:607-613`, `-metrics.adb:468-472`, `-analytics.adb:572-576` and `-intelligent_tiering.adb:528-532`, each preceded by the comment "Both element names are fixed by the pinned Botocore operation/output model."; the enforcement at `src/flyology-object_storage-s3-paginated_rest_xml_reads.adb:133-136` (open) and `:283-286` (close), exact comparison both times; the generated decoder `src/flyology-object_storage-s3-generated_list_directory_buckets_xml.adb:9-13` (`when Root => return "ListDirectoryBucketsOutput";`) with its message-less re-raise at `:272-274`; the strict runtime's check at `src/flyology-object_storage-s3-strict_xml_codecs.adb:312-315`; the generator rule at `tools/s3_codegen.py:815-816` (`root_name = shapes[root_shape].get("locationName", root_shape)`), the same rule for request payloads at `:1932`; the places where the crate already hard-codes the true wire root, `buckets.adb:914` (`ListAllMyBucketsResult`), `listings.adb:690` (`ListBucketResult`), `versions.adb:528` (`ListVersionsResult`), `metadata_configurations.adb:211` and `metadata_tables.adb:295`; the server emitters `src/flyology-object_storage-server-s3_applications.adb:9599-9608` and `:7237`; the qualification sentence `docs/qualification/list-directory-buckets.md:14`; the matrix rows `docs/compatibility/s3.md:36-40`.

**Repro:** `tests/repros/src/repro_s3_domain_a_4.adb`, exit status 1, four failed expectations.

**What is wrong:** The generator's rule "root element = payload shape's `locationName`, else the shape name" is right for request payloads, whose members carry a `locationName`, and wrong for responses, whose output shapes carry nothing: botocore's rest-xml parser ignores the root element name, so the model has never needed to record it. Dumped with python3, none of `ListBucketInventoryConfigurationsOutput`, `ListBucketMetricsConfigurationsOutput`, `ListBucketAnalyticsConfigurationsOutput`, `ListBucketIntelligentTieringConfigurationsOutput`, `ListDirectoryBucketsOutput`, `ListBucketsOutput`, `ListObjectVersionsOutput` or `ListObjectsOutput` carries a `locationName`, a `resultWrapper`, an `xmlNamespace` or a `payload` — the model is silent for every one of them, including the three whose wire roots the crate already hard-codes correctly, so the model cannot be the authority the comments claim. The AWS S3 API Reference, read from both the Response Syntax block and the Response Elements root-level-tag entry (three of the four also confirmed by a worked sample response on the same page), documents `<ListInventoryConfigurationsResult>` for ListBucketInventoryConfigurations, `<ListMetricsConfigurationsResult>` for ListBucketMetricsConfigurations, `<ListBucketAnalyticsConfigurationResult>` (singular "Configuration") for ListBucketAnalyticsConfigurations and `<ListAllMyDirectoryBucketsResult>` for ListDirectoryBuckets, while `API_ListBucketIntelligentTieringConfigurations.html` really does document the shape name `<ListBucketIntelligentTieringConfigurationsOutput>`, which is presumably why the pattern looked safe. Anyone calling the four affected operations against AWS gets an invalid-response failure on every 200; it is deterministic and total. ### S3-DOMAIN-A-5: the server-side PutBucketVersioning body parser is the only request codec that rejects an unqualified root

**Severity:** P0 (the discovery report said P2 by repository evidence, and P0 if a stock client were confirmed to send the body without `xmlns`). The condition it named is met. `mc version enable` — MinIO's own CLI, the default way to turn versioning on against any S3 endpoint — sends `<VersioningConfiguration><Status>Enabled</Status></VersioningConfiguration>` with a correct `Content-MD5` and is answered 400 `MalformedXML`, against a row (`docs/compatibility/s3.md:57`) that claims an "authenticated path-style server" and a "configuration-only six-server oracle". There is no client-side workaround: `mc` does not offer to add a namespace.

**Location:** `src/flyology-object_storage-s3-versioning.adb:41-55` (`Start_Element_Details` raises `Malformed_Configuration` with "bucket versioning namespace or attributes are invalid" when the namespace is not the S3 one and `Allow_Empty_Namespace` is False; the test itself at `:47-54`); `:171-186` (`Parse` passes `Allow_Empty_Namespace => False`, `Parse_Response` passes `True`); the server call at `src/flyology-object_storage-server-s3_applications.adb:10421-10425`, which invokes the strict `Versioning.Parse (Document)` after the Content-MD5 and checksum gates at `:10395-10420`; the lenient siblings `lifecycle.adb:63-85` (`Unqualified` is an accepted `Namespace_Style`), `notifications.adb:161-181` (identical) and `buckets.adb:531-545` (`Parse_Create_Configuration` has no namespace check at all; `grep -n Namespace_URI src/flyology-object_storage-s3-buckets.adb` returns nothing); the crate's own documentation at `src/flyology-object_storage-s3-versioning.ads:29-32` ("AWS responses use the S3 namespace, while a few otherwise compatible implementations omit it"); the existing assertions at `tests/src/object_storage_test_cases.adb:21868-21871` (`Expect_Malformed ("<VersioningConfiguration><Status>Enabled</Status></VersioningConfiguration>", "namespace-free versioning request accepted")`) and `:21879-21886` (`Parse_Response` accepts the same bytes); the matrix row `docs/compatibility/s3.md:57`.

**Repro:** `tests/repros/src/repro_s3_domain_a_5.adb`, exit status 1, three failed expectations, with `tests/repros/src/repro_s3_domain_a_5_live.adb` as the loopback holder used for the stock-client capture (it asserts nothing).

**What is wrong:** `Versioning.Parse` is the only request-body codec in the crate that treats the S3 namespace as a wire precondition, and the server calls exactly that one, so a `PUT /bucket?versioning` whose body omits `xmlns` gets 400 `MalformedXML` while the same client's lifecycle, notification and CreateBucket bodies succeed. The pinned model does not support the rule: `PutBucketVersioningRequest`'s `VersioningConfiguration` payload member carries `xmlNamespace`, which is what a serializer emits, and nothing marks it a parsing precondition. Three stock clients were driven at the in-process application with `PutBucketVersioning` and `Status=Enabled`. boto3 / botocore 1.43.89 and aws-cli v2 2.36.34 (Python 3.14.7) both send `<VersioningConfiguration xmlns="http://s3.amazonaws.com/doc/2006-03-01/"><Status>Enabled</Status></VersioningConfiguration>` and are rejected 400 `InvalidRequest` for the checksum reason (`requires one valid Content-MD5 header`), not the namespace, so both are unaffected by this finding. The strictness is not disclosed anywhere a client would look: the `.ads` documents "fail closed" for `Parse`, but neither `docs/compatibility/s3.md:57` nor `docs/qualification/put-bucket-versioning.md` names the namespace as a client requirement.

### S3-DOMAIN-A-6 (new): the listing query parsers reject `max-keys` above 1000 instead of capping the page

**Severity:** P1 (new; the verifier promoted it from the discovery report's first uncounted observation, which called it a documented policy value and marked its interop consequence "from memory, unverified"). It is neither documented as a wire rule nor consistent with AWS or MinIO, and a stock client hits it: a valid request is refused. It is not P0 because no default client invocation reaches it — the user must explicitly ask for more than 1000 — the caller can work around it by asking for 1000 or fewer, and the refusal is an honest 400 with a correct error code, losing no data.

**Location:** `src/flyology-object_storage-s3-listings.adb:111-118` (v1), `:223-230` (v2) and `src/flyology-object_storage-s3-versions.adb:134-141`, all three of the form `if Seen_Max_Keys or else not Number.Valid or else Number.Value > Core.Page_Size'Last then raise Malformed_List_Request with "invalid … max-keys";`; the bound itself at `src/flyology-object_storage-s3-core.ads:28`, `subtype Page_Size is Natural range 0 .. 1_000;`, a visible subtype; the server mapping of `Malformed_List_Request` to 400 `InvalidArgument` at `src/flyology-object_storage-server-s3_applications.adb:10763-10767` and the two neighbouring handlers; the backend page contract at `docs/compatibility/s3.md:863` ("max-keys 0..1000"), which is not a request-validity rule; the client side, where `Low_Level.List_Objects_Parameters.Max_Keys` is `S3.Core.Page_Size` so a Flyology client cannot even express the value.

**Repro:** `tests/repros/src/repro_s3_domain_a_6.adb`, exit status 1, three failed expectations.

**What is wrong:** The three listing query parsers reuse the response page bound `S3.Core.Page_Size'Last` as a request validity bound, so a request AWS documents as valid and MinIO answers with 200 is refused with 400 `InvalidArgument`. The AWS S3 API Reference is explicit that the parameter is a ceiling on the response, not a constraint on the request — `API_ListObjectsV2.html`, URI request parameters, `max-keys`: "Sets the maximum number of keys returned in the response. By default, the action returns up to 1,000 key names. The response might contain fewer keys but will never contain more." — the same wording appears for ListObjects and ListObjectVersions, and the `Errors` section of ListObjectsV2 lists only `NoSuchBucket`. The pinned MinIO answers `?max-keys=2000` and `?list-type=2&max-keys=2000` with 200, echoing `<MaxKeys>2000</MaxKeys>`. Against this crate's own application, aws-cli 2.36.34 gets `An error occurred (InvalidArgument) when calling the ListObjectsV2 operation: The ListObjectsV2 request is invalid` for `--max-keys 2000`, the same for `list-objects --max-keys 5000` and `list-object-versions --max-keys 2000`, while `list-objects-v2 --max-keys 1000` returns 200 with `"MaxKeys": 1000`; the same three commands against the pinned MinIO return 200. Anyone pointing a stock tool at a Flyology endpoint with an explicit large page hint gets a hard failure instead of a 1000-key page, and SDK paginators that pass a caller-supplied `MaxKeys` through do the same. The program sends six signed GETs through the in-process application: `?max-keys=1000`, `?list-type=2&max-keys=1000` and `?versions&max-keys=1000` all return 200 as controls, and the same three at 2000 each return 400 with an `InvalidArgument` body naming ListObjects, ListObjectsV2 and ListObjectVersions respectively. It is deterministic and affects the server only.

**Notes:** This needs a maintainer decision because it touches the visible subtype `S3.Core.Page_Size` (`core.ads:28`), which the "Ada interface values" rule puts under explicit approval: either the three query parsers clamp an oversized `max-keys` to `Page_Size'Last` and leave the subtype alone, which keeps every response bound and every backend contract intact and is exactly what AWS's own wording describes, or the request-side bound becomes a separate, wider type. The verification report recommends the clamp in the parsers, on the ground that it changes no public declaration. `docs/compatibility/s3.md:863` describes the backend page contract rather than the accepted request domain, and the two listing qualification documents mention 1000 only as the modeled default, so this is not a documented limitation. No existing test asserts the current rejection for values above 1000 in `tests/src/object_storage_test_cases.adb`; the fix should gain one.

### S3-DOMAIN-A-7 (new): `Versions.Validate` rejects every untruncated MinIO ListObjectVersions page, whatever the storage classes

**Severity:** P1 (new; the verifier found it while checking S3-DOMAIN-A-1 against a real server, and promoted it from the discovery report's fourth uncounted observation, which raised the mirror direction — `NextKeyMarker` present with an empty `NextVersionIdMarker` — and left it uninvestigated). Valid input raises through a reachable path, and as with S3-DOMAIN-A-1 it is not P0 because `docs/compatibility/s3.md:67` disclaims external interoperability for ListObjectVersions. In reach it is strictly worse than S3-DOMAIN-A-1: 100 per cent of untruncated MinIO pages fail, not only buckets containing a non-`STANDARD` version.

**Location:** `src/flyology-object_storage-s3-versions.adb:1031-1041`, whose first disjunct is `Value.Has_Next_Version_ID_Marker /= Value.Has_Next_Key_Marker`, followed by `or else Value.Is_Truncated /= Value.Has_Next_Key_Marker` and the non-emptiness pair, raising `Malformed_Version_Listing` with "inconsistent ListObjectVersions next markers"; the client mapping at `src/flyology-object_storage-client-low_level.adb:2226-2229`; the coverage gate at `tests/src/s3_implementation_corpus.adb:3318-3333`; the documented invariant at `docs/qualification/list-object-versions.md:87-89` ("truncated pages require both nonempty next markers, while final pages reject either one") and the corpus that enforces it, `tests/src/s3_list_object_versions_corpus.adb`.

**Repro:** `tests/repros/src/repro_s3_domain_a_7.adb`, exit status 1, one failed expectation; the live half is `tests/repros/src/repro_s3_domain_a_minio_probe.adb`.

**What is wrong:** `Versions.Validate` requires the two next-page markers to be present together and to match `IsTruncated`, a pairing the pinned model does not express — `ListObjectVersionsOutput` has no `required` list and `NextKeyMarker` and `NextVersionIdMarker` are plain optional strings with no cross-member constraint — and the AWS S3 API Reference does not require either, documenting both only as "When the number of responses exceeds the value of `MaxKeys`, … specifies the first … not returned", with no rule against emitting one, or an empty one, on an untruncated page. The pinned MinIO emits an empty `<NextVersionIdMarker></NextVersionIdMarker>` on every `?versions` response, including untruncated ones, and omits `<NextKeyMarker>` there, so `Has_Next_Version_ID_Marker` is True while `Has_Next_Key_Marker` is False, the first disjunct fires, and every page is rejected; its truncated pages carry both markers non-empty and are accepted. The client turns the exception into `Invalid_Response` and `Client.Objects.List_Versions_Page` returns nothing, so ListObjectVersions is completely unusable against MinIO through the high-level client, independently of S3-DOMAIN-A-1. It is deterministic. The program puts three documents through `S3.Versions.Parse_List_Object_Versions`, every `StorageClass` in them `STANDARD` so the storage-class rule cannot interfere: MinIO's untruncated envelope with the empty `NextVersionIdMarker` removed (control, `decoded, versions=1 truncated=FALSE`), MinIO's truncated envelope with both markers non-empty (control, `decoded, versions=1 truncated=TRUE`) and MinIO's actual untruncated envelope (`REJECTED, inconsistent ListObjectVersions next markers`). Live, the probe lists a second MinIO bucket holding only a default-class object and `List_Versions_Page flyology-review-domain-a-standard` still raises `Invalid_Response: malformed ListObjectVersions response`, which isolates this finding from S3-DOMAIN-A-1.

**Notes:** This finding and S3-DOMAIN-A-1 both break ListObjectVersions against MinIO and must be fixed together; fixing S3-DOMAIN-A-7 alone still loses any page containing a `REDUCED_REDUNDANCY` version, and fixing S3-DOMAIN-A-1 alone changes nothing at all against MinIO, since every page fails here first. Nothing in the repository catches either, because no third-party lane runs ListObjectVersions: `tests/src/s3_implementation_corpus.adb:3318-3333` gates the corpus's only `List_Versions_Page` caller on `FLYOLOGY_S3_IMPLEMENTATION` being `flyology-files` or `flyology-sqlite`, and the in-house server never emits a lone marker. A fix needs a maintainer decision about how much presence structure the decoder should require of a foreign server: the narrowest change that admits MinIO is to key the rule on truncation and non-emptiness — require both markers non-empty when `IsTruncated` is true, and ignore a present-but-empty marker otherwise — but that relaxes the invariant documented at `docs/qualification/list-object-versions.md:87-89`, so the qualification text and `tests/src/s3_list_object_versions_corpus.adb` must change with it. The direction the discovery report named, a present `NextKeyMarker` with an empty `NextVersionIdMarker`, is not reproducible against MinIO, whose truncated pages always carry both markers non-empty.

Two further observations were recorded by the verifier and are not counted:

- Codec diagnostics are erased by the shared XML boundary. `S3.XML.Parse` catches `others` and re-raises as `XML_Error "malformed S3 XML document"` (`s3-xml.adb:203-207`), so a `Malformed_Version_Listing` raised inside a SAX callback — "invalid ObjectVersion storage class", "unknown ListObjectVersions response field", "incomplete ObjectVersion entry" — reaches the caller as `malformed ListObjectVersions XML: malformed S3 XML document`, which is visible in the S3-DOMAIN-A-1 output.
