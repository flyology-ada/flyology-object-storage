## BACKEND-FILES: pure-files backend, durability bridge and secure erase (BACKEND-FILES-1 .. BACKEND-FILES-6)

The area covers `src/flyology-object_storage-backends-files.ad?`, `src/flyology-object_storage-durability.ad?`, `src/flyology_object_storage_durability.c`, `src/flyology_object_storage_secure_erase.c` and `docs/architecture/files-layout.md`, with `src/flyology-object_storage-backends.ad?` for the contracts, `src/flyology-object_storage-backends-memory.adb` as the reference oracle, and the admission bounds, status mapping and annotation routing in `src/flyology-object_storage-server-s3_applications.adb` read to establish reachability.

### BACKEND-FILES-1: CompleteMultipartUpload in an unversioned bucket inherits the replaced object's annotations and orphans the previous annotation sidecar

**Severity:** P1 (the discovery report also said P1).

**Location:** `src/flyology-object_storage-backends-files.adb:11810-11811` and `:11854`, where `Complete_Multipart_Upload` targets the fixed `Object_Path` for `Versioning_Unconfigured` and calls `Write_Header` with no `Annotation_Generation_ID`; `Write_Header`'s trailing field at `:2340-2350` and `:2493-2494`; the read-back into `Info.Version` at `:2811-2827`; the path-derived fallback `Stored_Annotation_Generation_ID` at `:2873-2907`, specifically `:2892-2896`; sidecar resolution at `:891-909`; the ordinary PUT path that mints a fresh identity and removes the replaced sidecar at `:7093-7099`, `:7128-7132`, `:7247-7249` and `:7388-7392`; the versioned generation file name at `:11812-11843`; `Delete_Bucket`'s sweep at `:3575-3875`; the reference backend's `Annotations.Clear` at `src/flyology-object_storage-backends-memory.adb:3345`; contract at `src/flyology-object_storage-backends.ads:2288-2290`; annotation routing at `src/flyology-object_storage-server-s3_applications.adb:15622`, `:15653`, `:15683` and `:15736`.

**Repro:** `tests/repros/src/repro_backend_files_1.adb` with helper `tests/repros/src/repro_backend_files_support.ad?`, exit status 1, four failed expectations.

**What is wrong:** Multipart completion writes its record without an annotation generation identity, so the persisted field is empty and the sidecar identity falls back to `SHA256(object path)`; in an unversioned bucket every generation of a key lives at the same fixed path, so two completions in a row on one key share one annotation sidecar. Annotations acknowledged against the first completed object are then served, byte for byte and with their original ETag, as annotations of the second completed object's bytes, and completion never removes the replaced generation's sidecar the way ordinary PUT does, so a completion that replaces a PUT-created generation leaves a `generation-*` directory no later request can read or delete. `Delete_Bucket` inspects only `objects/`, `versions/`, `multipart/` and `configuration/`, so the leak is permanent for the life of the root. Both effects are deterministic and need no concurrency; any client that combines annotations with multipart uploads on an unversioned bucket hits them. The reference memory backend clears the annotation map on completion (`memory.adb:3345`), so the intended contract is an empty annotation set on the newly published generation and the two backends disagree.

**Notes:** The verifier corrected one sub-claim of the discovery scenario: an ordinary PUT, annotate, then one completion does **not** expose the PUT generation's annotations through the API, because the PUT minted its own generation identity; that sequence produces only the orphan, and inheritance needs two completions in a row. The defect is confined to `Versioning_Unconfigured`, because a versioned publication's file name carries the publication number and so yields a distinct path-derived identity. No existing test asserts the wrong behaviour and none covers the combination: `tests/src/multipart_part_conformance.adb` has no annotation case and `tests/src/object_storage_test_cases.adb` has no files-backend annotation-plus-multipart sequence. A fix needs one maintainer decision: whether completion should mint a fresh annotation generation identity the way PUT does and remove the previous sidecar, or whether the path-derived legacy fallback should be retired for records written by current code, which changes the on-disk contract for FOSOBJ01-06 records. BACKEND-FILES-4 is the other half of the annotation-lifecycle problem (removal ordering), and BACKEND-FILES-6 shows the versioned path's own identity reuse.

### BACKEND-FILES-2: Valid object keys beyond 464 bytes are unusable on the files backend and are reported as a retryable 503

**Severity:** P1 (the discovery report also said P1).

**Location:** `src/flyology-object_storage-backends-files.adb:835-859` (`Encoded_Object_Path`, two hex characters per key byte, a new component every 100 characters); `:217-239` (`Ensure_Directory` through `Ada.Directories.Create_Directory` on absolute paths) and `:7443-7457` (the `when others` handler that maps the resulting `Use_Error` to `Backend_Unavailable`); the depth guard `Maximum_Object_Path_Depth = 32` at `:113`; key contract at `src/flyology-object_storage.adb:479-489` and `src/flyology-object_storage.ads:667-670`; status mapping at `src/flyology-object_storage-server-s3_applications.adb:1951-1954`; documentation at `docs/architecture/files-layout.md:4-6`.

**Repro:** `tests/repros/src/repro_backend_files_2.adb`, exit status 1, one failed expectation; the program also binary-searches and prints the measured ceiling.

**What is wrong:** The files backend expands every key byte to two hexadecimal characters and inserts a path separator every 100 characters, so a key of N bytes costs roughly 2.02N path bytes below `buckets/<name>/objects/`, while `Valid_Object_Key` admits 1,024 bytes. macOS enforces `PATH_MAX` = 1024 on every path-taking syscall, so `mkdir` on an intermediate component fails `ENAMETOOLONG`, `Create_Directory` raises `Use_Error`, and the blanket handler reports `Backend_Unavailable`, which the S3 adapter renders as 503 `SlowDown` — a status aws-cli and boto3 retry with backoff, so the request never completes and never reports a permanent error. Measured on this host (`getconf PATH_MAX /` = 1024, 49-byte root): 464 bytes is the largest accepted key and 465 already fails, matching the arithmetic exactly, so the ceiling scales with the root path length and is deployment-dependent rather than documented. HEAD, GET and DELETE of such a key fail identically, so an object written on Linux (limit 4096) becomes unreadable if the same root is opened on macOS, which `.github/workflows/ci.yml` runs as a qualified platform. The reference memory backend accepts the same 1,024-byte key (repro control), and the pinned model's `ObjectKey` shape expresses no maximum, so the crate's own documented 1,024-byte bound is what the repro asserts against.

**Notes:** No files-specific key-length limit exists in `docs/architecture/files-layout.md`, `docs/compatibility/s3.md` or the backend's own `.ads`; `files-layout.md:4-6` bounds each component, not the total path. The depth guard never fires, because a 1,024-byte key needs 21 components. No existing test puts a key longer than a few dozen bytes into a `Files.Store`. A fix needs a maintainer decision on externally visible policy: either a documented files-backend key-length limit reported as `Invalid_Request` or `Capacity_Exceeded` rather than the retryable `Backend_Unavailable`, or a path encoding that bounds total path length (for example digest-prefixed sharding), which changes the on-disk layout. AWS S3's own 1,024-byte key limit was recorded by the verifier as from memory and unverified; it is not load-bearing, since the crate's own contract supplies the bound.

### BACKEND-FILES-3: Singleton bucket-configuration readers size a stack local from the stored document, so a 3 MiB acknowledged policy kills the reading process

**Severity:** P0 (the discovery report said P1; the verifier raised it because the reader allocates a frame past the end of a 2 MiB task stack — an unchecked stack overflow — and the observed effect is abrupt process termination, SIGKILL with shell status 137, which on a server takes down every concurrent request rather than failing the one that asked).

**Location:** `src/flyology-object_storage-backends-files.adb:1579-1583` (`Read_String` declares `Result : String (1 .. Length)`, a dynamically sized local; only the 64 KiB `Data` buffer is chunked); the seven readers with that shape — bucket policy `:1780`/`:1795`, CORS `:1809`/`:1824`, encryption `:1839`/`:1857`, ownership controls `:1872`/`:1890`, lifecycle `:1908`/`:1930`, logging `:1947`/`:1965`, notification `:1980`/`:1998`; the already-chunked writer and readers at `:1478-1504` and `:1610-1631`; `Get_Bucket_Policy`'s `when others` handler at `:6258-6270`; admission bound `Maximum_Bucket_Policy_Bytes` = 16 MiB at `src/flyology-object_storage-backends.ads:2792` and `Valid_Bucket_Policy` at `src/flyology-object_storage-backends.adb:199-200`; request-body sizing at `src/flyology-object_storage-server-s3_applications.adb:176-187`; toolchain `s-parame.adb:55-66` (2 MiB `Default_Stack_Size`); flyology 0.1.1 `src/flyology-io-structured_servers.adb:386-391` (the HTTP `Worker` task declares no `Storage_Size`).

**Repro:** `tests/repros/src/repro_backend_files_3.adb`, exit status 1, one failed expectation; the child process reading the 3 MiB policy from a default-`Storage_Size` task is reported by `/bin/sh` as status 137 (SIGKILL), while the 1 MiB child control succeeds with status 0.

**What is wrong:** Reading a bucket policy, CORS, encryption, ownership-controls, lifecycle, logging or notification document needs as many contiguous bytes of the calling task's primary stack as the document has, while the writer streams the same document in 64 KiB chunks and admission allows 16 MiB. Any document larger than the reading task's stack is therefore writable, acknowledged with 200, durable on disk and unreadable afterwards. Because Flyology's HTTP worker task declares no `Storage_Size`, every server worker reads with GNAT's 2 MiB default, so the practical ceiling is roughly 2 MiB. The failure is not graceful: the oversized frame skips past the task's guard page and the process is killed with no Ada exception and no diagnostic, so a single `GetBucketPolicy` for an already-accepted configuration terminates the server for every client. It is fully deterministic, and the repro's environment-task control shows the bytes on disk are intact, so this is a read-path defect rather than a corruption.

**Notes:** The failure mode a caller sees depends on which task issues the read: from the environment task with headroom the same read succeeds, and with a 3 MiB local already on that stack it returns `Backend_Unavailable` instead — the same defect, not a separate one. That the 16 MiB documented bound also exceeds this host's 8 MiB process stack is an inference from the measured stack sizes, not a separate measurement. Existing coverage does not reach it: `tests/src/object_storage_test_cases.adb:1524-1579` round-trips 16 MiB only through replication, which uses the chunked `Read_Unbounded_String`, and the policy and CORS cases at `:583-657` and `:702-766` use short strings. The fix is mechanical — route these seven readers through `Read_Unbounded_String`, as the metadata, replication, website and named-configuration readers already do — and needs no new maintainer decision unless the maintainer also wants a smaller documented bound for these documents. If a maintainer's rubric treats an unchecked stack overflow as availability-only, this is still at minimum P1, because an acknowledged configuration can never be read back.

### BACKEND-FILES-4: A failed DeleteObject destroys the object's acknowledged annotations while leaving the object in place

**Severity:** P0 (the discovery report said P1; the verifier raised it because acknowledged payload data is destroyed by an operation that reports failure and did not delete its target, with no request having asked for that deletion — data loss under the rubric's first clause rather than a wrong result).

**Location:** `src/flyology-object_storage-backends-files.adb:8430-8435` (unversioned current delete) and `:8419-8424` (exact-version delete), both calling `Remove_Annotation_Generation` before `Remove_Path`; `Remove_Annotation_Generation` through `Remove_Tree` at `:1034-1046` and `:338-346`, where `Validate_Tree_Symlink_Free`, `Delete_Tree` and `Sync_Directory` make the removal durable before the unlink is attempted; `Remove_Path`'s `Data_Error` at `:8320-8331`; the batch handler that reports the failure at `:8517-8541`; the same ordering on the PUT path at `:7388-7395`; annotation payload identity at `src/flyology-object_storage.ads:571-577`; status mapping at `src/flyology-object_storage-server-s3_applications.adb:1951-1954`; documentation at `docs/qualification/delete-object.md:46-51`.

**Repro:** `tests/repros/src/repro_backend_files_4.adb`, exit status 1, two failed expectations; the injection makes `buckets/<b>/objects/` mode `0500` so the sidecar removal succeeds and the unlink fails, and the uninjected control key deletes cleanly.

**What is wrong:** `Delete_One` destroys the object's annotation sidecar, including an fsync of the sidecar's parent directory, before it issues the unlink that is the delete's publication point. If the unlink fails — EACCES on a directory that lost write permission, EPERM after a read-only remount, EIO, or `Data_Error` because a concurrent external change made the path something other than an ordinary file — the batch is reported as `Backend_Unavailable` (503 `SlowDown` at the S3 boundary), the object is still there and still readable, and the annotations the client stored and the server acknowledged are gone, with no request having asked for their deletion, no recovery path, and no diagnostic distinguishing this from an ordinary transient failure. Annotations are independent payloads with their own size, ETag and checksum, so nothing can re-derive them. The reproduction is fully deterministic.

**Notes:** The verifier confirmed the deterministic no-crash variant, which is the strongest one. The crash variant follows from the same ordering plus the fsync in `Remove_Tree` — a power loss between the two steps leaves exactly this state on any filesystem — and is verified by reading only, because the crash corpus lives in `tests/src/files_crash_probe.adb` and `tests/scripts/test.sh`, which this review may not modify; the deterministic crash matrix there contains no annotation scenario at all, so it is not gated. The btrfs-specific PUT-path window from the discovery report remains unverifiable on this APFS host. `docs/qualification/delete-object.md:46-51` documents that a status after publication is not proof the object deletion did not occur; it says nothing about destroying a different acknowledged payload when the deletion demonstrably did not occur. The fix should be a plain reordering — unlink first, then sweep the sidecar, with an orphan sweep for the crash case — and needs no new public constant or API, but the maintainer must decide whether the orphan sweep belongs in `Open`, in `Delete_Bucket`, or both. The orphan half is shared with BACKEND-FILES-1.

### BACKEND-FILES-5: Multipart operations with a valid upload ID but a different key answer `Backend_Unavailable` instead of `Not_Found`

**Severity:** P2 (the discovery report also said P2).

**Location:** `src/flyology-object_storage-backends-files.adb:3412-3446` (`Read_Manifest` locates the manifest by bucket and upload ID only, then calls `Read_Header` with the requested key); `:3070-3087` (`Read_Header` raises `Ada.IO_Exceptions.Data_Error` on a stored-key mismatch); the key-blind presence tests at `:10829-10837` (UploadPart), `:11114-11122` (ListParts), `:11611-11618` (Complete) and `:11980-11986` (Abort); the blanket handlers at `:11061-11078` and their three twins; the opaque upload-ID derivation at `:10690-10694`; contract at `src/flyology-object_storage-backends.ads:2657-2659` and `:2771-2773`; the reference behaviour at `src/flyology-object_storage-backends-memory.adb:332-346`; status mapping at `src/flyology-object_storage-server-s3_applications.adb:1951-1954`.

**Repro:** `tests/repros/src/repro_backend_files_5.adb`, exit status 1, four failed expectations, one per entry point; the memory backend runs the identical sequence first as the control and answers `Not_Found` each time.

**What is wrong:** The files backend resolves an active multipart upload by upload ID alone — the upload directory is named `SHA256 (Upload_ID)`, independent of the key — and discovers the key mismatch only when `Read_Header` validates the manifest's stored key, which it signals with `Data_Error`; every multipart entry point's blanket `when others` handler turns that into `Backend_Unavailable`, rendered as 503 `SlowDown`. A client that mistypes or mangles a key on a retry therefore gets a retryable server-overload response where AWS and the reference memory backend return a definitive 404 `NoSuchUpload`; aws-cli and boto3 retry 503 with exponential backoff, so the request loop terminates only when the retry budget is exhausted, and an `AbortMultipartUpload` sent with the wrong key can never retire the upload nor tell the client why. It is deterministic. The backend contract states that upload identifiers are scoped to the exact bucket and key and that a missing upload is `Not_Found`, so this is a documented-contract violation as well as a cross-backend divergence.

**Notes:** It needs a client mistake to trigger, which is why it stays an edge case, but the consequence is a wrong diagnostic that turns a permanent error into an indefinitely retried one. No existing test asserts either behaviour; `tests/src/multipart_part_conformance.adb` never uses a mismatched key and makes no `Not_Found` assertion at all. A fix is a key comparison before `Read_Manifest`, or mapping the manifest key check's `Data_Error` to `Not_Found`, and needs no new maintainer decision.

### BACKEND-FILES-6: Deleting the newest generation lets the next PUT reuse the deleted generation's opaque version ID

**Severity:** P2 (the discovery report also said P2).

**Location:** `src/flyology-object_storage-backends-files.adb:1254-1270` (`Next_Generation_Publication` returns `max(publication) + 1` from a scan of the retained generations, so the counter is not monotonic across deletions); the version-ID derivation at `:7288-7297`, repeated for delete markers at `:8246-8250` and for multipart completion at `:11821-11829`; the exact delete that unlinks the generation file outright at `:8419-8424`; the null-tombstone path that does not apply at `:8400-8418`; the annotation identity that does not collide at `:7093-7099`; contract at `src/flyology-object_storage-backends.ads:50-52` and the backend note at `src/flyology-object_storage-backends-files.adb:47-49`.

**Repro:** `tests/repros/src/repro_backend_files_6.adb`, exit status 1, two failed expectations; the memory backend runs the identical sequence first as the control and mints a different identifier.

**What is wrong:** The opaque version ID is a pure function of the publication number, and an exact delete removes the generation file with no residue that keeps the counter high, so deleting the newest generation (or every generation above some N) and republishing mints the deleted generation's exact version ID again. `GET key?versionId=<that id>` then returns the new bytes with status 200 instead of 404, so a client, replicator or audit consumer keyed on (key, version ID) silently reads different content under an identifier it believes it has already seen or already deleted. The memory backend uses a monotonic publication counter and never repeats, so the two backends disagree on an externally visible identity. The effect is deterministic, and the repro confirms the second-order consequence empirically, not only the identifier collision.

**Notes:** It stays P2 because it needs an exact delete of the newest generation followed by a republish, but the consequence is stronger than "two versions share an ID". Existing coverage only asserts that three consecutive publications differ (`tests/src/versioned_object_conformance.adb:544-549`); no test deletes the newest generation and republishes. S3's own uniqueness of version identifiers per object version was recorded by the verifier as from memory and unverified; the cross-backend divergence does not depend on it. A fix needs a maintainer decision because it changes the on-disk layout or record format: persist a per-key monotonic publication high-water mark, leave a tombstone for exact deletes the way null deletes already do, or mix an entropy source into the version-ID digest, which would end the current property that the identifier is reproducible from the generation file name.

## Coverage evidence: BACKEND-FILES

- Key path encoding is injective (uppercase hex only, no `.`, `..` or separator components, no case-folding collisions, distinct `.fos`/`.versions`/`.annotations` suffixes), and every path component derived from an untrusted identifier goes through SHA-256 or `Valid_Bucket_Name`; exact version IDs are compared against a directory scan and never composed into a path.
- Symlink handling checks every path symlink-first before kind or existence, `Validate_Immediate_Directory` uses raw `readdir` so dangling links are detected, and TOCTOU against a hostile local process is explicitly out of contract (`docs/architecture/files-layout.md:80-85`).
- Publication gate discipline: all 55 `Acquire_Publication` sites release on every normal and exceptional path (235 `Release` calls inspected), `Acquire_Publication` itself releases on `Validate_Required_Roots` failure, and the timed entry loop honours deadline and cancellation.
- Publication sequences (temp under `tmp/`, `Validate_New_Temp_Target`, `Sync_File`, rename, `Sync_Directory` of destination then `tmp/`) for object PUT, tags, object-lock rewrite, versioning, Object Lock enablement, bucket tags, policy, CORS, every singleton and named configuration document, metadata state, bucket create and delete, multipart initiate, part, completion and abort; temp files and directories are removed on every failure path inspected.
- Conditional writes are evaluated under the gate against the freshly read header immediately before rename in PUT, COPY and multipart completion, and two concurrent create-if-absent writers serialize correctly.
- Generation selection: current, null and exact semantics; the legacy `objects/` file as null version; delete-marker placement for enabled and suspended buckets; tombstone-based exact-null deletion with `Recover_Null_Tombstones` on `Open`; `Remove_Superseded_Null_Generations` also removes sidecars.
- ListObjectVersions bytewise key order, newest-publication-first within a key, `IsLatest` for markers, key and version marker resume, and common-prefix cursor advancement and dedup; ListObjects lists only the current non-marker generation per key.
- Record format: bounded lengths for every header field, exact file-size check against `Body_At + Size`, in-place patch offsets (`Body_Size_Position` 29, `Metadata_Position` 37) verified against the layout, part metadata monotonic and size-summed, checksum and method consistency.
- Streaming reads hold the file descriptor across gate release, so a concurrent unlink, tag rewrite or abort cannot tear a reader on POSIX; every `File_Type`, `Search_Type` and `Dir_Type` inspected is closed in its matching handler; the durability bridge frees its C string on every path and uses `F_FULLFSYNC` with an `fsync` fallback, and `secure_erase` is a volatile byte loop.
- Verifier checks with no finding: the S3 adapter does not clamp policies before they reach the backend, GNAT does not heap-allocate a large dynamically sized local, versioned buckets do not share the annotation-sidecar identity, tombstones do not keep the generation counter high, and no key check exists before `Read_Manifest` in any of the four multipart entry points.

- `Complete_Multipart_Upload` (`:11554-11954`) and `Copy_Object` snapshot creation (`:7693-7725`) hold the publication gate while copying the whole body, so every other operation on the store blocks for that duration and deadline-bound callers fail with `Timeout_Error`; a bounded stall and a latency concern, not a hang.
- `List_Object_Versions` (`:10604-10610`) and the memory backend (`memory.adb:2677-2687`) both return `Invalid_Request` when a supplied key-marker/version-id-marker pair no longer exists; consistent across backends, and AWS behaviour is not verifiable from the pinned model.
- `Put_Object_Internal` samples `Info.Modified` before the body is streamed (`:7113`), so `Last-Modified` reflects upload start; ordering uses publication numbers, so listings stay correct.
- `Open` takes no cross-process lock, so two processes opening one root corrupt each other's staging assumptions; documented as unsupported.
- `Has_Objects` (`:3508-3510`) calls `End_Search` in its handler even when `Start_Search` never ran; harmless with GNAT's implementation and shadowed by the outer handler.
- `List_Objects` and `List_Object_Versions` call `Select_Generation`, a directory scan, per file, making listings O(files x generations); performance only.
- `Get_Object` reports `Partial => False` for a range request on an empty object (`Empty_Object_Range`, `:8042-8050`); range resolution policy lives in the core package, outside this area.
- Policy values not counted: `Maximum_Object_Path_Depth` = 32, `Maximum_Metadata_Length` = 8 KiB, `Maximum_Checksum_Length` = 96, 64 KiB streaming buffers, the 10 ms gate poll interval and the 16 MiB document bounds.
