### CLIENT-BUCKETS-1: authentication rejections are recognised only at HTTP 401, so every stock server's `403 InvalidAccessKeyId` / `403 SignatureDoesNotMatch` becomes `Corrupt_Or_Invalid_Response` and, for mutations, `..._Outcome_Unknown`

**Severity:** P1 (the discovery report said P2 because the misclassification is "conservative, therefore safe"). The verifier raised it after measuring the one fact the discovery report held as unverified memory: the pinned MinIO release `RELEASE.2025-09-07T16-13-09Z` answers an unknown access key with `403 InvalidAccessKeyId` (`Content-Length: 378`) and a wrong secret with `403 SignatureDoesNotMatch` (`Content-Length: 433`), and this crate's own S3 application answers both with `403 SignatureDoesNotMatch`; neither ever emits 401. With that captured, the rubric's P1 clause is met on all three counts: the path is the most common operator error, the input is a well-formed stock rejection, and two documented public enum meanings are contradicted — `Corrupt_Or_Invalid_Response  Response was not conclusive or valid` (`client.ads:36`) is reported for a response that is both conclusive and valid, and `Bucket_Creation_Outcome_Unknown  Creation must be reconciled` (`client-buckets.ads:150`) instructs the caller to reconcile a request the server refused before touching any state. The "conservative" reading would hold if the value were advisory; it is the documented decision input for whether a mutation must be reconciled before retry. It is not P0 because `Result.Response.Error.Code` still carries the true code, so a caller who ignores the classification is unaffected.

**Location:** `src/flyology-object_storage-client-buckets.adb:4109` — the only 401 pairing in `Normalize_Create_Bucket_Response`'s `Conclusive_Rejection`, `or else (Value.Status = 401 and then Code = "InvalidAccessKeyId")` — and `:4110`, the only 403 pairing, `Code = "AccessDenied"`; `:4123-4131`, where `Failure` is `Authentication_Failed` only for `(401, InvalidAccessKeyId)` and `Authorization_Failed` only for `(403, AccessDenied)`, everything else falling through to `Invalid_Request`, `Unavailable_Or_Retryable` or `Corrupt_Or_Invalid_Response`; `:4136-4143`, where `Disposition` is `Bucket_Definitely_Not_Created` only when `Conclusive_Rejection` and `Bucket_Creation_Outcome_Unknown` otherwise; the same shape in the shared classifier for the generated bucket mutations at `:26443-26453` (`Conclusive_Generated_Mutation_Rejection`) and `:26464-26476` (`Generated_Mutation_Response_Failure`), in bucket tagging at `:24417-24426` (`Conclusive_Bucket_Tag_Rejection`) and `:24437-24450` (`Bucket_Tag_Response_Failure`), and on the read path at `:23474-23477` (`Normalize_Get_Bucket_Location_Response`); the single classifier that switches on status alone, `Normalize_Head_Bucket_Response` (`:4796-4822`), whose `elsif Value.Status = 403 then Authorization_Failed` at `:4810-4811` turns a bodyless credential rejection into an authorisation label instead; the in-repo server's own answer, `Verify_Request` mapping an unknown key and a bad signature alike to `Credential_Rejected` at `src/flyology-object_storage-server-authentication.adb:213-216` and `Send_Authentication_Error` emitting `403 SignatureDoesNotMatch` at `src/flyology-object_storage-server-s3_applications.adb:1907-1910`; the existing assertions of the wrong behaviour at `tests/src/flyology-object_storage-client-buckets-testing.adb:130`, `:271`, `:437`, `:711`, `:846`, `:982`, `:1120`, `:1257`, `:1391`, `:1527` and `:1658`.

**Repro:** `tests/repros/src/repro_client_buckets_1.adb` with helper `repro_client_buckets_fake.ads/.adb`, exit status 1, eight failed expectations.

**What is wrong:** every `Normalize_*_Response`, `Conclusive_*_Rejection` and `*_Response_Failure` body in `client-buckets.adb` enumerates exact `(status, code)` pairs, and the only authentication pair enumerated is `(401, "InvalidAccessKeyId")`. No S3 server in evidence returns 401 for a credential problem: MinIO returns `403 InvalidAccessKeyId` for an unknown key and `403 SignatureDoesNotMatch` for a bad signature, and this crate's own server returns `403 SignatureDoesNotMatch` for both. The pair therefore never matches, the response falls through to `Corrupt_Or_Invalid_Response`, and because the same predicate also decides `Conclusive_Rejection`, every bucket mutation additionally reports `..._Outcome_Unknown`. The caller is told that a well-formed conclusive refusal was "not conclusive or valid" and that the mutation must be reconciled by a read before any retry, when nothing was mutated and the correct action is to fix the credentials. It is deterministic and hits anyone who mistypes a key or lets a secret rotate, including anyone running this client against this repository's own server. `grep -c 'Status = 401 and then Code = "InvalidAccessKeyId"'` gives 88 occurrences in `client-buckets.adb`, and `rg InvalidAccessKeyId src/ server/src/` matches only the client packages, so no in-repo server ever emits the pair the client waits for. The program first runs two in-process exchanges against the crate's own S3 application, one with the access key in the credential replaced and one with a single signature hex digit flipped, and prints `HTTP 403 <Code> = "SignatureDoesNotMatch"` for both; it then serves the verbatim MinIO 403 documents from a scripted loopback origin and drives `Get_Location` (read), `Put_Tags` (mutation) and `Create` (mutation) through them, each reporting `CORRUPT_OR_INVALID_RESPONSE` and, for the two mutations, `BUCKET_TAG_MUTATION_OUTCOME_UNKNOWN` and `BUCKET_CREATION_OUTCOME_UNKNOWN`. Six control legs replay the two enumerated pairs (`401 InvalidAccessKeyId`, `403 AccessDenied`) through the same code and all pass, which isolates the missing pairs as the cause; the origin served all eleven exchanges exactly once.

**Notes:** The live MinIO run reaches the same classification through the same public calls with no scripted bytes (`repro_client_buckets_probe.adb`: `location/wrong-key` and `location/wrong-secret` both `CORRUPT_OR_INVALID_RESPONSE`, `put-tags/wrong-key` and `put-tags/wrong-secret` both `CORRUPT_OR_INVALID_RESPONSE` with `BUCKET_TAG_MUTATION_OUTCOME_UNKNOWN`, and a `put-tags/control` that reaches `BUCKET_TAGS_REPLACED` with `NO_FAILURE`), so the finding does not depend on the scripted origin. This is not a documented limitation: `docs/compatibility/s3.md` and `docs/qualification/*` say nothing about the accepted status and code pairs for authentication, and the closest text, "every accepted service status/code pair" at `docs/qualification/list-buckets.md:21-22`, describes the corpus rather than a limitation. `review/baseline/service-2.json` has no error shape for `InvalidAccessKeyId` or `SignatureDoesNotMatch`, so the pinned model cannot justify the 401 pairing either way. The unit suite pins the wrong behaviour: `tests/src/flyology-object_storage-client-buckets-testing.adb` carries 32 `401, "InvalidAccessKeyId"` rows and no row anywhere presents `403 InvalidAccessKeyId` or `403 SignatureDoesNotMatch`, and `tests/src/s3_http_socket_corpus.adb` has 401 rows of the same shape; those rows may stay if the 401 pairing is retained, but a fix must add the 403 rows. The same fall-through catches any structured rejection whose exact pair is unlisted, which is the structured-error half of the gap whose bodyless and non-XML half is CLIENT-LOW-4 (`src/flyology-object_storage-client-low_level.adb:1956-1958`); CLIENT-LOW-4 reaches callers of this file through the `Raise_*_Exchange_Failure` mappers at `client-buckets.adb:108-112` and `:137-141`, so the two are complementary and neither is counted twice. `Normalize_Head_Bucket_Response` (`:4796-4822`) is the one classifier that would not fall through, because it switches on status alone; it labels the same 403 `Authorization_Failed`, which is wrong in a different way and must be settled by the same decision. A fix is a maintainer decision about the public error surface: which `(status, code)` pairs count as conclusive authentication rejections (at minimum `403 InvalidAccessKeyId` and `403 SignatureDoesNotMatch`, with `403 RequestTimeTooSkewed` and `400 AuthorizationHeaderMalformed` in the same class), and whether the 401 pairing is kept for compatibility. The identical pattern appears at 18 sites in `client-objects.adb` and 11 in `client-transfers.adb`, so the decision should be made once and applied uniformly.

### CLIENT-BUCKETS-2: a bodyless HeadBucket rejection discards `x-amz-bucket-region`, so `Client.Buckets.Head` cannot report where a redirected bucket lives

**Severity:** P2 (the discovery report also said P2; unchanged). Confirmed for the mechanism and its consequence at every layer of this repository, with one boundary recorded: the discovery report's external premise, that AWS attaches `x-amz-bucket-region` to the 301/403/404 HeadBucket responses used for region discovery, was not checked against a live AWS endpoint and remains unverified. MinIO was checked and does not redirect at all: a HeadBucket signed with an `eu-west-1` credential scope against a bucket MinIO reports as `us-east-1` answers `200 OK` with no `x-amz-bucket-region` header. No server in the six-server matrix can produce the shape, so the repro supplies the header itself. The discarded datum and the `.ads` sentence it contradicts are both real, but reaching it needs a cross-region bucket plus a wrong signing region, which is the rubric's "contract drift needing unusual input".

**Location:** `src/flyology-object_storage-client-low_level.adb:4952-4964`, where `Decode_Head_Bucket_Complete_Response` builds `Headers.Bucket_Region => H ("x-amz-bucket-region")`, and `:4965-4966`, where it passes `Headers` into `Decode_Head_Bucket_Response` for every status; `:4886-4906`, where `Headers` is consulted only inside the `Status = 200` branch and returned as `Result => Headers`; `:4907-4913`, the `else` branch returning `(Kind => Head_Bucket_Rejected, Status => Status, Error => Head_Error (...))` with no mention of `Headers`; `:4865-4871`, where `Head_Error` synthesises `Code => "HTTP" & Status_Text`, `Message => Operation & " returned HTTP status " & Status_Text` and `Resource => US.Null_Unbounded_String`, carrying through only `Request_ID` and `Host_ID`, so there is no field a region could hide in; `src/flyology-object_storage-client-low_level.ads:1396-1404`, where the `Head_Bucket_Rejected` variant has exactly `Status` and `Error`; `src/flyology-object_storage-client-buckets.ads:10129-10141`, where the convenience `Head_Outcome` likewise carries `Region` only on `Bucket_Available`, against the documented purpose at `:10179` (`@param Bucket Bucket whose availability and region are requested`); and `src/flyology-object_storage-client-buckets.adb:4806-4807` (`elsif Value.Status in 301 | 307 | 400 | 501 then Invalid_Request`), which additionally labels the redirect a request rejection — discovery observation 2, folded in here.

**Repro:** `tests/repros/src/repro_client_buckets_2.adb`, exit status 1, three failed expectations.

**What is wrong:** `Decode_Head_Bucket_Complete_Response` parses `x-amz-bucket-region` out of the response, hands it to `Decode_Head_Bucket_Response`, and that function throws it away on every non-200 status, returning a synthesised `HTTP301` error whose message repeats the status and nothing else. The `Head_Bucket_Rejected` variant has no field that could hold a region, so the loss is structural rather than an oversight in one branch: no caller of the typed low level, the composable operation or the convenience can recover the one datum a HeadBucket redirect exists to convey, and the convenience's documented purpose is met only on 200. The redirect is additionally reported as `Invalid_Request`, which `client.ads:26` defines as a "Local or modeled service request rejection" — a redirect is not one. It is deterministic. The program works at two layers. It first calls the public `Low_Level.Decode_Head_Bucket_Response` with `Status => 301` and a `Head_Bucket_Result` whose `Bucket_Region` is `eu-west-1`, prints every readable field of the returned rejection (`HTTP301|HeadBucket returned HTTP status 301||AMZREQ1|AMZHOST1`) and finds no region; it then serves `HEAD /flyology-elsewhere` from a scripted loopback origin as `301 Moved Permanently` with `Content-Length: 0` and `x-amz-bucket-region: eu-west-1`, and drives both the convenience `Head` (`Head_Outcome`) and the parameter-record `Head` (`Head_Bucket_Result`), each losing the region and the composable leg reporting `Failure = INVALID_REQUEST`. The four control legs repeat every leg with `200 OK` and the same header, all reporting `eu-west-1`, which isolates the non-200 branch; the origin served all four exchanges.

**Notes:** The discard is in `Client.Low_Level`, so CLIENT-LOW is the sibling area for any fix, but the finding is counted once, here, because the public contract that promises a region is this file's convenience `Head` and CLIENT-LOW did not report it. Refutation attempts that failed: no other public path recovers the header (the composable `Head` exposes only `Response : Low_Level.Head_Bucket_Outcome`, the same two fields); `Get_Location` cannot substitute, because a 301 to GetBucketLocation takes the identical bodyless-rejection route through `Decode_Get_Bucket_Location_Response`'s `else` branch at `client-low_level.adb:4499-4505`; `docs/qualification/head-bucket-composable.md` excludes cross-region redirect *following*, not exposing the region a redirect carries, so it is not a documented limitation; and the header is not rejected as invalid on a 301, since the singleton and transfer-coding checks accept it and the repro shows the value present in `Headers` at the moment it is dropped. `review/baseline/service-2.json` models `BucketRegion` as the `x-amz-bucket-region` header of `HeadBucketOutput` and declares only `NoSuchBucket`, so the model neither requires nor forbids the header on a non-200. Existing tests pin the discard: `tests/src/flyology-object_storage-client-buckets-testing.adb:583-584` assert `(301, Invalid_Request)` and `(307, Invalid_Request)`, and the helper `Check_Head_Bucket_Response` at `:503-522` builds the outcome from the status alone, so no test ever supplies the header on a non-200. A fix needs a maintainer decision on the public surface: either add a region, or a full modelled-header component, to the rejected variants of `Low_Level.Head_Bucket_Outcome` and `Buckets.Head_Outcome`, or fold the value into `Error.Resource` or `Error.Message`. The first changes two public variant records; the second changes the meaning of a documented field. Both are `.ads` decisions. The measured MinIO behaviour also sharpens the uncounted observation that `Head` returns the signing region when the header is absent (`client-buckets.adb:2846-2849`, documented at `client-buckets.ads:10174-10176`): a bucket MinIO reports as `us-east-1` is reported by `Head` as `Region = "eu-west-1"` purely because the request was signed for `eu-west-1`, so `Head`'s `Region` is not a trustworthy region source on any server that omits the header, which is every server in the matrix.

### CLIENT-BUCKETS-3: `Client.Buckets.List_Page` with a nonempty `Prefix` is unusable against the pinned MinIO release

**Severity:** P2 (new; the discovery report recorded it as an uncounted observation with no severity, noting that a MinIO run "would settle interop"). The verifier ran it and MinIO fails the rule. Verdict: DOCUMENTED LIMITATION — the behaviour reproduces exactly as described and the strictness is written down at `docs/qualification/list-buckets.md:13-16` ("An explicitly supplied prefix must be echoed with the same presence and bytes, every returned bucket name must remain in that prefix") — but it is counted as a confirmed finding because the documented rule has an interop consequence: the public convenience parameter `Prefix : Optional bucket-name prefix filter` (`client-buckets.ads:961`) raises `Low_Level.Invalid_Response` against MinIO, a server the compatibility matrix lists for ListBuckets at `docs/compatibility/s3.md:12` ("native/lightweight clients and s5cmd across the six-server matrix"), and no maintained document says so. Not raised higher because the rule is documented and the strict direction is deliberate: the client refuses to present an unfiltered page as a filtered one.

**Location:** `src/flyology-object_storage-client-low_level.adb:4141-4148` — the echo rule, `(if Prepared.Requested_List_Buckets_Has_Prefix then not Page.Has_Prefix or else US.To_String (Page.Prefix) /= Requested_Prefix else Page.Has_Prefix and then US.Length (Page.Prefix) > 0)` followed by `raise Invalid_Response with "ListBuckets response does not match prepared request"` — and `:4150-4172`, the per-bucket prefix and region checks that follow; `src/flyology-object_storage-client-buckets.adb:191-197`, where the convenience overload sets `Has_Prefix => Prefix'Length > 0` at `:196`, so any nonempty prefix arms the rule; `:137-141`, where the convenience turns the resulting `Response_Invalid` into `raise Low_Level.Invalid_Response with "ListBuckets response is invalid or exceeds the XML limit"`, a message that names neither the prefix nor the server; the documented rule at `docs/qualification/list-buckets.md:13-16`; the matrix claim at `docs/compatibility/s3.md:12` and `:487-506`; and the real-server corpus call that would not notice, `tests/src/s3_implementation_corpus.adb:3182-3184`, which invokes `List_Page` with `Maximum => 1_000` and no prefix.

**Repro:** `tests/repros/src/repro_client_buckets_3.adb`, exit status 1, two failed expectations.

**What is wrong:** the ListBuckets decoder requires a server that was sent `prefix=` to echo `<Prefix>` byte-for-byte. MinIO does not: `GET /?max-buckets=10&prefix=flyology` answers `200 OK` with a `ListAllMyBucketsResult` carrying `Owner`, one correctly filtered `Bucket`, and no `<Prefix>` element. The convenience overload therefore raises `Low_Level.Invalid_Response` and the composable overload reports `Response_Invalid` with `Corrupt_Or_Invalid_Response`, for a response that is a valid, correctly filtered page. Anyone calling the public `Prefix` parameter against MinIO hits it — and, by the same rule, against any server that filters without echoing. It is deterministic. The program replays MinIO's exact document from a scripted loopback origin and drives both the convenience `List_Page` (which raises) and the parameter-record `List_Page` (`LIST_BUCKETS_EXCHANGE_FAILED`, `CORRUPT_OR_INVALID_RESPONSE`); the control legs replay the identical document with `<Prefix>flyology</Prefix>` added and pass with `PAGE_AVAILABLE, status 200` and one bucket in the page, which isolates the echo rule from any parse error. The failure also occurs live against the container with no scripted bytes (`repro_client_buckets_probe.adb`): `List_Page (Prefix => flyology)` raises `FLYOLOGY.OBJECT_STORAGE.CLIENT.LOW_LEVEL.INVALID_RESPONSE`, the composable form reports `HTTP_Result = RESPONSE_INVALID`, and the no-prefix control on the same server returns `PAGE_AVAILABLE, status 200`.

**Notes:** The pinned botocore documentation embedded in `review/baseline/service-2.json` supports the rule for AWS ("If `Prefix` was sent with the request, it is included in the response"), but `Prefix` is in no `required` list, so the shape itself does not mandate the echo; the rule is a repository policy, not a model obligation. It is recorded as a limitation rather than a bug because the strictness is deliberate and documented; what is missing is that neither the compatibility matrix nor the `.ads` parameter documentation warns that the parameter is AWS-only in practice, and the diagnostic the caller receives ("response is invalid or exceeds the XML limit") names neither the prefix nor the server. No maintained gate would notice, because the real-server corpus calls `List_Page` only without a prefix (`tests/src/s3_implementation_corpus.adb:3182-3184`). The fix is a maintainer decision between the two directions, and neither is an implementation detail: keep the strict echo rule and document the limitation — stating in `docs/compatibility/s3.md` and at `client-buckets.ads:961` that MinIO, and any server that filters without echoing, is unsupported for a prefixed `List_Page` — or relax the rule, accepting a missing `<Prefix>` while still enforcing that every returned name matches the requested prefix, which is a new public policy choice about what a filtered page is allowed to mean. Either way the diagnostic should name the real cause. It is counted as confirmed under the DOCUMENTED LIMITATION verdict because the choice is still open and a public parameter is unusable against a matrix-listed server until it is made.

- `Get_Location`'s compatibility normalisation (`""` to `us-east-1`, `EU` to `eu-west-1`, everything else verbatim) matches the documented behaviour at `client-buckets.ads:10214-10216`.
- The PutBucketTagging preparation computes Content-MD5 and the requested checksum header as documented (`client-low_level.adb:200-245`, `Checksums.Compute` at `:227`).
- Exchange hygiene: every scripted exchange in the three repro programs was served exactly once (eleven in `repro_client_buckets_1`, four in each of `repro_client_buckets_2` and `repro_client_buckets_3`), so no operation leaked or replayed a request.
- Nothing tracked was modified during verification; `git status --short` shows only `review/`, `tests/repros/` and `sqlite/tests/repros/`.

- HeadBucket statuses 301, 307, 400 and 501 are labelled `Invalid_Request` (`client-buckets.adb:4806-4807`), which `client.ads:26` defines as a "Local or modeled service request rejection"; a redirect is not one. Folded into CLIENT-BUCKETS-2 rather than counted separately, because it has no observable consequence beyond the discarded region.
- The generated result records carry a synthesised `Status => 500` sentinel in the exchange-failed case. `Put_Bucket_Replication_Result` and its siblings are flat records (`client-buckets.ads:6763-6772`), so on a transport failure `Normalize_Put_Bucket_Replication_Failure` (`client-buckets.adb:8765-8769`) stores `(Kind => Put_Bucket_Control_Rejected, Status => 500, Error => (others => <>))` into a field the spec documents as the complete modeled S3 response, and a caller who reads `Result.Response.Status` without first testing `Result.Kind` sees a fabricated 500 for an exchange in which no response was received. The variant-record results in the same file raise `Constraint_Error` instead, which is the safe behaviour; the inconsistency between the two families is the part worth raising with the maintainer. Not counted: it needs caller misuse, and the code comment at `:8765-8766` shows the choice was deliberate.
- `Pre_Admission_Rejected` becomes `Constraint_Error` with no `@exception` documentation: `client-buckets.adb:95` and `:124` (and the parallel mappers) `raise Constraint_Error with "HTTP request was rejected"`, while `grep -c '@exception' src/flyology-object_storage-client-buckets.ads` returns 0 for a spec whose convenience overloads can raise `Constraint_Error`, `Operation_Cancelled`, `Timeout_Error`, `Client_Closed`, `Connection_Error`, `Device_Error`, `Request_Body_Error` and `Invalid_Response`. A documentation gap rather than a behaviour defect; using a language check exception as a transport signal is a design choice a maintainer may want to revisit.
- Stale architecture prose: `docs/architecture/client-buckets.md:73-74` still says bucket-tagging "checksum selection currently fails locally until paired checksum generation is implemented", while `client-low_level.adb:224-245` computes and signs a digest for all ten modelled algorithms and `docs/qualification/bucket-tagging.md:51-52` says all ten are covered. Documentation only.
- CreateSession retains the temporary secret in `Response_Data`: the raw XML is accumulated at `client-buckets.adb:3505` and released with `Flyology.Bytes.Clear` on every exit path (`:3616`, `:3640`, `:3715-3776`). The pinned dependency documents `Clear` as "Release all retained elements and backing capacity" (`flyology_0.1.1/src/flyology-bytes.ads:91-93`), which is release, not zeroisation; the spec promises zeroisation only for the decoded identity (`client-buckets.ads:10915-10917`, `:10939-10941`), so no contract is violated. Noted for a security reviewer.
- `Head` returns the signing region when `x-amz-bucket-region` is absent (`client-buckets.adb:2846-2849`), documented at `client-buckets.ads:10174-10176`, so not counted; measured against the live MinIO it means a `us-east-1` bucket is reported as `eu-west-1` purely because of the signing region, so `Head`'s `Region` is not a trustworthy region source on any server that omits the header — which is every server in the matrix.
- CLIENT-LOW-4 (a bodyless or non-XML 4xx/5xx becoming `Invalid_Response`, `src/flyology-object_storage-client-low_level.adb:1956-1958`) is reachable through every convenience overload in this file, because the `Raise_*_Exchange_Failure` mappers re-raise `Invalid_Response` for `Response_Invalid | Response_Body_Too_Large | Response_Sink_Failed` (`client-buckets.adb:108-112`, `:137-141`). Not duplicated here; it belongs to CLIENT-LOW, and CLIENT-BUCKETS-1 is the structured-error half of the same classification gap.

None of these live in `Client.Buckets`; they belong to CLIENT-OBJECTS and the S3 domain areas. Also not read line by line: the 23 generated read and mutation instances beyond the sampled ones, whose shape was verified structurally, and the `Bounded_REST_XML_Reads`, `Paginated_REST_XML_Reads` and `REST_XML_Mutations` generic bodies themselves.
