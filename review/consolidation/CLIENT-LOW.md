### CLIENT-LOW-1: `Execute_Head_Object` raises `Invalid_Response` when a 200 omits `x-amz-version-id` after a `versionId=` request

**Severity:** P0 (the discovery report said P1). The verifier raised it on the rubric reading it states in full for all three version-echo findings: the P0 interop clause is about interoperability failure rather than about which side does the refusing, and here the library cannot complete a version-selected HEAD against any conforming S3 server on the default bucket state, the pinned model marks the demanded header optional, and the failure escapes as an exception rather than as a variant of `Head_Object_Outcome`, so a caller cannot even degrade gracefully. The strict alternative the verifier recorded and rejected: read literally, "an interop-breaking protocol violation that a stock client or server rejects" describes the library emitting bytes a stock peer refuses, and here the direction is reversed, so the finding would fall back to P1 ("unexpected exception on valid input via a reachable path").

**Location:** `src/flyology-object_storage-client-low_level.adb:5641-5658` (`Head_Object_Response_Bound`), returning `(Requested_Version'Length = 0 or else US.To_String (Value.Version_ID) = Requested_Version) and then (Returned_Payer /= "requester" or else Requested_Payer = "requester")` — plain equality with no absence tolerance; the decoder that leaves the value empty when the header is absent at `:5813` (`Version_ID => H ("x-amz-version-id")`, where `H` is `Flyology.HTTP.Client.Header`); the raise site at `:5877-5887` in `Execute_Head_Object` (`Invalid_Response with "HeadObject response does not match prepared request"`); `Prepare_Head_Object` at `:5153`, which copies `Parameters.Version_ID` into `Result.Requested_Head_Object_Version_ID` unconditionally and never rejects `"null"`; the private-part comment that states the intent at `src/flyology-object_storage-client-low_level.ads:10533-10535`; the contract `Invalid_Response` claims to enforce at `.ads:300-301`; the in-repo server's fallback at `src/flyology-object_storage-server-s3_applications.adb:4188-4194`; the conformance corpus case at `tests/src/s3_implementation_corpus.adb:1144-1172`.

**Repro:** `tests/repros/src/repro_client_low_1.adb` with helper `repro_client_objects_fake.ads/.adb`, exit status 1, one failed expectation.

**What is wrong:** `Head_Object_Response_Bound` compares the decoded `x-amz-version-id` against the retained request selector with plain string equality, and an absent response header decodes to the empty string. Any request that carried a `versionId` — including the AWS-documented `null` selector, which is how an object in a bucket where versioning was never enabled is addressed — therefore makes the predicate False and turns an otherwise valid 200 into `Invalid_Response`. The pinned model settles the response side: `HeadObjectOutput.required` is `[]` and `VersionId` is `{"location": "header", "locationName": "x-amz-version-id"}` with no presence requirement, so an omitting 200 does not violate the modeled contract `.ads:300-301` says the exception guards. Because the failure is an exception rather than an outcome variant, the caller never sees the metadata and cannot classify the result as a per-server deviation — which is exactly why no `*_ORACLE_MODE` in the implementation corpus can express it. Anyone doing a version-selected HEAD against MinIO, RustFS, SeaweedFS or AWS on a never-versioned bucket hits it, deterministically. The program scripts two exchanges on a loopback origin: the first replies to `HEAD /never-versioned/native-object?versionId=null` with the verbatim RustFS 1.0.0-rc.3 header set from `review/baseline-rustfs.md` section 1 probe (b) — `200 OK`, `accept-ranges`, `content-length: 64`, `content-type`, quoted `etag`, `last-modified`, the two request-id headers, `date`, and no `x-amz-version-id` — and the second is identical except that `x-amz-version-id: null` is added. It drives `Prepare_Head_Object` with exactly the corpus parameters (`Version_ID = "null"`, `Request_Payer = "requester"`, `Checksum_Mode = True`) and `Execute_Head_Object`. The first leg raises; all three control assertions pass, which isolates the version clause.

**Notes:** This predicate is what fails the repository's own conformance corpus against RustFS, MinIO and SeaweedFS: `review/baseline-rustfs.md` section 4 records 7/7 deterministic RustFS reproductions and section 5 records the byte-identical failure messages in `review/baseline/minio.log:96` and `review/baseline/seaweedfs.log:99`, and the corpus case is `tests/src/s3_implementation_corpus.adb:1144-1172`, which sets `Parameters.Version_ID := "null"` and asserts `Object_Found`. Its high-level twin is CLIENT-OBJECTS-1, the identical predicate shape at `src/flyology-object_storage-client-objects.adb:121-155`, and any fix must cover both layers. SERVER-3 is why neither shows up in the in-tree lanes: the in-repo server always supplies the header the client demands — HeadObject writes `x-amz-version-id: null` unconditionally at `s3_applications.adb:16619-16622` and GetObject writes it at `:4189-4194` only when the request named a version — so the memory-server CI gate is green while all three third-party servers are red, and the three findings must be sequenced together with the client predicates fixed before the server spelling. One attribution difference to reconcile when filing: this area's verification report anchors the `null` fallback at `s3_applications.adb:4188-4194` and describes it as the GET/HEAD route, which is the reverse of the operations SERVER-3 names; the masking effect is the same either way. This is not a documented limitation — `docs/compatibility/s3.md:449` documents the opposite direction ("The server omits the header for unversioned publication"), so the repository already treats omission as the correct shape, and the only statement of the client demand is the private-part comment at `low_level.ads:10533-10535`, which is the design decision under review rather than a maintained limitation. No existing test pins the defective behaviour at this layer: the socket-corpus cases added by commit 2703ed6 (`head-cancel-version`, `wrong-head-version`) always emit the header and none omits it, so the correction contradicts no assertion here. Two maintainer decisions a fix needs: whether the contract becomes "the response must not contradict the selector" — accept an absent header, reject a present-and-different one — or whether the mismatch becomes a typed outcome instead of an exception, noting that RustFS's versioning-suspended sentinel `00000000-0000-0000-0000-000000000000` (`review/baseline-rustfs.md` section 1(c)) is present-and-different, so a strict-echo contract is not viable across real servers even after the relaxation; and whether the server's `null` fallback should remain once the client stops requiring it.

### CLIENT-LOW-2: `Execute_Get_Object_Attributes` raises `Invalid_Response` when a 200 omits `x-amz-version-id` after a `versionId=` request

**Severity:** P0 (the discovery report said P1). The verifier raised it on the same rubric reading as CLIENT-LOW-1 and judged it sharper on one count: no server can satisfy the demand, because the repository's own in-process S3 application omits the header on this route, so the operation cannot complete against the library's own server either. The same strict alternative applies and was again recorded as immaterial: read literally, the P0 interop clause describes the library emitting bytes a stock peer refuses rather than refusing bytes a stock peer legitimately emits, which would put the finding at P1.

**Location:** `src/flyology-object_storage-client-low_level.adb:5383-5396` (`Decode_Get_Object_Attributes_Complete_Response`), which raises `Invalid_Response with "GetObjectAttributes response does not match request"` when the outcome is `Object_Attributes_Found` and `US.Length (Prepared.Requested_Get_Attributes_Version_ID) > 0 and then Version_ID /= US.To_String (Prepared.Requested_Get_Attributes_Version_ID)`; the binding at `:5371-5372` (`Version_ID : constant String := Singleton_Header ("x-amz-version-id")`) and `Singleton_Header`'s `""` for `Count = 0` at `:5348-5350`; the executor at `:5488-5516`; the in-repo GetObjectAttributes handler at `src/flyology-object_storage-server-s3_applications.adb:16347-16352`, which emits the header only when `US.Length (Snapshot.Info.Version) > 0` and has no `null` fallback; the pinned model's `GetObjectAttributesOutput` (`required = []`, `VersionId` an optional `x-amz-version-id` header); the unexercised coverage at `tests/src/s3_implementation_corpus.adb:1675-1861`.

**Repro:** `tests/repros/src/repro_client_low_2.adb`, exit status 1, one failed expectation.

**What is wrong:** The same mechanism as CLIENT-LOW-1 in a different decoder: the optional `x-amz-version-id` response header is required to equal the requested selector, and an absent header compares as the empty string, so `"" /= "null"` trips the check. A `GetObjectAttributes` request that selects `versionId=null` against an object in a never-versioned bucket turns a valid 200 carrying the requested ETag and ObjectSize into `Invalid_Response`. It is deterministic and reachable both from `Execute_Get_Object_Attributes` and from the composable `Client.Objects` GetObjectAttributes operation, which calls the same decoder. What makes it sharper than CLIENT-LOW-1 is that the demand is unsatisfiable even against the repository's own server: the attributes handler at `s3_applications.adb:16347-16352` has no `null` fallback, unlike the GET/HEAD route. The program proves that on the wire without Docker: it PUTs one object into a never-versioned bucket through `Repro_S3_Server.Run`, shows with a raw signed `GET /bucket/key?attributes&versionId=null` that the server answers 200 with zero `x-amz-version-id` headers, then starts the same application on the loopback listener and drives `Prepare_Get_Object_Attributes` (`Version_ID = "null"`, `Attributes.Entity_Tag` and `Attributes.Object_Size` selected) plus `Execute_Get_Object_Attributes`. The control leg, the same request with no version selector, returns `Object_Attributes_Found` with the ETag and `ObjectSize = 16`.

**Notes:** Unlike CLIENT-LOW-1 and CLIENT-LOW-3, this one is not masked by the in-repo server; it reproduces against it, because the attributes handler at `s3_applications.adb:16347-16352` has no fallback where SERVER-3's HeadObject (`:16619-16622`) and GetObject (`:4189-4194`) sites do. Nothing is currently red only because no maintained test reaches the branch: `tests/src/s3_implementation_corpus.adb:1675-1861` (`Require_Get_Object_Attributes`) never sets `Parameters.Version_ID`, and the socket-corpus attributes cases all echo a version. The defect is therefore unexercised rather than pinned, so no assertion has to be inverted with the fix. `docs/qualification/get-object-attributes.md:41-42` carries the same strict-echo requirement that CLIENT-LOW-1 shows is not satisfiable against real servers, and belongs with this finding rather than with CLIENT-OBJECTS, since the code it describes lives here. A fix needs the same maintainer decision as CLIENT-LOW-1 — tolerate an absent header versus expose a typed mismatch outcome — and the verifier's recommendation is that it be made consistently across all four sites (`low_level.adb:5641-5658`, `:5383-5396`, `:12463-12489` and `client-objects.adb:121-155` with `:7177-7211`).

### CLIENT-LOW-3: `Execute_{Put,Get,Delete}_Object_Tagging` require exactly one `x-amz-version-id` on every success, even with no version requested

**Severity:** P0 (the discovery report said P1). The verifier raised it on the same rubric reading and called it the broadest of the three, because the demand is unconditional on the request: no caller input avoids it, so the plain `Put_Tags` / `Get_Tags` / `Delete_Tags` path is affected on every server whose bucket never had versioning enabled, and for Put and Delete the mutation has already been applied when the exception is raised. The same strict alternative was recorded and rejected: under a literal reading of the P0 clause, which is about the library emitting bytes a stock peer refuses, all three version-echo findings fall back to P1.

**Location:** `src/flyology-object_storage-client-low_level.adb:12463-12489` (`Response_Version_ID`, nested in `Execute_Object_Tagging`), whose gate is `if Count > 1 or else (Success and then Count /= 1) then raise Invalid_Response with "invalid object tagging version header multiplicity";`; the supply of `Success` as `Status = Model.Response_Code (Expected)` at `:12527-12529`, which the pinned model makes 200 for `PutObjectTagging` and `GetObjectTagging` and 204 for `DeleteObjectTagging` (`service-2.json` gives `DeleteObjectTagging` an explicit `"responseCode": 204`; the other two default to 200); the separate and correct present-and-different check at `:12531-12538`, which is the one that binds an explicit selector; the shared executor's operation guard at `:12452`; the spec comment the code contradicts at `src/flyology-object_storage-client-low_level.ads:10538-10543` ("Empty means the request selected the current version, so any returned version remains an observation rather than proof"); the model's `PutObjectTaggingOutput.required = []`, `DeleteObjectTaggingOutput.required = []` and `GetObjectTaggingOutput.required = ["TagSet"]`, with `VersionId` an optional header in all three; the in-repo server's `Set_Version_Header` at `src/flyology-object_storage-server-s3_applications.adb:15846-15854`; the existing assertions of the wrong behaviour at `tests/src/s3_http_socket_corpus.adb:15091-15253`.

**Repro:** `tests/repros/src/repro_client_low_3.adb` with helper `repro_client_objects_fake.ads/.adb`, exit status 1, three failed expectations.

**What is wrong:** `Response_Version_ID` conflates two different rules. Header multiplicity (`Count > 1`) is a genuine protocol violation; header presence on a success is not, because the model marks `VersionId` optional in all three tagging output shapes. Since `Success` is only "the status matched the modeled response code", every 200 PutObjectTagging, every 200 GetObjectTagging and every 204 DeleteObjectTagging against a bucket that never had versioning enabled raises `Invalid_Response "invalid object tagging version header multiplicity"` — a misleading message, since the count is zero, not two. It needs no request parameter at all, which is what makes it the broadest of the three: the plain `Put_Tags` / `Get_Tags` / `Delete_Tags` call path is affected. For PutObjectTagging and DeleteObjectTagging the mutation has already been applied when the exception is raised, so the caller cannot distinguish an applied mutation from a corrupt response. `review/baseline-rustfs.md` section 8 records RustFS answering `PUT /bucket/native-object?tagging` with `200 OK`, `content-length: 0` and the two request-id headers only. The program scripts six exchanges on a loopback origin: `PUT`, `GET` (with a one-tag `<Tagging>` document) and `DELETE` on `/never-versioned/native-object?tagging` carrying no `x-amz-version-id`, then the same three with the header present, none of the six prepared requests carrying a `versionId` selector. All three no-header legs raise; all six control assertions pass, including the decoded tag set reaching the caller.

**Notes:** Its high-level twin is CLIENT-OBJECTS-2, `Tagging_Version_ID` at `src/flyology-object_storage-client-objects.adb:7177-7211`, which is the site that actually failed against RustFS in `review/baseline-rustfs.md` section 8 because the corpus calls `Client_Objects.Put_Tags`; the two are one defect at two layers and share a fix direction. As with CLIENT-LOW-1, the in-repo server is what keeps CI green — `Set_Version_Header` at `s3_applications.adb:15846-15854` defaults to the literal `"null"` when the identity has no version — and the server-side half of that masking is SERVER-3. **An existing test asserts the wrong behaviour and must be inverted with the fix:** `tests/src/s3_http_socket_corpus.adb:15091-15253` (`Require_Invalid_Version` with `Invalid_Version_Kind = Missing`, fixtures `tag-put-missing` / `tag-get-missing` / `tag-delete-missing` served at `:4332-4334`, `:4361-4363` and `:4386-4389`) requires `Invalid_Response` synchronously or `Corrupt_Or_Invalid_Response` with `Object_Tag_Mutation_Outcome_Unknown` in the composable path, and raises `"… object tagging accepted missing version response"` otherwise; the `Missing` case leaves `Selected` empty, so it pins exactly the no-selector case. It directly contradicts `tests/src/s3_implementation_corpus.adb:1617-1673` (`Require_Object_Tagging`), which expects success from real servers. It is not backed by any document: `docs/compatibility/s3.md:364-372` describes the tagging clients as validating "bounded responses and version IDs" without stating that a version header is mandatory, and the crate's own spec comment at `low_level.ads:10538-10543` says the opposite of the code. One line-span difference to reconcile when filing: this area's verification report gives `Response_Version_ID` as `:12463-12489`, while the CLIENT-OBJECTS consolidation cites `:12465-12475` for the same predicate from its own discovery report; the code is the same gate either way. The maintainer decision is whether `Version_ID` stays a plain `Unbounded_String` that is empty when the server omitted the header — the shape `Head_Object_Result` and `Get_Object_Attributes_Result` already use — or becomes an explicit optional, which is a public API change.

### CLIENT-LOW-4: a bodyless or non-XML 4xx/5xx becomes `Invalid_Response` instead of the typed rejection carrying the wire status

**Severity:** P2 (unchanged from the discovery report, whose confidence the verifier raised from Medium to High now that it has a run). Wrong diagnostics on a path a conforming S3 origin does not produce: the trigger is a non-S3 intermediary rather than ordinary valid input, and the client fails closed rather than accepting something wrong.

**Location:** `src/flyology-object_storage-s3-errors.adb:109-127` (`Parse`), where an empty or non-`<Error>` document raises `Malformed_Error` from either the `Seen_Code`/`Seen_Message` check or `when XML.XML_Error =>`; the roughly twenty decoders that convert it to `Invalid_Response`, among them `src/flyology-object_storage-client-low_level.adb:1956-1958` (ListObjectsV2), `:11297-11299` (DeleteObject) and `:7731-7733` (PutObject), with the same pattern at `:1694`, `:2228`, `:3340`, `:3884`, `:4369`, `:5331`, `:8240`, `:10849`, `:12412`, `:12732`, `:12925`, `:13193`, `:13427`, `:14044`, `:14426`, `:14779` and every bucket-control GET; the contrasting deliberate treatment for GetObject at `:7137-7166`, whose comment at `:7159-7163` reads "S3 peers and intermediaries may return bodyless or non-XML HTTP errors. Preserve the typed rejection and wire status instead of turning a valid rejection into a client protocol failure."; `Head_Error` at `:4856-4872`, which synthesises `Code => "HTTP" & <status>` and is used unconditionally by HEAD at `:5670-5674`; the composable mapping at `src/flyology-object_storage-client-bounded_rest_xml_reads.adb:105-111`; the distinct `Unavailable_Or_Retryable` value in `src/flyology-object_storage-client.ads:37-51`.

**Repro:** `tests/repros/src/repro_client_low_4.adb` with helper `repro_client_objects_fake.ads/.adb`, exit status 1, two failed expectations.

**What is wrong:** `S3.Errors.Malformed_Error` is raised for any non-2xx whose body is absent, whitespace, HTML or otherwise not an S3 `<Error>` document, and about twenty decoders convert it to `Invalid_Response`, discarding the HTTP status the caller needs. The failure mode appears when a reverse proxy, load balancer or CDN answers on the origin's behalf with a 503 and an HTML page, or when a peer answers 403 with no body. A synchronous caller loses the status entirely; a composable caller receives `Corrupt_Or_Invalid_Response` where `Unavailable_Or_Retryable` is the correct classification, so a transient outage is treated as a protocol violation and is not retried. The repository has already made the opposite decision twice — unconditionally for HEAD through `Head_Error`, and with an explicit explanatory comment for GetObject — so this is an internal inconsistency rather than a missing design decision, and every affected outcome type already carries a `Rejected` variant with the wire `Status`, so no new public type is needed. The program scripts four exchanges: a signed `ListObjectsV2` answered `503 Service Unavailable` with `content-type: text/html` and an HTML body, and a signed `DeleteObject` answered `403 Forbidden` with `content-length: 0`, both asserted to be typed rejections with `Error.Code = "HTTP503"` / `"HTTP403"` and both failing; then two controls that pass — a bodyless 503 on `HeadObject`, which already yields `Head_Object_Rejected` with `Error.Code = HTTP503`, and a 503 carrying a well-formed `<Error>` document on `ListObjectsV2`, which yields `Rejected` with status 503 and `Error.Code = SlowDown`.

**Notes:** No existing test asserts either behaviour — every 4xx/5xx fixture in `tests/src/s3_http_socket_corpus.adb` carries a well-formed `<Error>` body, and the only bodyless or non-XML error tests are the GetObject ones behind the tolerant path at `:7137-7166` — so the correction contradicts nothing. It stays P2 rather than P1 because a conforming S3 origin always emits an `<Error>` document: the model describes per-operation `errors` shapes but says nothing about intermediaries. The verifier's refutation attempts all failed: there is no wrapper that catches `Malformed_Error` earlier, since the composable generics catch only `Invalid_Response`; and the strictness is not uniform, so it is not deliberate. The fix is mechanical — mirror the GetObject `when S3.Errors.Malformed_Error` handler at each site — and the one maintainer decision is whether the synthesised `Code = "HTTP<status>"` convention that HEAD and GetObject already use should become the documented contract for the rest.

### CLIENT-LOW-5: `Prepare_Create_Session` rejects the explicit `Bucket_Key_Enabled = False` its specification says is preserved, and would serialise any set value as `true`

**Severity:** P2 (unchanged from the discovery report). Contract drift plus a latent value inversion rather than a live wire defect: no wrong bytes can reach the wire today, because the policy check fires before the serialiser.

**Location:** `src/flyology-object_storage-client-low_level.ads:6401-6416`, the published contract ("Empty strings preserve omission; Bucket_Key_Enabled preserves absent versus explicit false", with `@field Bucket_Key_Enabled Presence-preserving bucket-key request flag`); `src/flyology-object_storage-client-low_level.adb:2429-2432` (`Validate_Create_Session_Policy`), whose raising disjunction includes `or else (Bucket_Key_Enabled.Is_Set and then not Bucket_Key_Enabled.Value)`; the call from `Prepare_Create_Session` at `:2472-2482`, which remaps the raise to `Invalid_Request with "invalid CreateSession parameters"`; the serialiser at `:2494-2502`, which emits `Value => US.To_Unbounded_String ("true")` and never reads the caller's boolean; the pinned model's `CreateSessionRequest` (`required = ["Bucket"]`, `BucketKeyEnabled` a boolean bound to the header `x-amz-server-side-encryption-bucket-key-enabled`).

**Repro:** `tests/repros/src/repro_client_low_5.adb`, a pure preparation test with no server, exit status 1, two failed expectations.

**What is wrong:** The specification says the flag preserves absent versus explicit `false`; `Prepare_Create_Session` raises `Invalid_Request` on exactly the explicit `false` the comment promises, with a message that does not say which member was wrong, and the serialiser that would have emitted it hard-codes the string `"true"`, so the caller's boolean is never read. A caller who reads the specification and sets `(Is_Set => True, Value => False)` gets an exception; had the policy check not fired, the request would have carried `true`, silently inverting the value. The program prepares a request against an HTTPS virtual-hosted S3 Express origin with `SessionMode = ReadWrite`, `ServerSideEncryption = aws:kms`, a KMS key ARN and `Bucket_Key_Enabled = (Is_Set => True, Value => False)`, and asserts that preparation succeeds and that the canonical request carries `x-amz-server-side-encryption-bucket-key-enabled:false`; both fail. The two control legs pass and show the code path is otherwise live: with the flag absent the header is absent from the signed headers, and with it explicitly true the canonical request carries `…bucket-key-enabled:true`.

### CLIENT-LOW-6: `Execute_Create_Multipart_Upload` sends a mismatched prepared request to the origin before rejecting it

**Severity:** P2 (new; the verifier raised it from the discovery report's uncounted observation that this executor lacks the up-front `Prepared.Operation` check every other one has, which the discovery did not test). It needs an erroneous caller input, which is the P2 "needs unusual input" clause, but the consequence is a real unintended request executed against the origin rather than a wrong diagnostic, so the verifier placed it at the top of P2.

**Location:** `src/flyology-object_storage-client-low_level.adb:3505-3526` (`Execute_Create_Multipart_Upload`), where `Response` and `Payload` are elaborated in the declarative part so `Flyology.HTTP.Client.Execute` runs before the body, and no `Prepared.Operation` test exists anywhere in the subprogram; the check that does exist, after the exchange, at `:3345-3355` (`Decode_Create_Multipart_Complete_Response`); the guarded siblings for contrast, `Execute_List_Parts` `:13268-13279`, `Execute_Head_Object` `:5864-5867` and `Execute_Delete_Objects` `:12820-12823`, and the four thin wrappers delegating to guarded shared executors at `:8245`, `:9798`, `:10892` and `:12452`; the specification block at `src/flyology-object_storage-client-low_level.ads:6777-6790`, which carries no `@exception Invalid_Request`, against `:6763-6769`, which documents exactly that exception for the decoder.

**Repro:** `tests/repros/src/repro_client_low_6.adb` with helper `repro_client_objects_fake.ads/.adb`, exit status 1, one failed expectation.

**What is wrong:** `Prepared_Request` is one opaque private type used for all 116 modeled operations, so "did the caller hand me the right kind of prepared request?" is checked as the first statement of every executor in the package. The verifier enumerated all 110 `Execute_*` bodies: each either performs that test first or is a thin wrapper delegating to a guarded shared executor, and `Execute_Create_Multipart_Upload` is the single standalone body with no guard. Because its `Response` and `Payload` objects are elaborated in the declarative part, the whole HTTP exchange happens before the decoder's `Invalid_Request` is raised, so the fail-safe invariant the rest of the API establishes — a mismatched prepared request never touches the network — is broken at exactly one site. The mismatched request is not harmless: `Prepared.Message` is a fully signed, complete request for whatever operation it was prepared for, so the worst case is that a mutation the caller did not intend to send at that moment (a `DeleteObject`, an `AbortMultipartUpload`, a `PutObject` with a retained payload) is really executed against the origin, with its effect reported only as "prepared request operation mismatch". It is deterministic and needs no server cooperation. The program prepares a genuine `DeleteObject` for `/example-bucket/irreplaceable-object`, hands it to `Execute_Create_Multipart_Upload`, and asserts both that `Invalid_Request` is raised and that the origin exchange counter did not move: the exception assertion passes, the counter assertion fails, and the origin log shows it received `DELETE /example-bucket/irreplaceable-object HTTP/1.1`. Two controls pass and prove the counter works: the same mismatched request through the guarded `Execute_List_Parts` raises and sends nothing, and a genuine `Execute_Delete_Object` succeeds with exactly one request.

**Notes:** No existing test covers a mismatched prepared request for this operation, so nothing has to change with the fix. The fix needs no maintainer decision and no new public entity: one guard copied from `Execute_List_Parts` (`:13276-13279`) placed before the declarative part, plus an `@exception Invalid_Request` line in the `.ads` block at `:6777-6784` to match every sibling. The verifier's refutation attempts all failed — a caller never legitimately reuses a prepared request across executors, which is precisely why every other executor checks, and the decoder catches the mismatch only after the side effect has happened.

### CLIENT-LOW-7: `Valid_Model_Scalar` accepts Ada literal integer forms and forwards them verbatim into the signed request

**Severity:** P2 (new; the verifier raised it from the discovery report's uncounted observation that integer members are validated with `Long_Long_Integer'Value`, which the discovery did not carry to the wire). It needs unusual caller text through the public `Prepare_Model_Request`, which is the P2 clause, but the request is signed and sent with no client-side complaint, so the validator silently fails at the one job it exists for.

**Location:** `src/flyology-object_storage-client-low_level.adb:949-965`, where `Model.Integer_Shape | Model.Long_Shape` members are validated by computing `Number := Long_Long_Integer'Value (Value);` (the `'Value` call is at `:955`) and range-checking `Number`, while the raw `Value` text — not `Number` — is what the projector percent-encodes into the request target; the public projector documented at `src/flyology-object_storage-client-low_level.ads:193-220` and declared in the visible part at `:210`; the pinned model's `MaxKeys` (`{"type": "integer"}` with no `min`/`max`, so bounds reject nothing here and the defect is purely lexical).

**Repro:** `tests/repros/src/repro_client_low_7.adb`, exit status 1, four failed expectations.

**What is wrong:** `Valid_Model_Scalar` exists so that a modeled member value is checked before it is signed and sent, but for integer and long shapes it borrows Ada's own numeric-literal grammar through `Long_Long_Integer'Value` instead of the S3 wire grammar, and then hands the projector the caller's original text rather than the parsed number. Ada's `'Value` accepts underscores, based literals, exponents and a leading `+`, so a caller of the public `Prepare_Model_Request` who supplies an Ada-shaped literal gets a fully signed request carrying `max-keys=1_000`, `max-keys=16%233E8%23`, `max-keys=1E3` or `max-keys=%2B1000` — bytes no S3 server accepts — with no client-side error at all. The failure surfaces only as a remote `400 InvalidArgument` whose cause is not visible locally, and because the malformed text is inside the signed canonical request it cannot be repaired by an intermediary. It is deterministic. The program calls `Prepare_Model_Request (Model.List_Objects_V2_Operation, …)` with the `MaxKeys` member set to `"1_000"`, `"16#3E8#"`, `"1E3"` and `"+1000"` and asserts each is rejected at preparation; all four are accepted and the report prints the resulting target for each. Two controls pass and show the validator is reached and does reject genuine garbage: `"500"` prepares and reaches the target verbatim, and `"not-a-number"` is rejected as `invalid modeled request scalar`.

**Notes:** The typed preparers are unaffected because they format with `'Image`, which is why this is P2 rather than P1 — but that confines the defect to the generic public entry point rather than making it unreachable, and `Prepare_Model_Request` is declared in the visible part at `low_level.ads:210`, not an internal helper. Nothing downstream catches it: the repro shows the value reaching the signed request target, and the first thing that notices is the S3 server. No existing test exercises a non-decimal integer member through `Prepare_Model_Request`. The fix is local and needs no maintainer policy decision: reject any character outside an optional `-` followed by decimal digits before calling `'Value`, or serialise the trimmed `Number'Image` instead of the raw text so that the validated value is the value sent. The MODEL area independently confirmed that no model-side defect contributes — the descriptor supplies `Minimum` and `Maximum` correctly, compared as 64-bit values for both `integer` and `long` kinds — and routed the observation here as O-7.
