## SIGV4: signing, verification, admission and credentials (SIGV4-1, SIGV4-2)

The area covers `src/flyology-object_storage-s3-sigv4.ad?`, `-s3-sigv4_encoding.ad?`, `-s3-sigv4_verification.ad?`, `src/flyology-object_storage-server-authentication.ad?` and `-server-static_credentials.ad?`, with the admission call site, body-hash enforcement and exception handlers in `src/flyology-object_storage-server-s3_applications.adb` and the SigV4 sections of `docs/compatibility/s3.md`.

### SIGV4-1: A far-future `x-amz-date` escapes `Verify_Request` as `Ada.Calendar.Time_Error` and is answered 500 InternalError instead of 403 RequestTimeTooSkewed

**Severity:** P2 (the discovery report also said P2).

**Location:** `src/flyology-object_storage-server-authentication.adb:157-165` (the skew test in a `declare` block outside `Timestamp_Time`), with `:57-69` (`Timestamp_Time` and its narrow handler), `:224-227` (`Verify_Request`'s `when Constraint_Error` handler) and `:209` (the credential provider is invoked only afterwards); no upper year bound at `src/flyology-object_storage-s3-sigv4_encoding.adb:190-195`; call site at `src/flyology-object_storage-server-s3_applications.adb:6697`, catch-all at `:18056-18065`, and the mapping that should have run at `:1893-1897`; public contract at `src/flyology-object_storage-server-authentication.ads:41-48` and `:56-60`.

**Repro:** `tests/repros/src/repro_sigv4_1.adb`, exit status 1, three failed expectations.

**What is wrong:** `Valid_Timestamp` puts no upper bound on the year, so an `x-amz-date` anywhere in `Ada.Calendar.Year_Number` survives admission and is converted to a `Time`. The skew test then evaluates `Request_Time - Now` outside `Timestamp_Time`'s guard. With 64-bit `Duration` the difference overflows for any request time more than 292.277 years from the trusted clock, and GNAT's `"-" (Time, Time)` raises `Ada.Calendar.Time_Error`, which `Verify_Request`'s `when Constraint_Error` handler does not catch. The exception leaves the public `Verify_Request`, reaches `Handle`'s catch-all and becomes 500 InternalError for any routed request, sent to an unauthenticated peer, instead of the 403 RequestTimeTooSkewed the mapping exists to produce. It is fully deterministic and needs no valid credentials, because the check runs before the credential provider is invoked. The toolchain facts were re-derived from the toolchain the harness resolves: `Year_Number` is 1901 .. 2399 in `a-calend.ads:48`, `Duration_32_Bits` is False in `system.ads:154`, and `a-calend.adb`'s `"-"` converts any internal `Constraint_Error` into `Time_Error`, so `Constraint_Error` is never what escapes.

**Notes:** The verifier considered P1, on the grounds that the GNATdoc says the clock skew "is checked" and `Outcome_Status` has a dedicated `Request_Time_Too_Skewed` value, so an exception leaving the public function violates the documented contract and a third-party server built directly on `Authentication` would see it propagate into its own connection handler; P2 was kept because the in-tree caller contains it, the connection and process survive, and no valid request reaches the path. Years 0001 to 1900 are the same family already handled correctly: they fail `Year_Number` inside `Timestamp_Time` and yield 400 AuthorizationHeaderMalformed. No existing test asserts either case; `rg RequestTimeTooSkewed tests/ server/tests/` finds no assertion and no test sends an `x-amz-date` outside 2013. A fix needs one maintainer decision: give `Valid_Timestamp` an explicit accepted-year range, which introduces a new public policy bound in a SPARK unit and so falls under the repository's rule on specification values, or widen `Verify_Request`'s handler to `Constraint_Error | Ada.Calendar.Time_Error` and return `Request_Time_Too_Skewed`, which introduces no new interface value. The claim that aws-cli and boto3 retry 500 with backoff is the verifier's own knowledge and was not measured.

### SIGV4-2: `Static_Credentials.Create` accepts principals of 257 to 1,024 bytes that admission then rejects, so every correctly signed request is answered 403 SignatureDoesNotMatch

**Severity:** P1 (the discovery report said P2; the verifier raised it because the failing path takes valid input, an ordinary correctly signed request, and returns a wrong result, and because `Create`'s own GNATdoc promises to reject a field that is too long).

**Location:** `src/flyology-object_storage-server-static_credentials.adb:31-48` (`Create` checks only empty, `> Maximum_Principal_Bytes` and control bytes) and `:80-88` (`Authenticate` returns the long principal once `Allowed`); constants at `src/flyology-object_storage-server-static_credentials.ads:34-36` and the unmet `@exception` promise at `:26`; the 256-byte rejection at `src/flyology-object_storage-server-authentication.adb:18-31` and the collapse into one status at `:213-217`; the rendering at `src/flyology-object_storage-server-s3_applications.adb:1907-1910`; the layer contract that motivates 256 at `flyology_http` 0.1.3 `flyology-http-server-applications.ads:279-283`; documentation that publishes neither bound at `src/flyology-object_storage-server-authentication.ads:17-20`.

**Repro:** `tests/repros/src/repro_sigv4_2.adb` with helper `tests/repros/src/repro_sigv4_support.ads/.adb`, exit status 1, three failed expectations.

**What is wrong:** `Static_Credentials` bounds the principal at `Maximum_Principal_Bytes` of 1,024 and `Create` enforces only that, while `Authentication.Valid_Principal` rejects anything over 256 bytes because that is `flyology_http`'s `Set_Principal` contract. An operator who configures a static identity with a 257 to 1,024-byte principal, such as a tenant URN, a DN or an e-mail-style identifier, gets a provider `Create` accepted and a server on which every correctly signed request fails. The failure is deterministic and total: `Authenticate` verifies the signature successfully and returns the long principal, then admission collapses the length rejection into the same `Credential_Rejected` status a genuinely bad signature produces, and the S3 layer renders it as 403 SignatureDoesNotMatch with "The request signature does not match". Nothing in the response and nothing in either specification points at the principal, so the operator debugs a signature problem that does not exist.

**Notes:** There is a second route to the same defect, established by reading rather than by the repro: leaving `Principal` empty makes `Access_Key` the principal, and `Valid_Access_Key` accepts up to 1,024 alphanumerics, so an access key of 257 to 477 characters fails identically, 477 being the ceiling `Parse_Credential`'s 512-byte credential-text bound at `src/flyology-object_storage-s3-sigv4_verification.adb:75` imposes for a `us-east-1`/`s3` scope. There is no existing test on `Static_Credentials`, so nothing asserts the wrong behaviour; the corpus uses `Principal => "test-principal"` and the harness `"qualification"`. The verifier records the discovery's P2 as defensible because a principal above 256 bytes is an unusual configuration. A fix needs one maintainer decision, because both bounds are interface values: either `Maximum_Principal_Bytes` drops to the 256 the HTTP layer imposes, so a visible constant changes value and `Create` starts raising `Invalid_Credentials` for inputs it used to accept, or `Authentication` stops treating an over-long principal as `Credential_Rejected` and reports it distinctly, which needs a new `Outcome_Status` literal and a new S3 error mapping. Documenting 256 alone would leave `Create`'s `@exception Invalid_Credentials ... too long` promise unmet.

## Coverage evidence: SIGV4

- `SigV4.Sign` canonical request: method token validation, single URI encoding of the decoded path with `/` preserved, canonical query encoding and sort order matching botocore's `_canonical_query_string_url`, canonical header lowercasing, trimming, folding, stable sort and repeated-name joining, exactly one `host`, and payload-hash validation; all four AWS S3 published examples are asserted byte for byte on canonical-request hash and signature in `Check_SigV4_Official_Vectors` at `tests/src/object_storage_test_cases.adb:8905-9040`.
- `SigV4.Sign` string-to-sign and key derivation, including the full key chain and the wiping of every derived key and the prefixed secret on both normal and exceptional exit; `SigV4.Constant_Time_Equal` at `src/flyology-object_storage-s3-sigv4.adb:322-342`, re-derived by the verifier, folds the length difference into the accumulator and has no data-dependent exit.
- `SigV4_Encoding` under SPARK: `URI_Encode`'s three-times bound and loop invariant, ASCII-only `Lowercase`, `Normalize_Header_Value` trimming and folding, calendar-aware `Valid_Timestamp`, and the tchar and character-set validators.
- `SigV4_Verification.Parse`: prefix and single space, attribute splitting, rejection of duplicates and unknown attributes, the five-part scope with literal `aws4_request`, `SignedHeaders` required to be lowercase, tchar, strictly ascending and to include `host`, `x-amz-content-sha256` and `x-amz-date`, a 64-lowercase-hex signature, bounded inputs, and `Constraint_Error` mapped to `Malformed_Authorization`.
- `SigV4_Verification.Verify`: origin-form targets only, strict percent-escape validation that fails closed, query splitting before decoding so `%26` and `%3D` inside values are preserved, the `s3` service pin, the scope-date equality check, the payload-hash equality check, exact `SignedHeaders` agreement, constant-time signature comparison, and normalization consistent with MinIO's `EncodePath` and with the crate's own client.
- `Authentication.Verify_Request` admission rules: exactly one `authorization`, `x-amz-date` and `x-amz-content-sha256`; `STREAMING-*` hashes failing closed with 400; every physical `x-amz-*` header required in `SignedHeaders`; the session-token singleton rule; two-directional skew against a caller-supplied `Now`; the optional region pin; `UNSIGNED-PAYLOAD` only on `Secure_HTTPS`; per-occurrence header collection in wire order bounded at 256.
- Body-hash enforcement at `src/flyology-object_storage-server-s3_applications.adb:4055-4059` and every `Expected_Hash => Auth.Payload_Hash` site: the streamed body's SHA-256 is compared with the signed digest and a started response is failed rather than completed.
- `Static_Credentials` alphanumeric access keys, bounded copies into provider-owned fixed arrays, constant-time session-token comparison in both directions, and `Finalize` wiping all four buffers; `MFA` bounded copies and control-byte rejection; `Secrets` and its C shim volatile wipe loop with zero-length guards and wiping on exceptional paths.
- Client `low_level` signing on both preparers: the decoded path is signed and the encoded path sent, the query is canonicalised once, `host`, `x-amz-content-sha256`, `x-amz-date` and any session-token header are always signed, `UNSIGNED-PAYLOAD` is refused off HTTPS, and the 8,192-byte target bound mirrors the server.
- Verifier probe `tests/repros/src/repro_sigv4_probe.adb` passes with exit status 0 and is the evidence for seven checks: `UNSIGNED-PAYLOAD` is genuinely refused on plain HTTP with 400 and the body is not stored; two `Authorization` fields are rejected 400; header auth plus a presigned-style query is refused 400 by the operation's query validator without an internal error; a padded, mixed-case signed header verifies; a declared but absent signed header is rejected 400; an unsigned physical `x-amz-*` header is rejected 400; a scope date differing from `x-amz-date` is rejected 400; an uppercase `x-amz-content-sha256` is rejected 400 at admission; a presigned-style request is a clean 403 AccessDenied; and a body that does not match the signed hash is 400 XAmzContentSHA256Mismatch with nothing published.
- Read-only checks with no probe: request trailers are not an unsigned-input hole, because the `x-amz-trailer` header must itself be signed and `Reject_Unexpected_Trailers` at `s3_applications.adb:4073-4078` rejects any undeclared trailer; `x-amz-s3session-token` must be signed and there are no session credentials to confuse it with; `Verify`'s `Signed_Headers = Declared_Signed_Headers` check is a real guard only for third-party providers, since the server path builds the array from the declared list itself.

## Observations not counted: SIGV4

- `aws-chunked` and the `STREAMING-*` payload hashes are rejected at admission with 400 and, for `Content-Encoding: aws-chunked` with a plain hash, NotImplemented; this is a documented boundary (`docs/compatibility/s3.md:452-460`, `docs/qualification/put-object.md:9-11,166`), but botocore 1.36 and later default to `STREAMING-UNSIGNED-PAYLOAD-TRAILER` over HTTPS (from memory, unverified), so an HTTPS deployment would see 400s from those clients while loopback conformance passes.
- Presigned URLs are not implemented on either side and `docs/compatibility/s3.md:78` records them as planned and not claimed; a presigned request arrives without `Authorization` and gets 403 AccessDenied.
- The credential scope service is hard-coded to `s3` (`sigv4_verification.adb:335`); if AWS SDKs sign `WriteGetObjectResponse` with `s3-object-lambda` (from memory, unverified), a stock SDK cannot call that operation, while the crate's own client signs it with `s3` so the pair is self-consistent.
- `x-amz-s3session-token` must be signed but is neither bound to a credential nor rejected, so a long-term key plus an arbitrary session token is accepted under `Static_Credentials`; whether `Create_Session` issues credentials that would need binding is a SERVER-area question.
- The access-key character set is `[A-Za-z0-9]` in `Sign`, `Parse` and `Create`, so MinIO and Ceph RGW identities using `-` or `_` can be neither used by this client nor configured as static server identities; policy value.
- Only `x-amz-date` is accepted, with no `Date` header fallback, and `x-amz-content-sha256` must be present and signed; documented boundary at `docs/compatibility/s3.md:452-457`.
- Timestamps with year 0001 to 1900 pass `Valid_Timestamp` and fail `Year_Number` inside `Timestamp_Time`, yielding 400 AuthorizationHeaderMalformed rather than 403 RequestTimeTooSkewed; same family as SIGV4-1 but caught, so diagnostics only.
- Canonical-URI normalization is not injective on the raw target, so `/b/a%2Fc` and `/b/a/c` share a signature; identical to MinIO and harmless as long as the router decodes the target the same way.
- Best-effort erasure gaps consistent with `README.md:407-412`: the secondary-stack copy returned by `Static_Credentials.Secret_Key`, the return copies of `SigV4.HMAC`, and GNAT.SHA256's internal context copy are not wiped.
- `UNSIGNED-PAYLOAD` requires the listener's own scheme to be HTTPS, so behind a TLS-terminating proxy the SDK default is refused with 400 InvalidRequest; policy.
- `Static_Credentials.Authenticate` compares the access key with ordinary `=` before the constant-time checks (`static_credentials.adb:81`), so timing reveals whether an access key exists; AWS distinguishes this case explicitly with `InvalidAccessKeyId`, so it is not counted.
- Bounds that no stock client approaches: more than 128 query parameters returns False and 403; more than 256 signed physical header occurrences or more than 128 signed names returns 400.
- Diagnostic drift on input no stock client produces: a declared but absent signed header yields 400 AuthorizationHeaderMalformed where AWS answers 403 SignatureDoesNotMatch, and a trailing `&` or empty query segment yields 403 SignatureDoesNotMatch.
- Query sort order is by encoded name, which is botocore's behaviour, while aws-sdk-go sorts raw keys before encoding, so the two SDK families disagree for keys mixing unreserved and reserved bytes in the 0x2D to 0x2F range; ecosystem ambiguity, not a defect of this crate.
- `tools/s3-signed-socket.py` checks the request line, `Host`, header presence and `SignedHeaders` membership only and never recomputes a signature, so the signed-socket qualification does not itself evidence signature correctness; the AUnit vectors do.
