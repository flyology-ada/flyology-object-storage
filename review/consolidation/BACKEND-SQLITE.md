## Area section

## BACKEND-SQLITE: the SQLite backend crate, its catalog, and its durability shim (BACKEND-SQLITE-1 .. BACKEND-SQLITE-5)

The area covers `sqlite/src/flyology-object_storage-backends-sqlite.ad?`, `-sqlite-catalogs.ad?`, `-sqlite-databases.ad?`, `-sqlite-c.ads` and `sqlite/src/flyology_object_storage_sqlite_durability.c`, against the backend contract in `src/flyology-object_storage-backends.ads`, with `src/flyology-object_storage-backends-memory.adb` and `-backends-files.adb` read as cross-backend controls, `src/flyology-object_storage-server-s3_applications.adb` read for the status mapping, and `docs/architecture/sqlite-backend.md`, `docs/qualification/object-annotations-backend-server.md`, the SQLite suite and `tests/scripts/test-flyology-server.sh` read for the claimed coverage. The reproduction programs live in the second harness, `sqlite/tests/repros/src/`, whose smoke program `repro_sqlite_smoke` passes with exit status 0. One defect confirmed in another area is also present here and is not counted twice: the same-key copy predicate of BACKEND-MEMORY-2, which rejects a versioned self-copy as `Invalid_Request` without consulting `Options.Source_Selector`, is duplicated verbatim at `sqlite/src/flyology-object_storage-backends-sqlite.adb:2436-2445`, so a fix has to change this backend as well as the memory one.

### BACKEND-SQLITE-1: `Get_Object` opens the payload after the catalog gate is released, so a concurrent overwrite turns a valid GET into 503 SlowDown

**Severity:** P1 (the discovery said P2 with Medium confidence, assuming the window is a few instructions wide and that stock clients retry the 503; the verifier raised it because the measured rate under ordinary reader concurrency is about twelve failed GETs per overwrite rather than a rare edge, and because the code breaks an invariant `docs/architecture/sqlite-backend.md:20-23` states).

**Location:** `sqlite/src/flyology-object_storage-backends-sqlite.adb:2666-2683`, where `Get_Object` calls `Catalogs.Find_Selected_Object` with no `Check` argument, then evaluates read conditions, then calls `SIO.Open`; the overload that releases the gate before returning at `sqlite/src/flyology-object_storage-sqlite-catalogs.adb:5688-5716`; the hook's documented purpose at `sqlite/src/flyology-object_storage-sqlite-catalogs.ads:707-712`; the two sibling readers that do pass it, `Head_Object` at `backends-sqlite.adb:2581-2583` and `Copy_Object` at `:2448-2451`; the immediate unlink of the replaced payload at `:2232-2235`; the `when others` that produces the status at `:2736-2745`; the same unprotected window in the part readers at `:4067-4072` and `:4295-4301`; the S3 mapping at `src/flyology-object_storage-server-s3_applications.adb:1951-1954`; the invariant the code does not keep at `docs/architecture/sqlite-backend.md:20-23`.

**Repro:** `sqlite/tests/repros/src/repro_sqlite_1.adb`, exit status 1, two failed expectations.

**What is wrong:** `Get_Object` resolves the payload name under the catalog operation gate and opens the file after the gate has been released, while a concurrent `Put_Object` on the same key unlinks the superseded payload as soon as it leaves the gate. The reader's `SIO.Open` then raises `Name_Error`, the `when others` handler turns it into `Backend_Unavailable`, and the S3 boundary answers 503 `SlowDown` for a key that exists before and after the request. The program opens a SQLite store on a fresh scratch root, seeds one key, and runs two 20 s phases of 32 reader tasks against 2 writer tasks that all publish the same bytes, so the entity tag never changes and every GET is required to succeed. Phase A reads with no conditions: 316,407 GETs, 294,126 `SUCCESS` and 22,281 `BACKEND_UNAVAILABLE`, that is 7.0 %, against 1,822 PUTs that all returned `Success`. Phase B repeats it with a 14,284-byte matching `If-Match` list, the only work `Get_Object` performs inside the unprotected window: 336,671 GETs, 317,508 `SUCCESS` and 19,163 `BACKEND_UNAVAILABLE` against 1,792 PUTs, which shows the dominant factor is reader scheduling rather than the window's instruction count. Zero `NOT_FOUND` was recorded in either phase, so the catalog lookup always succeeded and only the file open failed, and the single-task control GET with the same arguments succeeds.

**Notes:** Not P0 because nothing is lost, no request is served with wrong bytes (the size check at `backends-sqlite.adb:2679-2681` and the immutable payload names prevent that), and 503 is retriable. The fix needs no interface change: `Head_Object` and `Copy_Object` already pass the `Check` hook for exactly this purpose and an open POSIX descriptor survives unlink, so giving `Get_Object` and the two part readers the same hook closes the window. The behaviour also contradicts `docs/architecture/sqlite-backend.md:20-23`, "Superseded and deleted bodies are intentionally retained until that recovery pass so an already-open reader is never invalidated by replacement", so either the code or that sentence has to change; this is discovery observation O5, confirmed and promoted into the finding rather than left as free-standing drift. No existing test asserts the wrong behaviour, because `sqlite/tests/src/flyology_object_storage_sqlite_tests.adb:1365-1518` races only writes against writes.

### BACKEND-SQLITE-2: the annotation copy lease is released below its own `CHECK(refs>0)`, so the first CopyObject of an annotated source raises after the destination has been committed

**Severity:** P1 (the discovery also said P1).

**Location:** `sqlite/src/flyology-object_storage-sqlite-catalogs.adb:2842-2846`, where the TEMP table is created as `annotation_copy_leases(payload TEXT PRIMARY KEY, refs INTEGER NOT NULL CHECK(refs>0)) WITHOUT ROWID`; the insert at `:846-856` (`VALUES(?1,1)` with `ON CONFLICT(payload) DO UPDATE SET refs=refs+1`); the release at `:874-892` (`UPDATE ... SET refs=refs-1 WHERE payload=?1 AND refs>0` followed by an unreachable `DELETE ... WHERE payload=?1 AND refs=0`); the unconditional annotation read at `:7331-7347`; the reclamation that counts the table at `:9150-9166`; the only caller of that overload and its lease handling at `backends-sqlite.adb:2448-2451`, `:2459`, `:2520-2521`, `:2532-2541`, with `Release_Annotations` at `:2378-2392`; the raise at `sqlite/src/flyology-object_storage-sqlite-databases.adb:398-400`; the build flags that contain no CHECK suppression at `sqlite/flyology_object_storage_sqlite.gpr:19-36`; the S3 dispatch at `src/flyology-object_storage-server-s3_applications.adb:14555` and the catch-all that renders 500 at `:18056-18065`.

**Repro:** `sqlite/tests/repros/src/repro_sqlite_2.adb`, exit status 1, four failed expectations.

**What is wrong:** the temporary lease table that keeps a source annotation payload alive across a copy declares `CHECK(refs>0)` but releases with `SET refs=refs-1`, so the very first release of a lease taken at 1 violates the constraint and `Step` raises `SQLite_Error` with "CHECK constraint failed: refs>0". `Release_Annotations` clears `Annotation_Leases_Held` only after the fallible call returns, so the raise leaves the flag set, `Copy_Object`'s own `when others` handler re-enters the release and raises inside itself, and the `SQLite_Error` escapes `Copy_Object` entirely; the S3 boundary answers 500 `InternalError`. Every CopyObject of an annotated source is affected, deterministically, on the first copy of that source in a process, and in both copy directives: the program reproduces it with the default directive and again with `Exclude_Annotations`, which the discovery predicted but did not demonstrate. The destination has already been committed at the point of the raise, which the program shows by reading the copied annotation and heading the copied object successfully after the exception, so a client sees 500 for a copy that actually succeeded, and a retry against a versioning-enabled bucket publishes a second destination generation. A second copy of the same source succeeds, because the lease then goes 1 to 2 to 1, which is what masks the defect; an unannotated control copy in the same program succeeds, which is why the maintained copy tests pass.

**Notes:** Not P0: nothing is lost or corrupted and the client's retry succeeds. Two side effects matter for the fix. The `DELETE ... WHERE refs=0` immediately after the update is dead code, because the CHECK makes `refs=0` unreachable, so the intended reference-count lifecycle cannot complete even once; and the stranded `refs=1` row keeps `Delete_Payload_If_Unreferenced` at `catalogs.adb:9150-9166` from ever reclaiming that annotation payload until the process restarts. There is no SQLite annotation coverage at all, which is BACKEND-SQLITE-5, so no existing test asserts the wrong behaviour; the memory and pure-files backends are covered by `tests/src/object_storage_test_cases.adb:19555-19696`, driven at `:19734` and `:19743`. A fix needs a maintainer decision on the intended lease lifecycle, either dropping the `CHECK` and keeping the delete-at-zero, or making the release a `DELETE ... WHERE refs=1` and `UPDATE ... WHERE refs>1` pair, and should separately clear `Annotation_Leases_Held` before the fallible call so the handler cannot re-enter it. This defect is also what makes BACKEND-SQLITE-3's release path fail today, though BACKEND-SQLITE-3 stands independently of it.

### BACKEND-SQLITE-3: a failed lease release inside `Find_Selected_Object`'s exception handler skips `Gate.Release` and leaks the catalog gate forever

**Severity:** P0 (the discovery also said P0). The store stops answering every operation, on every bucket, permanently, until the process is killed.

**Location:** `sqlite/src/flyology-object_storage-sqlite-catalogs.adb:7349-7361`, where the handler runs `Release_Annotation_Copy_Leases_Internal (Item, Annotations)` before `Item.Gate.Release`; the fallible release at `:864-893`, which raises whenever the update does not change exactly one row and always for a lease at 1; `Operation_Gate` at `:918-928`, an `entry Acquire when not Held` with a plain `procedure Release`, no owner tracking, no timeout and no controlled unlock; the `Item.Gate.Acquire` that begins every catalog operation, for example `:3348`, `:5701`, `:5734`, `:7331` and `:9148`; the gate-safe sibling `Release_Annotation_Copy_Snapshot` at `:7363-7379`; the non-leasing overload that `Get_Object` and `Head_Object` use at `:5688-5716`; `Open_Source` at `sqlite/src/flyology-object_storage-backends-sqlite.adb:2394-2416` and `Check_Context` at `:164-177`, which raise `Operation_Cancelled`, `Timeout_Error` or `Data_Error`; the only caller of the lease-taking overload at `:2448-2451`.

**Repro:** two programs. `sqlite/tests/repros/src/repro_sqlite_3.adb` is the deterministic mechanism: it seeds a key, attaches one annotation, confirms `Head_Bucket` works, removes the source body file so `Open_Source` raises `Data_Error` under the gate, calls `Copy_Object`, and then probes `Head_Bucket` from a second task with a bounded 5 s wait; exit status 1, one failed expectation. `sqlite/tests/repros/src/repro_sqlite_3b.adb` is the caller-reachable trigger with no tampering: the same setup with 200 annotations attached purely to widen the interval between `Copy_Object`'s entry `Check_Context` and the `Open_Source` callback, and the `Deadline` argument alone as the trigger, scanned upward in 3 µs steps (attempts rejected at the entry check raise `Timeout_Error`, take no leases and are harmless, so the scan is safe); it stops at a 6 µs deadline after 1 attempt rejected at the entry check, and the probe again does not return within 5 s; exit status 1, one failed expectation.

**What is wrong:** the release that runs before the unlock is fallible, so a raise there skips `Item.Gate.Release` and `Held` stays `True` for the life of the process. Every subsequent catalog call, on any bucket, then blocks in the protected entry with no deadline and no cancellation, including `Close`, so an S3 server on this backend stops answering every request and cannot even close the store; re-opening cannot recover it from the same process. The caller-reachable sequence is `Copy_Object`, the only caller of the lease-taking overload, on a source generation carrying at least one annotation, where the `Open_Source` callback raises. `Open_Source` raises when the caller's token is cancelled, when the caller's deadline has passed, or when the source body file is missing, symlinked or mis-sized. Cancellation and deadline are plain arguments of the public `Copy_Object` profile, so an ordinary S3 CopyObject whose client aborts, or whose request deadline expires while the request waits for the gate, wedges the whole backend; `repro_sqlite_3b` demonstrates exactly that through the public `Backend` interface with nothing but a caller-supplied deadline. `Get_Object` and `Head_Object` cannot reach the leaking handler: they use the overload at `catalogs.adb:5688-5716`, which takes no leases and whose handler releases the gate unconditionally, so a cancelled or timed-out GET of an annotated object is not enough.

**Notes:** the amplifier is the unconditional gate entry the discovery lists as observation O9 (`catalogs.adb:918-928`): `Gate.Acquire` ignores the caller's `Token` and `Deadline` while waiting, so under contention a request's deadline can expire inside the gate-held window, which is what makes the timed-out-copy trigger easy to hit; on its own O9 is only latency, but a fix for this P0 should consider it. Discovery observation O3, the full-bucket listing scans that hold the gate, compounds it for the same reason. Two secondary effects are visible in the runs: the timed-out `Copy_Object` reports `Backend_Unavailable` instead of propagating `Timeout_Error`, because the SQLite exception replaced the original one before `Copy_Object`'s `when Operation_Cancelled | Timeout_Error => raise` handler could see it, and the store is unrecoverable in-process. Independently of BACKEND-SQLITE-2's constraint violation, any SQLite failure in the release has the same effect, because the handler puts fallible work before the unlock. No existing test covers it: the SQLite suite performs no annotation operation and no test asserts that the store survives a failed `Copy_Object`. A fix needs the unlock to run first, or under a controlled object, plus the separate BACKEND-SQLITE-2 lease repair; whether `Gate.Acquire` should honour the caller's deadline is a maintainer decision.

### BACKEND-SQLITE-4: `Delete_Bucket` reports `Backend_Unavailable` for a bucket whose keys are all delete markers

**Severity:** P1 (the discovery also said P1).

**Location:** `sqlite/src/flyology-object_storage-sqlite-catalogs.adb:3352-3374`, where the emptiness test is `EXISTS(... FROM buckets ...)`, `EXISTS(... FROM objects ...)` and `EXISTS(... FROM multipart_uploads ...)` and `object_versions` is never consulted; the restricting foreign key at `:387` (`FOREIGN KEY(bucket_name) REFERENCES buckets(name) ON DELETE RESTRICT`); the marker publication that removes the `objects` mirror row and returns early at `:6271-6279` and `:6317-6319`; the transaction and `Safe_Rollback` at `:3385-3393`; the wrapper that re-raises only `Operation_Cancelled` and `Timeout_Error` and turns everything else into `Backend_Unavailable` at `sqlite/src/flyology-object_storage-backends-sqlite.adb:386-406`; the documented status at `src/flyology-object_storage.ads:21,45` ("Bucket still contains objects"); the two backends that get it right, `src/flyology-object_storage-backends-files.adb:3846-3852` and `src/flyology-object_storage-backends-memory.adb:578-600` with markers retained at `backends-memory.adb:1957`; the S3 mappings at `src/flyology-object_storage-server-s3_applications.adb:1947-1950` (409 `BucketNotEmpty`) and `:1951-1954` (503 `SlowDown`); the existing assertions at `sqlite/tests/src/flyology_object_storage_sqlite_tests.adb:7660-7663` and `:1503-1518`.

**Repro:** `sqlite/tests/repros/src/repro_sqlite_4.adb`, exit status 1, one failed expectation.

**What is wrong:** `Catalogs.Delete_Bucket` decides emptiness from the current-object mirror and the multipart table only, but `object_versions` holds retained generations and restricts the bucket row. Any versioning-enabled or suspended bucket whose keys have all been deleted through DeleteObject therefore has no mirror rows, passes the emptiness test, and then trips the foreign key inside the transaction; the SQLite error is rewrapped as `Backend_Unavailable` and the server answers 503 `SlowDown` rather than the 409 `BucketNotEmpty` that the defined status exists to produce. Every client that enables versioning, deletes its objects the ordinary way, and then tries to delete the bucket sees an indefinite retry loop instead of a definitive answer telling it to remove the versions first. The failure is deterministic. The program runs one class-wide procedure over the identical sequence, `Create_Bucket`, `Put_Bucket_Versioning (Versioning_Enabled)`, `Put_Object`, `Delete_Object`, `Head_Object`, `Delete_Bucket`, first against the memory store as a control and then against a SQLite store on a fresh root: the memory control returns `BUCKET_NOT_EMPTY` and SQLite returns `BACKEND_UNAVAILABLE`.

**Notes:** Not P0: nothing is deleted, because the transaction rolls back, so the defect is the reported status rather than durability. The memory and pure-files backends both count retained generations, so the cross-backend expectation is unambiguous and no maintainer decision is needed beyond adding `EXISTS(SELECT 1 FROM object_versions WHERE bucket_name=?1)` to the emptiness query; the discovery's supporting claim that AWS answers 409 `BucketNotEmpty` here was recorded as from memory and unverified, and the finding does not rest on it. The existing SQLite `Bucket_Not_Empty` assertion at `sqlite/tests/src/flyology_object_storage_sqlite_tests.adb:7660-7663` asserts the status only with a current data object, and the versioning race test at `:1503-1518` permanently removes the generation before its `Delete_Bucket` cleanup, so the marker-only path is untested and no test asserts the wrong behaviour.

### BACKEND-SQLITE-5: the annotation qualification record claims SQLite corpus evidence that does not exist

**Severity:** P2 (the discovery also said P2). Contract and qualification drift: the document overstates the evidence, and the gap it hides is precisely where BACKEND-SQLITE-2 and BACKEND-SQLITE-3 live.

**Location:** `docs/qualification/object-annotations-backend-server.md:26-27` ("Memory, pure-files, and SQLite implement the same interface.") and `:45-47` ("The maintained backend and server corpora exercise payload, checksum, version, list, missing, condition, and copy-directive behavior across the implementations."); `sqlite/tests/src/flyology_object_storage_sqlite_tests.adb`, which has zero matches for `Put_Object_Annotation`, `Get_Object_Annotation`, `Delete_Object_Annotation` or `List_Object_Annotations`, its only `annotation` matches being migration DDL fixtures at `:551-963` and `:1861-1872` and `Empty_Vector` arguments at `:3397-3398` and `:3439-3440`; `tests/src/s3_implementation_corpus.adb`, which has zero matches for `annotation` and which `tests/scripts/test-flyology-server.sh:39-41,111-122` shows to be the only corpus run against `s3_sqlite_server`; the class-wide `Exercise_Object_Annotations` at `tests/src/object_storage_test_cases.adb:19555-19696` with its copy-directive assertions at `:19661-19675`, driven at `:19734` and `:19743`; `docs/architecture/sqlite-backend.md`, which does not mention annotations at all.

**Repro:** none. This is a documentation finding with no program; it was verified with `rg` and by reading the cited sources, as the area brief allows.

**What is wrong:** the qualification record presents annotation behaviour as corpus-verified "across the implementations" while naming SQLite as one of them, but no SQLite-backed test performs any annotation operation, and the only black-box corpus run against `s3_sqlite_server` has no annotation coverage. A reader auditing the record would conclude that SQLite annotation copy is exercised, while BACKEND-SQLITE-2 and BACKEND-SQLITE-3 show that the first CopyObject of any annotated SQLite object fails and can wedge the store.

**Notes:** one correction to the discovery, which said annotation behaviour is asserted only on the memory backend: it is exercised against two, because `Exercise_Object_Annotations` is defined over `Backends.Backend'Class` and driven against both the memory store and the pure-files store. The substantive claim survives, because that suite lives in the root crate and the SQLite suite is a separate crate that does not call it, so the exerciser is never driven against a SQLite store. The cheapest repair is to run the existing class-wide `Exercise_Object_Annotations` against a SQLite store from the SQLite suite, which would have caught both of the annotation defects above; if that is not wanted, the sentence at `:45-47` should name the implementations it actually covers.

## Coverage evidence: BACKEND-SQLITE

- `Databases` binding layer: text and blob binds copy through `sqlite3_malloc64` with `SQLITE_TRANSIENT`, all integers use `bind_int64` and `column_int64`, object keys, version IDs, tags, metadata, entity tags and documents bind as BLOB while bucket names and payload names bind as TEXT with `COLLATE BINARY`, `column_text` and `column_blob` are read before `column_bytes`, every statement is a stack-local controlled object finalized on scope exit so none outlives an exception, `Reset` clears bindings, and `Step` maps every non-ROW and non-DONE code to `SQLite_Error`.
- `Open`: `trusted_schema=OFF`, `foreign_keys=ON` verified, application id and `user_version` checked, an empty database created under `BEGIN EXCLUSIVE`, a nonempty unrecognized database and a newer schema refused, the V1 to V22 upgrades each in one exclusive transaction with rollback on failure, WAL and `synchronous=FULL` verified after migration, the table and column validators, and `quick_check`; the catalog handle is closed and the gate released on any failure. The root lock is acquired before the catalog opens, staging and unreferenced objects are reclaimed before serving, and both directories are synced.
- Versioning merge: `CASE WHEN ?2=0 THEN versioning_status ELSE ?2` and the MFA twin match `Merge_Bucket_Versioning`'s postcondition exactly, because `Versioning_Unconfigured` and `MFA_Delete_Unconfigured` are position 0 (`src/flyology-object_storage.ads:230-240`), the columns are `NOT NULL` with `CHECK ... BETWEEN 0 AND 2`, and both parameters bind as integers so no NULL can enter the CASE. MFA and Object-Lock admission is read and the row published under the same gate.
- PUT publication order matches `docs/architecture/sqlite-backend.md:8-14`: exclusive staging create, fsync (`F_FULLFSYNC` then `fsync`), rename, objects-directory sync, then one `BEGIN IMMEDIATE` transaction that evaluates write conditions against the current mirror, upserts the mirror, replaces metadata, tags and parts, publishes the generation per versioning mode, copies annotations and commits with `synchronous=FULL`; a non-success or raised catalog result deletes the new payload, and the previous payload is removed only after commit. Payload names are SHA-256 of bucket, key, sequence, pid and clock rather than of content, so equal bodies never share a name and `payload UNIQUE` cannot fire on valid input.
- Delete paths: `Delete_Selected_Object` and `Delete_Objects` run `BEGIN IMMEDIATE`, read versioning and MFA once, evaluate `Require_Unversioned` and MFA before the first entry, evaluate conditions per entry, publish opaque or null markers with publication-order verification, refresh the current mirror, and roll back the whole batch on any raise; retired payloads are reclaimed only after commit and only when unreferenced.
- Multipart: `Put_Multipart_Part`, `Complete_Multipart_Upload` and `Abort_Multipart_Upload` each run one transaction; completion re-validates every selected part's payload, size, modified time, entity tag and checksum inside the transaction (`Conflict` on drift) and enforces ascending order, composite contiguity, the 5 MiB minimum for nonfinal parts, capacity, expected size and expected checksum, then retires the upload and its parts atomically.
- Listing: bucket, part, annotation and point-configuration pages use keyset predicates with `LIMIT Maximum+1`; object and version listings order by BLOB `object_key` bytewise and by `publication_order DESC`; delimiter projection and the paired key and version cursor are computed in Ada; delete-marker rows are validated to carry no object metadata.
- Object Lock, legal hold and retention: the bucket must be versioning-enabled for Put, retention may only be extended in the same mode, and permanent deletion checks legal hold and unexpired retention inside the delete transaction.
- Bucket metadata state CAS (`Create_Bucket_Metadata_State`, `Replace_Bucket_Metadata_State`, `Delete_Bucket_Metadata_State`) compares the complete expected snapshot inside a transaction under the gate.
- Unix durability C shim: `flock(LOCK_EX|LOCK_NB)` on a persistent inode with `O_CLOEXEC`, `F_FULLFSYNC` with a fallback to `fsync`, and errors reported through the return code and mapped to `Device_Error` in Ada.
- Verifier measurements with no finding: the vendored build defines `SQLITE_THREADSAFE`, `SQLITE_DQS`, `SQLITE_DEFAULT_MEMSTATUS`, `SQLITE_OMIT_DEPRECATED`, `SQLITE_ENABLE_API_ARMOR`, `SQLITE_ENABLE_COLUMN_METADATA`, `SQLITE_ENABLE_DBSTAT_VTAB`, `SQLITE_ENABLE_RTREE` and `SQLITE_USE_URI` and suppresses no CHECK constraint (`sqlite/flyology_object_storage_sqlite.gpr:19-36`); `Get_Object` is the only reader of `Find_Selected_Object` without a `Check` hook, across the three call sites at `backends-sqlite.adb:2448`, `:2581` and `:2666`; `Delete_Bucket` leaves no partial state, because it runs inside `Begin_Transaction` with `Safe_Rollback` on the handler.

## Observations not counted: BACKEND-SQLITE

- The same-key copy predicate confirmed as BACKEND-MEMORY-2 is duplicated verbatim at `sqlite/src/flyology-object_storage-backends-sqlite.adb:2436-2445`; counted once, in that area, but a fix has to change this backend too.
- O1 `backends-sqlite.adb:2884-2886`: `Delete_Objects` calls `Delete_Payload_If_Unreferenced` without the per-payload `begin ... when others => null` that `Delete_Selected_Object` uses (`:2823-2831`) and without its `Sync_Path (Objects_Path, Directory => True)` (`:2831-2833`). Below the rubric, because `Delete_Payload_If_Present` (`:224-233`) swallows every filesystem error, so only a SQLite failure inside the catalog call can raise, and the `Backend_Unavailable` result is explicitly ambiguous by contract; worth fixing for symmetry, not a demonstrable defect.
- O2 `catalogs.adb:8776-9040`: `Complete_Multipart_Upload` fills `Retired_Payloads` only from `Collect_Multipart_Payloads` and never calls `Append_Version_Annotation_Payloads_Internal`, unlike `Put_Object` (`:6066`, `:6087`) and the delete paths (`:6500`, `:6554`), so annotation payload files of replaced generations are orphaned. The catalog rows go away with the generation and startup reclamation removes the files, so this is a bounded disk leak, not incorrectness.
- O3 `catalogs.adb:7981-7988, 8122-8218`: `List_Objects` scans every object of the bucket per page and `List_Object_Versions` appends every prefix-matching generation into an Ada vector before projecting the page, both while holding the gate; per-request memory and latency grow with bucket size. Scalability rather than correctness, but it compounds BACKEND-SQLITE-3, because a long listing is what makes another request's deadline expire while it waits for the gate.
- O4 `catalogs.adb:8221-8237`: a `Version_ID_Marker` that no longer exists yields `Invalid_Request`; the memory backend does the same (`backends-memory.adb:2677-2691`), so this is a cross-backend design choice outside this area.
