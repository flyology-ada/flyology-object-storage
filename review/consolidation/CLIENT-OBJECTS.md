### CLIENT-OBJECTS-1: Whole/range GetObject and HeadObject reject a valid 200/206 that omits `x-amz-version-id` after a `versionId=` request

**Severity:** P0 (the discovery report said P1). The verifier raised it because the effect is a total interop break rather than a corner of one operation: no stock server can satisfy the demand for an object in a bucket that never had versioning enabled, which is the documented meaning of `versionId=null`, and the only server that passes is the in-repo one, whose fallback exists to satisfy exactly this check. The counter-reading the verifier recorded and rejected: the rubric's P0 clause names "an interop-breaking protocol violation that a stock client or server rejects", and here the crate emits conforming requests and mis-validates conforming responses, so a strict textual reading lands on P1 ("wrong result or unexpected exception on valid input"), a direction of rejection the verifier judged immaterial to the harm the clause exists to capture.

**Location:** `src/flyology-object_storage-client-objects.adb:121-137` (`Get_Object_Response_Bound`) and `:139-155` (`Head_Object_Response_Bound`), both returning `(Requested_Version'Length = 0 or else US.To_String (Result.Version_ID) = Requested_Version) and then (Returned_Payer /= "requester" or else Requested_Payer = "requester")`; the four callers reached from public entry points, `:951-956` (synchronous `Get_Whole`, `raise Low_Level.Invalid_Response`), `:2429-2434` (composable whole read), `:2551-2556` (composable range read) and `:2964-2973` (composable HeadObject); the verbatim copy of the caller's selector into the bound at `:2683`, `:2804` and `:3063`, with no `"null"` special case anywhere in the file; the decoders that leave `Version_ID` empty when the header is absent at `src/flyology-object_storage-client-low_level.adb:5813` (HeadObject) and `:7220` (GetObject); the in-repo server's fallbacks at `src/flyology-object_storage-server-s3_applications.adb:4189-4194` and `:16620-16622`; the existing assertions of the wrong behaviour at `tests/src/s3_http_socket_corpus.adb:9333` (definition `:9308-9331`) and `:9741` (definition `:9711-9739`); the qualification prose at `docs/qualification/get-object.md:11-12` and `head-object.md:10-11`.

**Repro:** `tests/repros/src/repro_client_objects_1.adb` with helper `repro_client_objects_fake.ads/.adb`, exit status 1, three failed expectations.

**What is wrong:** `Get_Object_Response_Bound` and `Head_Object_Response_Bound` require a successful response to echo the requested `versionId` byte-for-byte. The pinned model marks `VersionId` optional on both output shapes — `GetObjectOutput` and `HeadObjectOutput` have `required: None` and carry `VersionId` as `{"shape":"ObjectVersionId","location":"header","locationName":"x-amz-version-id"}` — and a bucket that never had versioning enabled answers `?versionId=null` with a `200`/`206` carrying no `x-amz-version-id` at all: `review/baseline-rustfs.md` section 1 records that RustFS response verbatim, and section 5 records byte-identical failures against MinIO (`review/baseline/minio.log:96`) and SeaweedFS (`review/baseline/seaweedfs.log:99`). The absent header decodes to `Version_ID = ""`, `"" = "null"` is False, and a complete valid read is destroyed: the synchronous `Get_Whole` raises `Low_Level.Invalid_Response` after the head is decoded, the composable whole and range reads clear the destination and return `*_Exchange_Failed` with `Corrupt_Or_Invalid_Response`, and `Head_Object` returns `Head_Exchange_Failed`. Anyone addressing an object by `versionId=null` — the documented way to name an object in a never-versioned bucket, and what the repository's own conformance corpus does at `tests/src/s3_implementation_corpus.adb:1147` — hits it on every call. It is fully deterministic, because the predicate is a pure function of two strings. The program scripts six exchanges on a loopback origin: three carrying the verbatim RustFS never-versioned header set (`200 OK`, `accept-ranges`, `content-type`, strong `etag`, `last-modified`, `x-request-id`, `x-amz-request-id`, `date`, `content-length: 64`, no `x-amz-version-id`) and three controls identical except for an added `x-amz-version-id: null`, calling `Head_Object`, `Get_Whole` (`Whole_Get_Outcome` overload) and `Get_Whole` (bounded-destination overload) against each set with `Version_ID => "null"`. All three control legs pass, which isolates the version clause: with no `x-amz-request-charged` the payer clause is True, so it cannot be what fires.

**Notes:** This finding and CLIENT-LOW-1, the identical predicate in the low-level layer at `src/flyology-object_storage-client-low_level.adb:5641-5658`, are the two client-side defects behind the failed conformance corpus against RustFS, MinIO and SeaweedFS recorded in `review/baseline-rustfs.md`; SERVER-3, the in-repo server's unconditional `x-amz-version-id: null`, is the fallback that masks both, which is why the memory-server CI gate is green, so the three must be sequenced together and the client predicates fixed before the server spelling. One attribution difference to reconcile when filing: this area's reports place the unconditional emission in GetObject's `Set_Common_Headers` (`s3_applications.adb:16620-16622`) and the conditional one, emitted only when the request carried a version selector, on HeadObject (`:4189-4194`), which is the reverse of the operations named in SERVER-3; the masking effect is the same either way, because between them the in-repo server always supplies the header the client demands. Two existing tests assert the defective behaviour and must change with the fix, `tests/src/s3_http_socket_corpus.adb:9333` (`Require_Invalid_Whole_Get ("scoped-get-version-missing")`) and `:9741` (`Require_Invalid_Head ("scoped-head-version-missing")`); the `-mismatch`, `-duplicate`, `-control` and `-del` cases in the same loops are correct rejections and must keep failing. `docs/qualification/get-object.md:11-12` and `head-object.md:10-11` ("a successful response must echo it byte-for-byte") state the requirement the pinned model does not impose and no stock server satisfies, so they are part of the defect rather than a defence and must be reworded; the verifier explicitly did not treat them as a documented limitation for that reason. The maintainer decision a fix needs is the contract itself: relaxing the predicate to "present and different is a mismatch; absent is accepted" (`review/baseline-rustfs.md` section 7) is the minimal change, but it will still reject RustFS's suspended-versioning sentinel `00000000-0000-0000-0000-000000000000` (section 1(c)), so a strict-echo contract is not viable across real servers even after the relaxation, and whether the residual mismatch stays an exception with `Corrupt_Or_Invalid_Response` or becomes a typed outcome is a public-API decision, because today the exception escapes before any outcome exists and no oracle mode can classify it. `git log -S 'Get_Object_Response_Bound'` gives `f4cabde` and `-S 'Head_Object_Response_Bound'` gives `2703ed6`, both 2026-08-30; neither diffstat touches `tests/src/s3_implementation_corpus.adb` or any `tests/scripts/test-*.sh`, and both touch only `object_storage_test_cases.adb` and `s3_http_socket_corpus.adb`, whose fakes always echo the requested version.

### CLIENT-OBJECTS-2: Put/Get/DeleteObjectTagging reject every successful response that omits `x-amz-version-id`, even with no version requested

**Severity:** P0 (the discovery report said P1). The verifier raised it for the same interop reason as CLIENT-OBJECTS-1 and judged it stronger on three counts: the demand is unconditional, so no caller input avoids it; it was observed directly against a real server, `review/baseline-rustfs.md` section 8 recording RustFS's verbatim `200 OK` to the repository's own `PUT …?tagging` and the resulting `INVALID_RESPONSE`; and the mutation is actually applied while being reported as `Object_Tag_Mutation_Outcome_Unknown`, with the documented reconciliation read failing identically, so a caller can neither complete nor reconcile through this API. The same counter-reading applies and was again judged immaterial: the crate is the rejector rather than the emitter, so a strict textual reading of the rubric's P0 interop clause lands on P1.

**Location:** `src/flyology-object_storage-client-objects.adb:7177-7211` (`Tagging_Version_ID`), whose gate is `if Count > 1 or else (Success and then Count /= 1) then raise Low_Level.Invalid_Response with "invalid object tagging version header multiplicity";` and which consults `Requested` only later, at `:7203-7204`, for a present-and-different value; the three callers `:7421-7423` (Put, `Success := HTTP_Client.Status (Response) = 200`), `:7669-7671` (Get, `= 200`) and `:7960-7962` (Delete, `= 204`), each wrapping the call in `exception when Low_Level.Invalid_Response =>` and producing `Normalize_*_Failure (HTTP_Client.Response_Invalid, …)`; the `Start_*` procedures every public tagging entry point funnels through at `:7511`, `:7758` and `:8049`; the low-level decoder that already accepts an empty version at `src/flyology-object_storage-client-low_level.adb:12379-12383`; the in-repo server's `Set_Version_Header` at `src/flyology-object_storage-server-s3_applications.adb:15846-15854`; the maintained documents `docs/architecture/client-objects.md:99-101` and `docs/qualification/object-tagging.md:72-74`; the maintained certainty rows 3, 5 and 7 of `tests/corpora/composable-client/object-tagging-certainty.tsv`; the existing assertions of the wrong behaviour at `tests/src/s3_http_socket_corpus.adb:15091-15254` (`Require_Invalid_Version`), invoked at `:15256-15260`.

**Repro:** `tests/repros/src/repro_client_objects_2.adb`, exit status 1, six failed expectations.

**What is wrong:** `Tagging_Version_ID` raises `Low_Level.Invalid_Response` whenever a successful tagging response carries anything other than exactly one `x-amz-version-id` header. Rejecting a duplicate is right; rejecting an absent one is not, because the pinned model marks the member optional on all three output shapes — `PutObjectTaggingOutput.required` is `None`, `GetObjectTaggingOutput.required` is `['TagSet']` and `DeleteObjectTaggingOutput.required` is `None` — and a never-versioned bucket has no version to report. Because the multiplicity test never reads `Requested`, it fires on ordinary tagging calls that mention no version at all, which is exactly what the repository's own real-server call `Client_Objects.Put_Tags (…)` at `tests/src/s3_implementation_corpus.adb:1629` does. The consequence is worse than a failed read: the server applied the tag replacement or deletion and answered `200`/`204`, the client reports `Object_Tag_Mutation_Outcome_Unknown` with `Corrupt_Or_Invalid_Response`, the `Tagging_Outcome` convenience overload re-raises the exception, and the documented way out of an unknown mutation, a reconciling `Get_Tags`, fails the same way. It is deterministic and affects every caller using object tagging against MinIO, RustFS, SeaweedFS or AWS on a never-versioned bucket. The program scripts eight exchanges: four carrying the verbatim RustFS tagging reply shape from `review/baseline-rustfs.md` section 8 (`x-request-id`, `x-amz-request-id`, `content-length`, no `x-amz-version-id`; `200` for Put, `200` plus a one-tag `<Tagging>` document for Get, `204` for Delete), then four controls identical except for `x-amz-version-id: null`, calling `Put_Tags`, `Get_Tags`, `Delete_Tags` and the `Tagging_Outcome` convenience `Put_Tags`, with every `Parameters.Version_ID` left empty. All four control legs pass.

**Notes:** CLIENT-OBJECTS-2 and CLIENT-LOW-3 (`Execute_Object_Tagging`'s twin predicate at `src/flyology-object_storage-client-low_level.adb:12465-12475`) are the two tagging sites of one defect and share a fix direction; the corpus reaches this layer, not the low-level twin, because it calls `Client_Objects.Put_Tags`. As with CLIENT-OBJECTS-1, the in-repo server's always-emitted header is what keeps CI green, the server-side half being SERVER-3. The balance of maintained documents is against the code, not for it: `docs/architecture/client-objects.md:99-101` says "All three preserve the optional response version ID and structured S3 errors", and rows 3, 5 and 7 of `tests/corpora/composable-client/object-tagging-certainty.tsv` (`selection = omitted-version`) require a `200`/`204` with no S3 code to map to `Object_Tag_Mutation_Completed` with `No_Failure` and no reconciliation, which is precisely the case the code refuses; `docs/qualification/object-tagging.md:72-74` is ambiguous rather than permissive, so it is not a documented limitation, and a fix must reconcile it with `docs/architecture/client-objects.md:100-101`. `tests/src/s3_http_socket_corpus.adb:15091-15254` asserts the defective behaviour for all three operations and must change, but only its `Missing` variant is wrong; the `Duplicate`, `Mismatch`, `Control` and `Delete_Control` variants driven from the same loop are correct rejections. One maintainer decision is needed: whether an absent header on a success yields `Version_ID = ""`, matching the low-level decoder that already accepts an empty value at `client-low_level.adb:12379-12383`, or a new explicit "no version reported" discriminant on the tagging result records, which is a public API change. `git log -S "invalid object tagging version header multiplicity"` gives `51c4375` (2026-08-30) and `144d63d`; `51c4375`'s diffstat touches the socket corpus, the certainty TSV and the fixture verifier, not `tests/src/s3_implementation_corpus.adb` and no live-server script.

### CLIENT-OBJECTS-3: GetObjectTorrent labels every rejection `No_Failure`, including transient 500/503 responses that every sibling maps to `Unavailable_Or_Retryable`

**Severity:** P2 (new; the verifier raised it from the discovery report's second uncounted observation, which named only the 404 and 500 inconsistency and did not test it). Wrong diagnostics on a reachable path: the value is a label, callers can still read `Response.Kind`, `Response.Status` and `Response.Error.Code`, and no bytes or state are lost; it is not P1 because the response payload itself is correct and complete.

**Location:** `src/flyology-object_storage-client-objects.adb:5200-5210` (`Normalize_Get_Object_Torrent_Response`), which returns a fixed `Failure => No_Failure` for every decoded outcome with no reference to `Value.Kind`, `Value.Status`, the error `Code` or `Admission`; the classifying sibling in the same file, `Normalize_Get_Object_ACL_Response` at `:4899-4940`; the torrent path that reaches the normalizer only for a decoded complete response at `:5405-5422`; the shared domain's definition at `src/flyology-object_storage-client.ads:22-23` and the identical field wording for this operation's result at `src/flyology-object_storage-client-objects.ads:1527`; the existing coverage at `tests/src/s3_get_object_torrent_socket_corpus.adb:703`, with that corpus's only `500` scenarios at `:341-345` (`malformed-error`) and `:346-348` (`error-limit`).

**Repro:** `tests/repros/src/repro_client_objects_3.adb`, exit status 1, two failed expectations.

**What is wrong:** `Normalize_Get_Object_Torrent_Response` hardcodes `Failure => No_Failure` instead of classifying the decoded status and error code the way every other normalizer in the package does. The ACL sibling maps `404` with `NoSuchBucket|NoSuchKey|NoSuchVersion` to `Not_Found`, maps `409 OperationAborted`, `429 SlowDown`, `500 InternalError`, `502 BadGateway`, `503 SlowDown` and `504 RequestTimeout` to `Unavailable_Or_Retryable`, and maps anything unmodeled to `Corrupt_Or_Invalid_Response`; the tagging, legal-hold and retention normalizers carry the same table, and `tests/corpora/composable-client/put-certainty.tsv` documents it as the maintained policy. A caller that routes retry policy off the shared `Failure_Reason` domain — which `client.ads:22-23` presents as exactly that, the "stable reason domain shared by composable provider results", with `No_Failure` defined as "Successful or conclusively failed condition" — sees a `503 SlowDown` from GetObjectTorrent as carrying no failure, while the identical response to GetObjectAcl, GetObjectTagging, GetObjectLegalHold or GetObjectRetention on the same client yields `Unavailable_Or_Retryable`. It is deterministic and needs no unusual input; it needs only a server that answers `?torrent` with a transient error. The program scripts five exchanges and demonstrates both sides in one run: a well-formed `503 SlowDown` and a `500 InternalError` answered to `Get_Torrent` (asserted `Unavailable_Or_Retryable`, both failing), a `404 NoSuchKey` answered to `Get_Torrent` (reported only), the identical `503 SlowDown` answered to `Get_ACL` (control, passes with `Unavailable_Or_Retryable`) and a `200 OK` torrent body (control, passes).

**Notes:** The `404` label is a deliberate, tested choice — `tests/src/s3_get_object_torrent_socket_corpus.adb:703` asserts `No_Failure` for a `404` rejection, and for a `404 NoSuchKey` the enum's own text ("conclusively failed") arguably admits it — which is why the program asserts only the `500` and `503` cases and merely reports the `404` one. No test covers a well-formed retryable rejection on this path: that corpus's only `500` scenarios are a malformed error body and an over-limit error body, both of which take the `Response_Invalid` path instead, so the retryable statuses can be corrected without contradicting a test. There is no torrent certainty corpus and no torrent-specific policy in the `.ads`, so nothing documents a different domain for this operation. The maintainer decision is how far to align: the minimal fix maps only the six retryable status and code pairs, and the consistent fix reuses the sibling table whole, which would also change `404` to `Not_Found` and force the `:703` assertion to be updated.

## Coverage evidence: CLIENT-OBJECTS

- Probe `tests/repros/src/repro_client_objects_probe.adb`, exit status 0 (PASS): a `Content-Length` and body-length disagreement is handled cleanly by both `Get_Whole` overloads. Served a `200 OK` declaring `content-length: 64` with 100 body octets, the read is framed at the declared 64 octets and the excess is discarded, which is correct HTTP; served the same header with 32 octets followed by a close, the owned-bytes overload raises `Flyology.HTTP.Protocol_Error` ("peer closed before Content-Length was received") and the bounded overload produces `Whole_Get_Exchange_Failed` with `Corrupt_Or_Invalid_Response` and a zero-length destination. No unhandled exception and no partial body left readable. One contract note recorded as a documentation gap rather than a finding: `Protocol_Error` is the documented framing exception of the pinned `flyology_http_0.1.3_eb09a80a` `Read_All` (`src/flyology-http-client.ads:1174`), while `src/flyology-object_storage-client-objects.ads:3231-3233` names only `Response_Too_Large` and `Low_Level.Invalid_Response` for a larger or malformed successful body; propagating the transport and framing exception class is consistent with `docs/architecture/client-objects.md:66-68`. Whether an over-long body desynchronises a *reused* connection was not covered and belongs to `flyology_http`, since the loopback helper closes the peer after each exchange.
- Range binding (`Bind_Response_Range` `:2327-2377`, `Range_Header` `:2311-2325`, `Valid_Range_Request` `:2302-2307`, `Complete_Range_Child` `:2502-2587`): a server that ignores `Range` and returns `200` with the full body is refused, an oversized body first fails as `Response_Body_Too_Large`, suffix, open-ended and bounded requests are resolved against the `Content-Range` total with `Resolve_Range` and the returned interval must equal the resolution, the received byte count must equal `Content-Length` and the ETag must equal the `If-Match` sent; the low-level `Valid_Content_Range` (`client-low_level.adb:5933-5979`) has already required strict digits and `First <= Last < Total` before this layer runs.
- Destination ownership and clearing for whole, range and torrent reads: the pinned `flyology_http` `Finish (…, Destination)` contract (`flyology-http-client.ads:1018-1033`) restores length zero on every non-success, so a transport failure, timeout, cancellation or `Response_Body_Too_Large` mid-body cannot leave partial bytes readable, and the Objects layer additionally clears on every invalid or rejected decode (`:2413`, `:2433`, `:2444`, `:2536`, `:2555`, `:2565`, `:2580`, torrent `:5361-5504`).
- Non-replay of mutations: the eight mutating operations implement `Operation_Request_Body_Source` and none implements `Rewindable_Request_Body_Source`, and `flyology_http` replays a streamed body only when the source is rewindable (`flyology-http-client.ads:502-506`, `:558-562`); the synchronous put overloads reject a rewindable source up front (`:690-694`), and source cursors are reset only at `Start_*`.
- Conditional put buffer ownership (`Start_Put` `:1996-2045`, `Finish` `:2198-2220`, `Finalize` `:1984-1994`): validation and signing precede `Move_From`, a failed start moves the token back and rolls the operation back, `Finish` checks `Same_Pool` and moves the token back before re-raising a saved exception, matching `.ads:294-305`; `Read_Now` (`:1823-1849`) never reads past the detached buffer.
- Certainty normalizers for put, delete, delete-objects, tagging, legal hold, retention and annotation deletion: an admission other than `Response_Observed` is always `Outcome_Unknown`, only exact modeled status and code pairs are conclusive, and the put table matches `tests/corpora/composable-client/put-certainty.tsv` row for row.
- Composable state machines, all 18 operations: the child is released exactly once on every path, `Clear_Prepared_Request` is guarded by `not Is_Active (Item.Child)`, `Response_Limit_Exceeded` becomes `Response_Sink_Failed` with the pre-`Finish` admission, saved exceptions are re-raised only from `Finish` after `Consume`, and a restart requires the same `HTTP`, `Destination` and `Cancellation` owners.
- Synchronous `Get_Whole` (`Whole_Get_Outcome` overload, `:889-978`): requires `200`, a strong quoted ETag and a present `Content-Length`, rejects `Content-Length > Maximum` before reading as documented at `.ads:3232-3233`, reads at most `Maximum` bytes and requires the received length to equal `Content-Length`; the `Response` local is a `Limited_Controlled` lease, so the early raise paths release it.
- Entity-tag validation (`Valid_Exact_Entity_Tag` `:96-119`), `Timestamp` (`:83-94`), `Apply_Complete_Put_Options` (`:542-671`) and the HeadObject sink (`Write` `:2906-2918`, any body octet on a HEAD is refused as `Response_Sink_Failed`) were each checked against their specifications and match.
- Verifier measurements with no finding: the control legs of `repro_client_objects_1` and `repro_client_objects_2` show that adding only `x-amz-version-id: null` to otherwise identical responses turns every failing leg green, so status, ETag and `Content-Length` checks are not what fires; `repro_client_objects_3`'s `Get_ACL` leg shows the sibling normalizer classifying the identical `503`.

## Observations not counted: CLIENT-OBJECTS

- `Normalize_Put_Response` (`:1708-1792`) treats every modeled rejection outside its table, for example `404 NoSuchKey` or `400 BadDigest`, as `Outcome_Unknown` with `Corrupt_Or_Invalid_Response`. This is the maintained policy of `tests/corpora/composable-client/put-certainty.tsv` ("status alone does not prove semantic rejection"), so it is a documented limitation; the `Failure` label is unflattering for a well-formed S3 error whose code is simply not in the put table, and it forces a reconciliation read after, for example, a `Put_If_Matches` on an absent key.
- Whole and range reads bound the entire response body, error XML included, by the destination capacity, which `src/flyology-object_storage-client-objects.ads:442-443` states ("Destination capacity is the response body bound"). A tight destination therefore reports a large `NoSuchKey` error body as `Response_Too_Large` and hides the S3 code. Real, but specified; a documented limitation.
- `Failed_Reason` (`:32-46`) maps `Response_Body_Too_Large` to `Response_Too_Large` while the mutation normalizers override it to `Corrupt_Or_Invalid_Response` (`Normalize_Get_Object_ACL_Failure:4943-4962` and peers). Only the bounded-buffer reads can receive that HTTP result, so no caller can observe the divergence today; a latent inconsistency worth a comment, not a defect.
- `Bind_Response_Range` rejects `Content-Range: bytes a-b/*`, but `client-low_level.adb`'s `Valid_Content_Range` rejects the `*` total first and S3 always sends the total, so there is no reachable effect.
- The ListObjects v1 marker fallback uses the last `Contents` key when `NextMarker` is absent on a delimiter listing (`:391-416`). It is reached only for a truncated page, prefers `NextMarker`, and raises `Invalid_Response` rather than looping when a truncated page has neither; S3 requires `NextMarker` whenever a delimiter is used, so this is a server-deviation path only.
- `Singleton_Header` in `Get_Object_ACL` (`:4980-4998`) and `Delete_Object_Annotation` (`:6924-6944`) refuses a present but empty `x-amz-request-id:` or `x-amz-id-2:` value. Both return `""` for `Count = 0`, so an *absent* header is accepted and this is not another instance of the CLIENT-OBJECTS-1 and CLIENT-OBJECTS-2 class; no observed server sends an empty id header.
