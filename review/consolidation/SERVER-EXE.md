### SERVER-EXE-1: administrator login runs 600,000 PBKDF2 iterations on the shared cooperative event loop and stalls the S3 listener

**Severity:** P1 (the discovery report said P1, unchanged, and the verifier raised its confidence from Medium to measured). The single-login case is a wrong result on valid input via a reachable path with the default configuration, which is P1. It is not P0: the stall terminates, so it is starvation rather than a hang or deadlock; it falls into none of the P0 security categories, with no signature bypass, traversal, credential exposure or authorisation bypass; and the unbounded-starvation variant needs a local process that can reach the loopback-only management port.

**Location:** `server/src/flyology_object_storage_server_runtime.adb:432-441` (`Login` calls `Admin_Credentials.Verify` inline in the handler), `:187-190` (the S3 listener instantiates `Flyology.IO.Structured_Servers` with `Handler_Model => Flyology.Lightweight_Task`) and `:853-858` (the management listener does the same, `Server : aliased Structured.Server (Capacity => 32)`); `server/src/flyology_object_storage_server_credentials.adb:16` (`Work_Factor : constant Positive := 600_000;`), `:134-145` (the derivation loop: no `delay`, no I/O, no `Cancellation.Requested` poll) and `:325-344` (`Verify` derives first and then compares in constant time, so a wrong password costs the same as a right one) with the length and user gate at `:329-333`; the handler-model contract at `/Users/yrashk/.local/share/alire/builds/flyology_0.1.1_7be049fc/5e4ec5d2d7fb582d5512843a434aaaa816073423e6241e0ce95898ea1d152ad2/src/platform/darwin/flyology.ads:21-26` and the pool-size contract at `.../src/flyology-execution_groups.ads:154-158`; the handler requirement at `flyology-io-structured_servers.ads:100-105`; the documented listener coupling at `server/README.md:8-12`; the existing coverage at `server/tests/scripts/test.sh:102-117` and the `env -i` launches at `:388-392,462-471`.

**Repro:** `tests/repros/shell/repro_server_exe_1.sh`, exit status 1, one failed expectation. It starts the server itself on a fresh temporary root under `/private/tmp/claude-501/` with `env -i`, `FLYOLOGY_S3_PORT=0 FLYOLOGY_ADMIN_PORT=0` and the memory backend, reads the two `READY` ports and the `BOOTSTRAP ADMIN` password from the server's own output, then times three signed SigV4 `ListBuckets` requests with no other traffic, three logins on their own, and three signed S3 requests each issued 0.15 s into a valid login, with a plain TCP connect alongside. It fails when the worst concurrent S3 latency exceeds `max(10 x worst baseline, 0.050 s)`, the floor keeping sub-millisecond scheduling noise from tripping the ratio, and it always stops the server. The control re-issues the same signed request with no login in flight.

**What is wrong:** Both HTTP listeners run their handlers as Flyology lightweight tasks, and with the shipped default of one shared execution group every handler for both listeners is multiplexed onto a single event-loop thread. `Login` performs a 600,000-iteration PBKDF2-HMAC-SHA256 derivation inline in its handler, and that loop contains no I/O, no delay and no `Cancellation.Requested` poll, which is exactly the CPU-only case `Structured_Servers` requires handlers to break up. The event loop therefore cannot run any other handler for the roughly one second the derivation takes, so every in-flight and newly accepted S3 request waits behind it. Measured against the built binary: the signed S3 baseline with no other traffic is **0.002 s** (three runs, 0.002/0.002/0.002, status 200, 184 bytes); the same signed request issued 0.15 s into a single valid administrator login takes **0.771–0.876 s** (the recorded runs are 0.863, 0.849 and 0.771, worst 0.863 s), a factor of about 350; one login on its own costs **0.99–1.07 s** of CPU (runs 1.001, 1.067, 1.074, and a wrong-password login measured at 0.994 s, because `Verify` derives before it compares); ten simultaneous logins starve one S3 request for **10.2 s** (`t+1 s3=10.201 200 184`, flood wall 10.50 s, min 1.10 s, median 6.40 s, max 10.50 s, with zero 429 or 503); and fifty simultaneous logins hold the management listener for **51 s** and cause 1–3 of the 50 connections to be closed with no response at all. The plain TCP connect always completes in 0.001 s, because the kernel's accept queue absorbs the connection, so a health check that only opens a socket does not see the outage and only a request that needs a response does. Anyone running the server hits the one-second version on every workbench sign-in; the unbounded version needs only a local process that can open the loopback management port and post form bodies, with no session, no credential and no rate limit (SERVER-EXE-2), and it also drops connections outright once the queue exceeds the 30 s request timeout. It is fully deterministic.

**Notes:** Five refutation attempts failed. A wrong password does not short-circuit before the derivation: `credentials.adb:329-333` rejects a wrong `User` and a `Password'Length` outside `1 .. 64` first, but `Login` reaches `Verify` only with a 48-character password, so every attempt pays the full cost, measured at 0.994 s. The two listeners are not on different execution groups: both use the default `Handler_CPU`, so both are placed by the same automatic pool. The pool is not larger than one by default, and raising it does not remove the coupling — with `FLYOLOGY_LOOP_POOL_SIZE=8` against the same binary a **single** concurrent login costs the S3 probe nothing (0.002 s, login 1.001 s), but **ten** concurrent logins still stall an S3 request for **0.774 s** and the flood's wall time only falls from 10.5 s to 2.13 s, so the pool size raises the number of simultaneous derivations needed to starve the loop from one to the pool size and nothing more; the executable never grows the pool (`rg 'Grow_Configured_Pool'` over `server/`, `src/`, `sqlite/` and `tests/` finds no call site), the variable is not mentioned in `server/README.md`, and `server/tests/scripts/test.sh:388-392,462-471` launch the server with `env -i`, so the shipped default is one. It is not documented: `server/README.md:8-12` couples the two listeners only through supervision order ("The management child depends on the S3 child, so an S3 generation failure restarts the workbench generation as well") and no document says a workbench sign-in pauses S3 service. And no existing test would catch it: `server/tests/scripts/test.sh` issues its three logins sequentially with `sleep 1` between them and never runs S3 traffic concurrently with a login, while nothing in CI runs the lightweight handler model at all (see the observations below). A fix needs a maintainer decision this review cannot make: either the derivation moves off the cooperative loop (a `Flyology.Native_Task` handler model, or an explicit worker for password verification), or the loop is broken up with a cooperative yield and a cancellation poll, or the executable grows the automatic pool at startup — the last of which introduces a new public policy value, a pool size, under the "Ada interface values" and "Decision authority" rules, and would only raise the threshold rather than remove it, as the `FLYOLOGY_LOOP_POOL_SIZE=8` measurement shows. SERVER-EXE-2 is what leaves this path with no admission bound at all, so the two are best read together.

### SERVER-EXE-2: management route `Concurrency`/`Rate_Per_Second` policies are inert

**Severity:** P2 (the discovery report said P2; unchanged). The library explicitly calls the consuming layers optional — `flyology-http-server-routing.ads:81`, "Route-local policy consumed incrementally by **optional** toolkit layers" — so this is not a violation of a library contract, and `server/README.md` promises no rate limit. What is wrong is that the server declares admission policy on five routes and never enforces it, and that `server/tests/scripts/test.sh` paces itself as though the limit existed.

**Location:** `server/src/flyology_object_storage_server_runtime.adb:882-887` (the `/api/login` registration with `Body_Handling => Apps.Buffer_Body, Max_Body => 256, Concurrency => 1, Rate_Per_Second => 2`), with the same shape on `/api/buckets` (GET and POST), `/api/objects`, `/api/buckets/delete` and `/api/logout` at `:888-918`; `:846-850`, where `Handle` calls `State.Routes.Serve` directly and `grep -rn -i 'middleware|bulkhead|rate_limit' server/src/` returns nothing (exit 1); the policy fields and "A zero concurrency or rate value means unlimited" at `flyology-http-server-routing.ads:81-89`; the unused consumer at `flyology-http-server-middleware_rate_limits.ads:24-25` ("Token-bucket middleware. Burst capacity equals the configured route requests-per-second rate. Rejection is 429 with Retry-After."); the maintained test's pacing at `server/tests/scripts/test.sh:102-117`.

**Repro:** `tests/repros/shell/repro_server_exe_2.sh`, exit status 1, two failed expectations. It starts the server on a temporary root, fires 50 barrier-synchronised `POST /api/login` requests with a wrong 48-hex password from one peer, tallies the outcomes and `Retry-After` headers, and asserts that some are rejected with 429 or 503 and that at most the declared burst of 2 is admitted. Control: one wrong-password login on its own is answered 401, so the request shape is right and the flood measured real handler work.

**What is wrong:** Five management routes carry `Concurrency` and `Rate_Per_Second` values, but the router is served with no middleware, so the only readers of those fields, `Middleware_Rate_Limits` and `Middleware_Bulkheads`, are never instantiated and every management request from every peer is admitted up to the listener's 32 handler slots. Of 50 simultaneous `POST /api/login` attempts with a wrong password, **49 were run to completion** and answered 401, each paying a full 600,000-iteration derivation, 1 failed as a transport error (`RemoteDisconnected`), and **zero** received 429 or 503; the flood's wall time was **51.66 s**, min 1.05 s, median 27.08 s, max 51.66 s. The declared policy is `Concurrency => 1, Rate_Per_Second => 2`, whose token bucket has a burst capacity equal to the rate, so at most 2 should have been admitted. On its own this is a documentation-versus-code discrepancy; combined with SERVER-EXE-1 it is what removes any admission bound from the expensive login path, and it also means the `Concurrency => 1` intended to serialise bucket create and delete is absent, though the backends' own atomic primitives still make those operations safe.

**Notes:** Three refutation attempts failed. The router does not enforce the policy itself: no counter or bucket exists in `routing.adb` outside the middleware packages, and `Configure_Route` only stores the values. The burst did not merely happen to fit under the limit: the flood is barrier-synchronised, so all 50 requests are outstanding simultaneously, and 47–49 were nonetheless served. And the effective serialisation is not equivalent to a limiter: the requests are serialised by the single event loop of SERVER-EXE-1, so all of them run and the burst takes about 51 s of CPU instead of being rejected in milliseconds. An earlier run of the same script against the same server showed `47 x 401` and `3 x transport-error RemoteDisconnected`; the split between answered and dropped connections varies, the zero limiter rejections do not. Nothing in `server/tests/scripts/test.sh` asserts a 429 or 503, and its `sleep 1` between mutating requests passes with or without the limit, so no existing test changes with the fix. A fix needs a maintainer decision on the client key policy and the retained-key capacity that `Middleware_Rate_Limits` takes as generic formals; both are new externally visible resource choices under the "Decision authority" rule.

### SERVER-EXE-3: any `FLYOLOGY_OBJECT_STORAGE_ROOT` is handed to `Files.Open`/`SQLite.Open`, which delete `<root>/tmp`, `<root>/staging` and unreferenced `<root>/objects` files with no layout check

**Severity:** P2 (the discovery report said P2; unchanged). The data destroyed is never the store's own acknowledged writes, and it needs a root that is not a dedicated directory, which the rubric puts at P2, "edge-case incorrectness … needing unusual input". It sits at the top of that band: the destruction is silent, irreversible, and reached through one documented variable whose documentation states no dedicated-directory precondition.

**Location:** `server/src/flyology_object_storage_server_configuration.adb:42-45`, where the only check on the root is `Root'Length = 0` for non-memory backends; `server/src/flyology_object_storage_server.adb:64-68,78-82`, which pass `US.To_String (Settings.Storage_Root)` straight to `Files.Open` and `SQLite.Open` with no further validation; `src/flyology-object_storage-backends-files.adb:3514-3573` (`Open`) and specifically `:3548-3564`, which checks that the root is not a symlink and is a directory, creating it if absent, then for `<root>/tmp` checks not-a-symlink, is-a-directory, `Validate_Tree_Symlink_Free`, `Ada.Directories.Delete_Tree`, with nothing looking for a store marker or refusing a non-empty foreign directory; `src/flyology-object_storage-backends-files.adb:364-365`, where `Temp_Path` is exactly `<root>/tmp`, so the swept directory is the store's staging area; `sqlite/src/flyology-object_storage-backends-sqlite.adb:304-305`, the `Clean_Directory` calls over `<root>/staging` and `<root>/objects`; the documented precondition at `docs/architecture/files-layout.md:3` and `:66`; the variable's documentation at `server/README.md:64`; the existing coverage at `server/tests/scripts/test.sh:458-471`.

**Layout marker:** there is none. `docs/architecture/files-layout.md` was read in full and grepped for `marker|\.flyology|layout file|sentinel` with no match. The document states the precondition on the operator — "The files backend requires exclusive ownership of its configured root by one process" at line 3, and "opening the exclusively owned root removes interrupted staging artifacts" at line 66 — but defines no on-disk marker that `Open` could check, and `server/README.md:64` documents the variable as "mandatory for files and SQLite" without the precondition. The SQLite root's `catalog.sqlite3` and `.flyology-object-storage.lock` are created, not required, so they are not a marker either.

**Repro:** two programs, at both levels. The cheaper one is `tests/repros/src/repro_server_exe_3.adb`, exit status 1, two failed expectations: it creates a scratch directory with `tmp/keep.txt`, `tmp/nested/deep.txt` and `notes/readme.txt`, runs a control on a dedicated empty root (open plus create a bucket, which succeeds), then calls `Files.Open` on the foreign directory and asserts that `Open` either raised `Configuration_Error` or left the sentinels in place; `Open` returns normally, `tmp/keep.txt` and `tmp/nested/deep.txt` are gone, and `notes/readme.txt` survives. The second is `tests/repros/shell/repro_server_exe_3_server.sh`, exit status 1, four failed expectations, which drives the real executable through the documented variable for both backends: pointed at a files root holding `./notes/readme.txt`, `./tmp/keep.txt` and `./tmp/nested/deep.txt`, the server prints both `READY` lines and the root afterwards holds only `./notes/readme.txt`; pointed at a SQLite root holding `./notes/readme.txt`, `./objects/keep.txt` and `./staging/keep.txt`, the server prints both `READY` lines and the root afterwards holds `./.flyology-object-storage.lock`, `./catalog.sqlite3` and `./notes/readme.txt`.

**What is wrong:** `Configuration.Load` accepts any non-empty string as the storage root, and the executable passes it straight to the backend's `Open`, which treats the directory as a store it owns: the files backend recursively deletes `<root>/tmp`, and the SQLite backend deletes every ordinary file under `<root>/staging` and every ordinary file under `<root>/objects` that the freshly created catalog does not reference. Neither backend looks for any marker distinguishing a real store from an arbitrary directory, and no diagnostic is printed — the server prints `READY` and serves normally. An operator who mistypes the root (`/var` for `/var/lib/flyology`, a home directory with a `~/tmp`, a checkout with a scratch area) loses that content silently and irreversibly. On the macOS test host `/tmp` and `/var` are symlinks and are refused, so a Linux deployment is the exposed case. It is deterministic.

**Notes:** Shared responsibility. The destructive code belongs to the FILES and SQLITE backends (`src/flyology-object_storage-backends-files.adb:3548-3564`; `sqlite/src/flyology-object_storage-backends-sqlite.adb:304-305`); the reachable path from a documented, unvalidated configuration variable belongs to the executable (`server/src/flyology_object_storage_server_configuration.adb:42-45` and `server/src/flyology_object_storage_server.adb:64-68,78-82`). A fix could sit in either layer — an `Open` that refuses a non-empty directory without a layout marker, or an executable that validates the root before opening — and choosing between them, plus choosing whether to introduce a marker file, is a maintainer decision under "Decision authority", since a marker is a new on-disk artefact and a new externally visible precondition. Four refutation attempts failed: `Validate_Tree_Symlink_Free` does not protect a foreign tree, raising only for symlinks, non-ordinary files or depth above 64, and a sentinel tree of two ordinary files in two ordinary directories passed and was deleted; the sweep is not wider than the store's own directories, because the control shows `<root>/notes/readme.txt` surviving both backends, which is precisely what makes the loss invisible to an operator inspecting the rest of the root; the executable does not refuse a root it did not create, since both backends printed `READY` on the foreign roots; and no existing test covers it, because `server/tests/scripts/test.sh:458-471` always uses a fresh `$RUN_ROOT/<backend>-store` and no test points a store at a directory holding foreign content. SERVER-EXE-5 is adjacent but distinct and is counted separately: this finding is about a directory that was never a store, that one about a directory that is a store and is currently owned by a live process.

### SERVER-EXE-4: supervisor termination diagnostics are discarded

**Severity:** P2 (the discovery report said P2; unchanged). Wrong diagnostics on a valid and common input, a port already in use; no wrong data and no unsafety.

**Location:** `server/src/flyology_object_storage_server_runtime.adb:1075-1080`, where the report is `"object-storage server stopped: " & Result.Outcome'Image` and `Result.Termination` and `Result.Child` are never read; `:920-924`, where the management `Bind_Socket`/`Listen_Socket` have no handler, so `Socket_Error` escapes the generation; `flyology-supervision.ads:167-177,405-411`, where `Supervisor_Result` carries `Child`, `Generation` and a `Termination_Summary` with the exception id, exception name and up to 512 characters of message; the exception-swallowing handler at `runtime.adb:1082-1089`; the contrasting pre-supervisor path at `server/src/flyology_object_storage_server.adb:92-98`, which does print `Exception_Information`; the existing coverage at `server/tests/scripts/test.sh:343-385` (`expect_startup_failure`); the configuration gap at `server/src/flyology_object_storage_server_configuration.adb:66-70`, which validates neither port availability nor equal S3 and management ports.

**Repro:** `tests/repros/shell/repro_server_exe_4.sh`, exit status 1, one failed expectation. It holds a loopback port with a `python3` listener, starts the executable with `FLYOLOGY_ADMIN_PORT` set to that port, captures stdout and stderr, and asserts that the failure diagnostic names at least one of the failing child, the endpoint, or the exception. The diagnostic under test is exactly `object-storage server stopped: STARTUP_FAILED`; it names the failing child, no; the endpoint `127.0.0.1:53658`, no; the exception, no. Controls, all passing: the exit status is non-zero (1), the executable does report that the server stopped, and a pre-supervisor configuration failure does name its cause (`raised CONSTRAINT_ERROR : FLYOLOGY_OBJECT_STORAGE_BACKEND must be memory, files, or sqlite`).

**What is wrong:** When a child generation terminates with an exception during startup, `Flyology.Supervision.Static` copies the child's identity and a 512-character termination summary into `Supervisor_Result`, but the executable prints only `Result.Outcome'Image`. The exception never reaches GNAT's unhandled-exception reporter either, because the runtime's task termination hook captures it, so the operator gets one enumeral for every distinct failure: a port in use, a permission problem, a duplicated `FLYOLOGY_S3_PORT`/`FLYOLOGY_ADMIN_PORT` pair, or an exhausted restart budget all read as `STARTUP_FAILED` or `RECOVERY_EXHAUSTED`. The misleading half is visible in the reproduction output: the S3 child had already printed `READY s3 http://127.0.0.1:53670`, so an operator reading the output sees a successful listener followed by an unexplained `STARTUP_FAILED`. Anyone starting the server on a busy port hits it, and it is deterministic.

**Notes:** Three refutation attempts failed. `Exception_Information` does not reach stderr through the main procedure: `Runtime` catches everything at `runtime.adb:1082-1089` and returns normally, so main's handler is not involved for supervisor outcomes, and the control at the end of the program confirms the contrast, a pre-supervisor configuration failure naming its cause. The "admin" text that appears in the output is not a diagnostic: it is the `BOOTSTRAP ADMIN` banner and the credentials path, printed on every run, which is why the program scopes its assertion to the `object-storage server stopped:` line and everything after it — an earlier draft of the script matched the banner and produced a false PASS, and the scoped version is the one reported here. And `Configuration.Load` does not reject the conflict earlier, validating neither port availability nor equal ports (`configuration.adb:66-70`), so the supervisor is the first place the conflict is seen. `server/tests/scripts/test.sh:343-385` asserts only a non-zero exit and every case it runs fails before the supervisor starts, where `server.adb:92-98` does print `Exception_Information`, so no existing test asserts the wrong behaviour and none must change. A fix is a formatting decision — which of `Child`, `Generation`, `Termination.Exception_Name` and `Termination.Message` to print, and whether the child ids get names — rather than a new interface value, so it does not need a "Decision authority" ruling.

### SERVER-EXE-5: the executable enforces the documented exclusive-root precondition for SQLite but not for files

**Severity:** P2 (new; the verifier raised it from the discovery report's observations list, where the missing files-root lock was recorded and deferred to the FILES area). The deterministic part is the missing enforcement and the emptying of a live process's staging directory; the harmful part, destroying a staging file the first process is actually mid-way through writing, requires a timing race that was not demonstrated, and the destroyed data would be transient staging rather than acknowledged writes. It is not P1 because the exclusive-ownership statement in `docs/architecture/files-layout.md` is a precondition on the operator rather than a promise by the code; the verifier recorded that a maintainer who reads the SQLite backend's `flock` as establishing that enforcement is the contract would reasonably raise it to P1.

**Location:** `src/flyology-object_storage-backends-files.adb:3514-3573` (`Open` takes no lock of any kind; the only guards are symlink and directory-kind checks); `src/flyology-object_storage-backends-files.adb:364-365` and the 18 uses of `Temp_Path (Item)` in the same body, with bucket-creation staging at `:3606` and publication staging at `:3902`, `:4142`, `:4388`, `:4686`, `:5195` and `:6122`, so `<root>/tmp` is the live staging target of ordinary operations rather than a startup-only directory; the multipart tree that is not swept, `files.adb:402-403,524-530`; the contrasting SQLite enforcement at `sqlite/src/flyology-object_storage-backends-sqlite.adb:107-125` (`Acquire_Root_Lock`), called from `Open` at `:301-302`, taking `flock(LOCK_EX|LOCK_NB)` on `<root>/.flyology-object-storage.lock` and raising `Configuration_Error : could not acquire exclusive SQLite backend root lock`; the documented preconditions at `docs/architecture/files-layout.md:3` ("The files backend requires exclusive ownership of its configured root by one process") and `README.md:36` ("one process owning an exclusive storage root").

**Repro:** `tests/repros/shell/repro_server_exe_5.sh`, exit status 1, two failed expectations. It starts server 1 on a fresh files root, places a sentinel inside the live `<root>/tmp/`, starts server 2 on the same root, and asserts that server 2 is refused or that the sentinel survives. Server 2 reached `READY` (both lines), server 1's `tmp/owner-staging.tmp` did not survive, and server 1 was still alive. The sentinel stands in for server 1's transient staging artefacts and is created by the script — the program says so in its header, and it does **not** claim to have destroyed a real in-flight staging file. Control, passing: the identical two-process attempt on a SQLite root is refused, and the refusal names the reason (`raised FLYOLOGY.OBJECT_STORAGE.BACKENDS.SQLITE.CONFIGURATION_ERROR : could not acquire exclusive SQLite backend root lock`).

**What is wrong:** The server executable offers one `FLYOLOGY_OBJECT_STORAGE_ROOT` variable for both persistent backends, and the exclusive-ownership precondition the architecture documents is enforced for exactly one of them. Pointing a second server at a live files root — a restart that overlaps the old process, a misconfigured supervisor unit, an operator running a second instance for a different port — succeeds silently, and the second `Open`'s `Delete_Tree` of `<root>/tmp` removes whatever the first process has staged there at that instant. Ordinary publication paths stage in exactly that directory, so a concurrent PUT, tag replacement, bucket creation or multipart completion can lose its staged record and fail, or at the margins leave the first process to `Sync_Directory` a directory that was replaced underneath it. The narrow, timing-dependent nature of the harm is why this is P2 rather than higher, and it is why the deterministic part of the reproduction is the missing refusal rather than a corrupted object.

**Notes:** Shared responsibility with the FILES and SQLITE areas: the asymmetry is between the two backends' `Open` (`files.adb:3514-3573` takes no lock; `sqlite.adb:107-125` `Acquire_Root_Lock`, called from `Open` at `:301-302`), while what belongs to this area is that the executable offers one variable for both and enforces the documented precondition for only one of them. Four refutation attempts failed. The harm is not confined to startup: `Temp_Path` is the staging target of every publication path listed in the Location field, so the swept directory is in use for the whole lifetime of the first process. In-flight multipart state is not destroyed too, which would have made it worse: uploads live under `buckets/<bucket>/multipart/` (`files.adb:402-403,524-530`), which the sweep does not touch, and that bound on the damage is why the severity is P2 rather than P1. The executable does not refuse the second start for another reason, since the second server printed both `READY` lines while the first was still alive. And it is not the same defect as SERVER-EXE-3: that one is about a directory that was never a store, this one about a directory that is a store, currently owned by a live process, and the asymmetry with the SQLite backend is what makes it a defect rather than a design choice. `server/tests/scripts/test.sh` never runs two servers on one root, so no existing test changes with the fix. A fix is a maintainer decision on mechanism: the files backend could take the same `flock` the SQLite backend already takes, at the cost of making the files backend depend on a lock file inside its root, which is a new on-disk artefact and a new failure mode on filesystems without working advisory locks.

## Coverage evidence: SERVER-EXE

- Two questions the discovery's earlier pass left open were resolved in the same discovery report and neither is a finding. Shutdown classification: `Static.Request_Stop` (`static.adb:823-851`) moves the phase to `Stopping_Children` at once and fixes the terminal outcome at `Shutdown_Completed`, and every later generation termination, whatever its `Kind`, only advances the stop order (`static.adb:741-742`), so a SIGTERM during startup — including the window where `Mark_Ready` would raise `Program_Error` "after stopping begins" (`supervision.ads:304-309`) — and a deferred `Server_Failed` raised by `Structured_Servers.Serve` at stop (`structured_servers.adb:536`) both end with exit status 0. Handler exceptions during shutdown: resolved by the same classification, and no reachable handler exception escapes to `Structured_Servers` in the first place.
- Credential bootstrap in C (`..._credentials_native.c`): CSPRNG source (`arc4random_buf`/`getrandom` with EINTR retry), 24 random bytes to 48 hex characters (192 bits), 32-byte random salt; the temp file is created with `O_WRONLY|O_CREAT|O_EXCL, 0600` before any write, fully written and `fsync`ed, published by `link()` that never replaces an existing name (EEXIST makes the caller reload the racing process's file), with a parent-directory `fsync` and a distinct status when only cleanup failed so the password is still revealed.
- `Secure_File`: `lstat` rejects symlinks and directories as non-regular, the effective uid must own the file and the mode must be exactly `0600`; the TOCTOU window between the check and `Ada.Text_IO.Open` needs directory write access by an attacker who could equally pre-create the file, which then fails the uid check.
- Credential file `Load`: fixed 160-character single line, `File_Prefix` pinning version, username and iteration count, lowercase-hex-only decoding, more than one line rejected; GNAT 15.3.1 `Index` (Forward) with `From` past the end returns 0 through a null slice and raises `Index_Error` only for `From < Source'First` (`a-strsea.adb:610-621`), so short lines hit the length check.
- PBKDF2-HMAC-SHA256 `Derive` (single block, `INT(1)` big-endian, XOR chain) and its iteration-1 self-test vector `120fb6cf…0be17b`, confirmed with `python3` to equal `hashlib.pbkdf2_hmac('sha256', b'password', b'salt', 1, 32)`; constant-time comparisons for the verifier and session tokens; work factor 600,000 matching the OWASP figure the README cites. The work factor itself is correct and is not what SERVER-EXE-1 is about.
- Plaintext lifetime: `Password`, `Password_Bytes`, `Salt`, `Derived`, `U`, `Next`, `Candidate`, the HMAC context and the session `Token` are wiped on normal and exceptional paths; the password is printed exactly once, only when `Generated`, only to standard error (`server.adb:31-42`), and no other `Put_Line` in `server/src`, `src/flyology-object_storage-server*.adb` or the HTTP server library prints request material.
- Sessions and cookies: 32 random bytes to 64 hex (256 bits), 12-hour absolute expiry, slot reuse only of unoccupied or expired entries with oldest-expiry eviction when all 64 are live, `Revoke` wipes; `HttpOnly; SameSite=Strict; Path=/; Max-Age=43200` with no `Secure` (documented, loopback HTTP only) and `Max-Age=0` on logout; a single `Cookie` header is required and duplicate `flyology_admin` pairs fail closed.
- CSRF and rebinding: `Local_Request` compares the parsed request authority with the exact bound loopback authority; mutations require an exact `Origin`; login and logout accept an absent `Origin` for non-browser clients but reject a mismatching one; every `/api/*` route checks `Local_Request` and `Authenticated` (or `Same_Origin`/`Strict_Same_Origin`) before touching the backend.
- Asset serving: three fixed routes with no path parameter, contents read once at startup and SHA-256 pinned against compiled digests, the three pinned digests confirmed byte-for-byte equal to the SHA-256 of the shipped files; `FLYOLOGY_ADMIN_ASSET_ROOT` changes only where assets are read from, not what is served.
- Response and error surface: `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, a CSP of `default-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'self'`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and `Cross-Origin-Resource-Policy: same-origin` on every handler response; JSON bodies escape `"` and `\` and map control characters, object keys are emitted URI-encoded, and `app.js` uses `textContent` only; error responses are fixed JSON tokens and a fixed 421 text, with no paths or exception text reaching the client.
- Bounded bodies and ingress budget: login 256 bytes, create and delete 68 bytes, GET routes reject bodies, a 4 KiB shared ingress budget, 30-second request and 5-second header timeouts on the management listener.
- Configuration validation other than the storage root: the backend name is lower-cased and closed, the bind address must be numeric IPv4, ports go through `Port'Value` in 0 .. 65535, capacity is 1 .. 4096, AWS credentials are required as a complete non-empty pair with the session token only alongside them, and the region is length- and scope-segment-validated. The management listener is hard-bound to `Loopback_IPv4` (`runtime.adb:920-924`) and no option can move it.
- Signals and lifecycle: the SIGTERM handler is a protected `Attach_Handler` that only latches a flag, a stop latched before `Supervisors.Run` is sticky, the supervisor stops the dependent management child first, each child stops accepting and drains (2 s and 10 s) before forced cancellation, the 12 s grace exceeds the drain, `Shutdown_Completed` yields exit 0 and any other outcome or exception sets a failure exit status, the files and SQLite `Store` is a block-local object finalised after `Run` returns on every path, and the SQLite root lock is an OS lock released on process death. SIGPIPE is suppressed at the socket layer.
- Restart behaviour: `On_Failure` with bounded default recovery limits (3 per 5 s, 10 per incident, 60 s), so a port already in use ends in `Startup_Failed` or `Recovery_Exhausted` rather than an infinite loop; the missing cause text is SERVER-EXE-4. `Structured_Servers.Serve` always closes the transferred listener.
- Handler exception containment: `Routing.Serve` answers any escaping management-handler exception with a plain 500 and keeps the connection loop; `Connection_Handlers.Serve` absorbs transport, timeout, payload and protocol exceptions around both the read and the `Handle` call; the S3 application's `Handle` ends in a `when others` that answers 500 `InternalError` or marks a started response failed. Only `Operation_Cancelled` reaches `Structured_Servers`, where it is counted as cancelled rather than failed, so `Server_Failed` is not reachable from S3 or management traffic.
- Management continuation tokens: `Core.Valid_Listing_Continuation_Syntax` (`core.adb:8-24`) enforces a 70-character minimum, an even remainder and a maximum before `Decode_Continuation` indexes `Raw (Digest_Last + 1)`, and `Listings.Decode_Continuation` (`src/flyology-object_storage-s3-listings.adb:329-376`) returns `Valid => False` for malformed input and contains no `raise`, so the `token` query parameter cannot make `Object_Inventory` raise.
- Credential path versus store layout: buckets live under `<root>/buckets/` and staging under `<root>/tmp/` (files) or `<root>/objects/`, `<root>/staging/`, `catalog.sqlite3` and `.flyology-object-storage.lock` (SQLite), so the default `<root>/admin.credentials` is neither enumerated as a bucket nor swept at `Open`, including on the SERVER-EXE-3 path.
- Verifier measurements with no finding: the plain TCP connect alongside every stalled S3 request in `repro_server_exe_1.sh` completes in 0.001 s, showing the outage is invisible to a socket-only health check; the `FLYOLOGY_LOOP_POOL_SIZE=8` run shows the coupling surviving a larger pool; the `notes/readme.txt` control in both SERVER-EXE-3 programs shows the sweep confined to the store's own directories; and the SQLite control in `repro_server_exe_5.sh` shows the enforcement that the files backend lacks.
- Process hygiene: nothing tracked was modified during verification (`git status --short` shows only the untracked `review/`, `tests/repros/` and `sqlite/tests/repros/` trees), and every server process started was stopped (`pgrep -fl flyology_object_storage_server` returns nothing).

## Observations not counted: SERVER-EXE

- **Corrected by the verifier.** The discovery recorded that "With `FLYOLOGY_S3_BIND=0.0.0.0`, `SO_REUSEADDR` on the S3 listener lets another local user on BSD-derived kernels bind `127.0.0.1:9000` more specifically". The hijack is real but the stated mechanism is wrong. All four combinations were measured on this macOS host: wildcard `SO_REUSEADDR` True with specific True SUCCEEDED, wildcard True with specific False was refused (48 Address already in use), wildcard False with specific True SUCCEEDED, wildcard False with specific False was refused. Only the *attacker's* socket needs `SO_REUSEADDR`; the option the server sets on its own listener (`runtime.adb:214-215`) is irrelevant to the outcome, and the more-specific listener does receive the loopback connections, verified by accepting one. It is therefore a platform property of any wildcard bind on BSD-derived kernels, not something the server's socket options cause or can remove, and removing `SO_REUSEADDR` from the S3 listener would not help. It stays an observation about the documented `FLYOLOGY_S3_BIND=0.0.0.0` option on multi-user macOS hosts and is not a defect in the executable's code.
- Credential-file default drift, confirmed. `server/README.md:72-73` says the file defaults "to `admin.credentials` inside a persistent backend root, or `./flyology-admin.credentials` for memory"; `configuration.adb:47-54` uses `<root>/admin.credentials` whenever `FLYOLOGY_OBJECT_STORAGE_ROOT` is set, memory backend included. Documentation drift only.
- Main's handler does not cover its declarative part, confirmed. Running the built executable with `FLYOLOGY_OBJECT_STORAGE_BACKEND=not-a-backend` prints GNAT's `Execution of … terminated by unhandled exception / raised CONSTRAINT_ERROR : FLYOLOGY_OBJECT_STORAGE_BACKEND must be memory, files, or sqlite` with a traceback rather than the `object-storage server startup failed:` prefix, exit status 1. Fail-closed and the cause is named, so cosmetic; it is also the control that makes SERVER-EXE-4's silence a gap rather than a house style. Within `Load`, a non-numeric or out-of-range `FLYOLOGY_S3_PORT`, `FLYOLOGY_ADMIN_PORT` or `FLYOLOGY_S3_CAPACITY` is re-raised with GNAT's `'Value` or range-check text rather than a variable name, and based or underscored literals are accepted.
- `Local_Request` is a textual authority comparison, confirmed against a live server on port 64932: `Host: localhost:64932` receives `HTTP/1.1 421 Status` while `Host: 127.0.0.1:64932` receives `HTTP/1.1 200 OK`. Only hand-typed URLs are affected; the printed `READY` line gives the numeric form.
- The server crate is not built or tested in CI, confirmed. `grep -n 'server' .github/workflows/ci.yml` matches only lines 271 and 301, both about `tests/scripts/`, so nothing in the workflow builds `server/` or runs `server/tests/scripts/test.sh`; the lightweight handler configuration that produces SERVER-EXE-1, the management API, the credential bootstrap and the SIGTERM path are gated only by a local `alr test`. A process gap that belongs with the CI and baseline area rather than with this crate's code.
- The assets loader requires a working directory or `FLYOLOGY_ADMIN_ASSET_ROOT`, confirmed. `assets.adb:16-27` looks only at `./assets/index.html` and `./server/assets/index.html`, so started from any other directory the executable fails with `CONSTRAINT_ERROR : management assets not found`. Documented at `server/README.md:74-76` and fail-closed; every reproduction script above sets `FLYOLOGY_ADMIN_ASSET_ROOT` explicitly for that reason.
- `Assets.Read_All` rebuilds files through `Ada.Text_IO.Get_Line`, so the pinned digest is over a normalised image: a missing final newline is added and one trailing empty line is dropped. Only trailing whitespace of an asset can differ from the pinned bytes, and the served bytes equal the digested bytes, so the integrity of executable content is intact.
- Policy values, not counted as defects: memory store `Bucket_Capacity 256`, `Object_Capacity 100_000`, `Byte_Capacity` 16 GiB (`server.adb:52-54`), S3 handler timeout 60 s, 10,000 requests and 600 s per connection, management capacity 32, session capacity 64 and 12 h, bucket inventory 256, object page 64 and 128, drain 10 s and 2 s, grace 12 s, readiness 15 s, ingress budget 4 KiB, clock skew 900 s, torrent piece 256 KiB.
- Credential-file edge cases, all fail-closed: a zero-length file fails startup with `End_Error` from `Get_Line` instead of "invalid administrator credential file"; a directory at the path is reported as "must be owner-owned mode 0600"; `umask` bits in the owner triple make `open(..., 0600)` create a `0400` file that the next startup rejects, as does an operator `chmod 400`; and `link(2)` publication fails on filesystems without hard links, or against a stale `<path>.tmp.<pid>` from a crashed process with a reused PID.
- Password and secret copies survive on the secondary stack (the `Hex` result, the `"BOOTSTRAP … password=" & Password` concatenation, the `Set-Cookie` header string) after the named buffers are wiped; no reachable path exposes them. Bootstrap ordering also leaves a persisted credential whose password was shown once if a later configuration or bind failure occurs, which commit `4401e0e` already isolates in tests. With `AWS_ACCESS_KEY_ID` absent the executable prints `BOOTSTRAP S3 access_key=FLYOLOGYLOCAL secret_key=<64 hex>` to standard error on every start as the README documents, and the `S3_Secret_Key` constant is retained unwiped for the process lifetime alongside the provider's wiped copy.
- Same-site cookies: because `SameSite` treats every port of `127.0.0.1` as one site, a page on another loopback port can attach the session cookie to cross-origin requests; mutations require an exact `Origin`, login and logout reject a mismatching one, and the GET inventory routes are unreadable cross-origin.
- `Status` reports `s3_address` as bound, for example `0.0.0.0`, and `app.js:157` renders `http://0.0.0.0:<port>` as the copyable endpoint. Cosmetic.
- `Run_S3` does not close `Listener` when `Bind_Socket` or `Listen_Socket` raise before `Serve` takes ownership, so the descriptor leaks once per failed generation, bounded by the recovery limits at most ten per process; it is not separately reproducible without also triggering SERVER-EXE-4.
- A second SIGTERM re-latches the flag with no forced exit; SIGINT and SIGHUP take the default action and terminate without drain. Backends are crash-safe by design and the README documents only SIGTERM.
- Stop policy `Request_Abort => False` with a 12 s grace (`runtime.adb:989-992`): a handler that ignores cancellation for longer than the grace is classified `Stop_Timeout` then `Stuck`, and `Supervisors.Run` cannot return while the task is alive, so the process would not exit on SIGTERM. No reachable handler was found that blocks that long — the PBKDF2 derivation of SERVER-EXE-1 is far shorter and backend I/O observes the token — leaving a wedged disk as the only scenario, outside the executable's control.
- The S3 request deadline of 60 s is a monotonic deadline for each complete request including the streamed body, so a single-request upload or download needing more than 60 s over the configured link is cut; multipart clients are unaffected, and the in-tree harness uses the same value, so this is a consistent policy value rather than drift. During the 10-second S3 drain only admission stops, and keep-alive connections keep serving until forced cancellation then cuts an in-flight request without acknowledging it, consistent with the README's "allows a ten-second S3 drain".
- `Mark_Ready` after a stop request raises `Program_Error`, reachable only by a SIGTERM in the milliseconds between a child's bind and its readiness call; the generation ends with an unlogged exception, the listener descriptor is not closed, and the process exits 0. Harmless.
- Gaps in `server/tests/scripts/test.sh` beyond the four named in the findings above: a credential file with a foreign owner, a symlink, a directory or zero length (only `0644` is tested), a root that is a file or symlink, `FLYOLOGY_S3_BIND` other than the default, `AWS_SESSION_TOKEN` with the complete pair, `AWS_REGION` other than `us-east-1`, session expiry, session-slot eviction, ingress-budget exhaustion, a second SIGTERM, an S3 upload in flight at SIGTERM, a SIGTERM before readiness, the `FLYOLOGY_LOOP_POOL_SIZE` variable, and the exit status after a child failure. The reload run asserts only login and status, not that objects written before the restart are still listed.
