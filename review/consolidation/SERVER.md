## Area section

## SERVER: S3 application, routing, authorisation and operations (SERVER-1 .. SERVER-5)

The area covers `src/flyology-object_storage-server-s3_applications.ad?`, `src/flyology-object_storage-server.ads`, `-server-metadata_results.ads` and `-server-object_lambda_responses.ads`, with `src/flyology-object_storage-server-authentication.adb`, `src/flyology-object_storage.ads` (the public `Status` type), `src/flyology-object_storage-backends-memory.adb` (generation selection), the callers `tests/src/s3_server_harness.ad?` and `tests/src/s3_server_application_corpus.adb`, `docs/compatibility/s3.md` and the pinned botocore model `review/baseline/service-2.json`.

### SERVER-1: Content-MD5 is mandatory on DeleteObjects, PutBucketVersioning, PutObjectTagging and the other `requestChecksumRequired` routes, so stock aws-cli v2 is rejected

**Severity:** P0 (the discovery report said P1; the verifier raised it because the rubric's P0 covers an interop-breaking protocol violation that a stock client rejects, and a stock unconfigured aws-cli v2.36.34 was observed authenticating successfully against this server and then being refused on three ordinary operations — not a model-driven-SDK hypothetical).

**Location:** `src/flyology-object_storage-server-s3_applications.adb:17674-17683` (DeleteObjects: `MD5_Count /= 1 or else not Valid_Base64` answers 400 `InvalidRequest`), with the flexible-checksum verifier that never gets to substitute at `:17617-17670` and `:17713-17723`; `:10358-10369` (PutBucketVersioning, same gate); `:15883-15904` (object tagging, where `Algorithm_Count = 1 or else Has_Checksum_Header` answers 501 `NotImplemented` *before* the Content-MD5 gate, so no model-conformant request is accepted at all); the accept-either pattern the crate already uses elsewhere at `:5165-5200` (`Read_Bucket_Scalar_Control`'s `Require_Checksum`); documentation at `docs/compatibility/s3.md:506-508` and `:526-527`.

**Repro:** `tests/repros/src/repro_server_1.adb`, exit status 1, five failed expectations, with helper `tests/repros/src/repro_server_1_live.adb` (a listener holder for the stock-client run, not an assertion).

**What is wrong:** For every operation the pinned model marks `requestChecksumRequired: true`, the server treats Content-MD5 as the only acceptable integrity header rather than as one of several, and the gate runs before the already-implemented flexible-checksum verdict. A request carrying a correct `x-amz-checksum-crc32` or `-crc64nvme` is answered 400 `InvalidRequest` and nothing is deleted or configured; object tagging additionally answers 501 to any request carrying a flexible checksum at all. Since AWS turned on default integrity protection, stock aws-cli v2 sends `x-amz-sdk-checksum-algorithm: CRC64NVME` plus `x-amz-checksum-crc64nvme` and no Content-MD5 on exactly these operations, so unmodified `aws s3api delete-objects`, `put-bucket-versioning`, `put-bucket-tagging` and `put-object-tagging` all fail, and by inspection so do the other `requestChecksumRequired` routes. It is fully deterministic. The pinned model settles the input side: `ContentMD5` is in no such operation's `required` list, and for `DeleteObjects` and `PutBucketLifecycleConfiguration` the member does not exist in the input shape at all, so a client generated from this model has no modelled way to send it; the model's own `ChecksumAlgorithm` documentation says the flexible checksum is how `requestChecksumRequired` is satisfied.

**Notes:** Evidence is a stock aws-cli v2.36.34 driven against the crate's own loopback listener with only `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_DEFAULT_REGION` set and no checksum configuration; `list-objects-v2`, `s3 cp`, `s3api put-object` and single-key `s3 rm` all succeed in the same session, so authentication, signing and routing are fine and only these routes fail. CHECKSUM-2 is the same defect seen from a stock boto3 1.43.89 client and adds the sharper sub-case that `DeleteObjectsRequest` has no `ContentMD5` member, so DeleteObjects is unreachable from a stock SDK under any client configuration; SERVER-1 is the primary finding. Existing tests pass only because they never exercise the model-conformant shape: `tests/src/s3_server_application_corpus.adb:16039-16045` asserts `InvalidRequest` for a request with no integrity header at all, the ten-algorithm loop at `:16080-16096` leaves `Include_MD5` at its default `True`, and `tests/scripts/run-s3-server-slice.sh:107` drives DeleteObjects only through s5cmd v2.3.0 on aws-sdk-go v1, which still sends Content-MD5. This is not recorded as a documented limitation: `docs/compatibility/s3.md:506-508` states the rule as intended behaviour but never discloses that a model-driven client cannot comply. A fix is a maintainer policy decision, not a mechanical change: whether "at least one of Content-MD5 or a verified flexible checksum" replaces "Content-MD5 required" on these routes, and whether the object-tagging 501 at `:15889` becomes an accept path; `docs/compatibility/s3.md:506-508` and `:526-527` and the qualification prose would have to be restated with it.

### SERVER-2: Reading a delete marker loses `x-amz-delete-marker`, and a read of the marker's own version is 404 instead of 405

**Severity:** P1 (the discovery report said P2; the verifier raised it because the state is not unusual input — after any DELETE of any key in a versioned bucket that key's current version is a delete marker, so every subsequent GET or HEAD takes this path — and because the response is indistinguishable from "this key never existed". The missing-header half alone would be P2; the 404-instead-of-405 half is the reason for P1).

**Location:** `src/flyology-object_storage-server-s3_applications.adb:1929-1936` (`Send_Backend_Error` maps `Not_Found` to 404 `NoSuchBucket`/`NoSuchKey` with no marker-aware branch); the read arms that forward the plain result at `:17253-17262` (GetObject) and `:16880-16957` (HeadObject); the backend collapse at `src/flyology-object_storage-backends-memory.adb:318-331` (`Selected_Object_Index` returns 0 when the selected generation `Is_Delete_Marker`); the public `Status` enumeration with no delete-marker outcome at `src/flyology-object_storage.ads:39-62`; the only `x-amz-delete-marker` emitters are the DeleteObject arm and the WriteGetObjectResponse forwarding table.

**Repro:** `tests/repros/src/repro_server_2.adb`, exit status 1, seven failed expectations; controls confirm the DELETE itself reports `x-amz-delete-marker: true` with a version id, a live key still reads 200, and a key that never existed reads 404 with no marker header.

**What is wrong:** The backend collapses "the selected generation is a delete marker" onto the same `Natural` 0 it uses for "no such generation", so the server sees `Not_Found` and emits a bare 404 `NoSuchKey`. Two documented behaviours are lost: a read of a key whose current version is a delete marker does not carry `x-amz-delete-marker: true`, and a read of the marker's own version returns 404 instead of 405 `Method Not Allowed` with `Last-Modified`. Any versioning-aware client — replication, backup, or a tool walking ListObjectVersions and reading each generation — cannot distinguish "deleted" from "never existed", and cannot tell that the version it asked for is a marker. Everyone using a versioned bucket hits the first case on the very next read after any DELETE, deterministically. The pinned model's `GetObjectOutput.DeleteMarker` documentation states both behaviours verbatim, including the 405 and the `Last-Modified` header, and `HeadObjectOutput.DeleteMarker` carries the same binding.

**Notes:** BACKEND-MEMORY-3 is the backend half of this defect, verified at the backend interface with `repro_backend_memory_3` and with the pinned MinIO container as an oracle (HEAD of a marker-hidden key returns 404 with `x-amz-delete-marker: true`; HEAD and GET of the exact marker version return 405); SERVER-2 is the primary finding. This is not a documented limitation: `docs/compatibility/s3.md:59` and `:851-858` list exclusions that do not include delete-marker reads, and `:539-541` documents publishing and removing markers with no read-side caveat. No existing test asserts the wrong behaviour and none asserts the right one — `tests/src/s3_server_application_corpus.adb:18196-18206` and `:17754` cover only the DeleteObject response headers — but `tests/src/versioned_object_conformance.adb` does require a simple delete to make marker reads `Not_Found`, so a fix must update that expectation. The fix cannot be made in the server alone and needs a maintainer decision on the public API: either a new `Status` literal (for example `Delete_Marker`) in the visible type at `src/flyology-object_storage.ads:39-62`, or an out-parameter on the backend read operations carrying the marker's presence and `Last_Modified`; either way every backend and the conformance suite must be extended together.

### SERVER-3: HeadObject emits `x-amz-version-id: null` for an unversioned object while PutObject and GetObject omit it

**Severity:** P2 (the discovery report listed this under observations not counted as "harmless to clients, inconsistent between the two reads"; the verifier counted it because it also deviates from the crate's own documented three-way rule, and kept it at P2 because no client behaviour changes as a result).

**Location:** `src/flyology-object_storage-server-s3_applications.adb:16619-16622` (HeadObject's `Set_Common_Headers` writes the header unconditionally, substituting the literal `null`); the conditional GetObject path at `:4189-4194` (`Response_IO.Begin_Object`); the crate's own rule at `docs/compatibility/s3.md:446-450`; the identical model bindings for `HeadObjectOutput.VersionId` and `GetObjectOutput.VersionId` in `review/baseline/service-2.json`.

**Repro:** `tests/repros/src/repro_server_3.adb`, exit status 1, two failed expectations; controls confirm PutObject omits the header for unversioned publication, the two reads agree on a real version id in a versioned bucket, and an explicit `?versionId=null` selection reports `null` on both reads.

**What is wrong:** `docs/compatibility/s3.md:446-450` defines three distinct cases — omit for unversioned publication, the exact opaque identity for enabled publication, `null` for suspended publication — and HeadObject reports an unversioned object with the spelling reserved for a suspended bucket, while GetObject writes the header only when a version exists or the request asked for one. Anyone doing HEAD-then-GET on the same key in a never-versioned bucket sees two different answers, deterministically. The model gives the two reads no licence to differ: both members carry the same header binding and documentation.

**Notes:** This behaviour masks two client-side defects in CI. The client's `Head_Object_Response_Bound` (`src/flyology-object_storage-client-low_level.adb:5641-5658`, and the same predicate at `src/flyology-object_storage-client-objects.adb:139-155`) and `Get_Object_Response_Bound` (`src/flyology-object_storage-client-objects.adb:121-137`) reject a 200 that carries no `x-amz-version-id` after a `versionId=null` selection, and this server always supplies one — HEAD unconditionally at `:16619-16622`, GET through the `Has_Version_ID` branch at `:4192` — so the corpus passes against Flyology while all three third-party servers fail at that exchange. Those are CLIENT-LOW-1 (formerly BASELINE-1) and CLIENT-OBJECTS-1, and SERVER-3 is why neither shows up in the in-tree lanes. A maintainer changing the emitted header must therefore sequence it with the client predicates and confirm that no downstream oracle in `tests/` or the six-server comparison depends on the current spelling: the verifier's proposed fix (make HEAD match `:4189-4194`) keeps the `null` for an explicit `versionId=null` request and so leaves the lanes green, but any change that also dropped the header in that case would turn them red until the client is fixed. The verifier deliberately did not check MinIO, since the finding rests on the crate's disagreement with itself and with its own compatibility document rather than on AWS behaviour; the recollection that AWS omits the header on never-versioned buckets is unverified and not load-bearing. No existing test asserts either behaviour; the fix is a one-line change at `:16619` to match `:4189-4194`.

### SERVER-4: CompleteMultipartUpload `<Location>` is a path, not the URI the model documents

**Severity:** P2 (the discovery report listed it under observations not counted, as "clients only echo it"; the verifier counted it because it is a modelled output member carrying a value of the wrong form on an ordinary success path, and kept it at P2 because no stock client dereferences it).

**Location:** `src/flyology-object_storage-server-s3_applications.adb:13193-13197`, where the completion result is built with `Location => "/" & Bucket & "/" & URI_Encode (Key)`; the serializer at `src/flyology-object_storage-s3-multipart.adb:1125`; `shapes.CompleteMultipartUploadOutput.members.Location` in `review/baseline/service-2.json`, documented as "The URI that identifies the newly created object"; `docs/compatibility/s3.md:71`, which claims the operation without excluding the result URI.

**Repro:** `tests/repros/src/repro_server_4.adb`, exit status 1, one failed expectation; controls confirm the completion is 200 and that `<Bucket>`, `<Key>` and the composite `<ETag>` are present and correct.

**What is wrong:** Every successful CompleteMultipartUpload returns `<Location>/bucket/key</Location>` where the pinned model documents a URI; RFC 3986 requires a scheme, so this is a relative reference. A caller that treats the member as a URI — resolving it, storing it as a canonical object address, or comparing it with what AWS or MinIO returned — must know the endpoint out of band to make it usable. It affects every multipart completion and is deterministic. The model constrains `Location` only as a plain string, so the divergence is against the documentation rather than against a binding.

**Notes:** The crate documents nothing about `Location`. Fixing it needs a maintainer decision rather than an edit, because building an absolute URI requires choosing a scheme and this crate has none to use: `Apps.Request_Scheme` is `Plain_HTTP` for every request, since `server/src/flyology_object_storage_server_runtime.adb:168-170` and `tests/src/s3_server_harness.adb:89-91` both call `Apps.Create` without a `Scheme` argument. The choice is between a configured public base URI, deriving one from the signed `Host` header, or keeping the path deliberately and documenting it as a boundary in `docs/compatibility/s3.md`. No existing test asserts either form. The same always-`Plain_HTTP` constraint is what stops SERVER-5 short of a mechanical fix.

### SERVER-5: The modern default streaming payload sentinel is reported as `AuthorizationHeaderMalformed`

**Severity:** P2 — wrong diagnostics (the discovery report listed the `aws-chunked` rejection under observations not counted; the verifier counted only the diagnostic and refuted the discovery's premise that such a request receives 501).

**Location:** `src/flyology-object_storage-server-authentication.adb:139-140`, where `Payload_Hash /= SigV4.Unsigned_Payload and then not Valid_SHA256_Hex (Payload_Hash)` is one disjunct of the `elsif` chain evaluated at `:131-147` that returns `Malformed_Credentials`, before any signature verification (which begins at `:176`); the rendering at `src/flyology-object_storage-server-s3_applications.adb:1889-1892`; the arm that would answer correctly at `:14891-14895` (PutObject) and its UploadPart twin at `:12617-12621`; the HTTPS gates at `:6733` and `:6874`; documentation at `docs/compatibility/s3.md:342-345` and `:457-460`.

**Repro:** `tests/repros/src/repro_server_5.adb`, exit status 1, three failed expectations; controls confirm that the same `aws-chunked` request with an ordinary hex payload hash gets 501 `NotImplemented`, that an ordinary PutObject succeeds, and that a well-shaped but wrong payload hash is still `XAmzContentSHA256Mismatch`.

**What is wrong:** `Verify_Request` treats "the payload hash is neither 64 hex digits nor `UNSIGNED-PAYLOAD`" as the same failure as a broken Authorization header, and the server reports that as 400 `AuthorizationHeaderMalformed` with "The authorization header is malformed". Since AWS turned on default integrity protection, aws-cli v2 and boto3 send `x-amz-content-sha256: STREAMING-UNSIGNED-PAYLOAD-TRAILER` for PutObject and UploadPart over HTTPS — captured on the wire from aws-cli/2.36.34 through a TLS sniffer — so an operator who terminates TLS in front of this server sees every upload fail with a message accusing their credentials, while the real cause, an unimplemented payload encoding that the crate reports correctly one branch away as 501 `NotImplemented "aws-chunked payloads are not implemented"`, is never mentioned. It is deterministic for anyone in that deployment and invisible to anyone speaking plain HTTP, where the same client sends a fixed-length body with a header checksum that the server accepts.

**Notes:** Partially confirmed: rejecting `aws-chunked` framing is a documented limitation (`docs/compatibility/s3.md:342-345`, `:457-460`), so only the diagnostic is counted, and the discovery report's premise that such a request receives 501 is refuted — it receives 400, because the payload-hash shape check runs inside `Verify_Request` and never reaches the `aws-chunked` arm. It is not P0 because a stock PutObject over the transport this crate actually ships (plain HTTP) does not use `aws-chunked` and succeeds; the failing shape appears only when the client's endpoint URL is `https://`, which for this crate means a TLS terminator, since nothing in the repository passes `Scheme => Secure_HTTPS`. The repro substitutes the sentinel into an otherwise ordinary signed request, which is sound because the server decides before checking the signature, and necessary because the crate's own `S3.SigV4.Sign` raises `Invalid_Signing_Input` for that sentinel. The compatibility document words its exclusion as *SigV4* streaming, while `STREAMING-UNSIGNED-PAYLOAD-TRAILER` is the unsigned variant, and `:343` positively claims physical checksum trailers, so the document does not clearly cover the modern default and says nothing about the status code. No existing test covers a non-hex payload-hash sentinel. A fix needs a maintainer decision on where the boundary belongs: either `Verify_Request` gains a distinct status for a recognised-but-unimplemented streaming sentinel, which is a new literal in a public `Authentication` type, or the S3 application inspects `x-amz-content-sha256` before authenticating, which changes what is decided before the signature is verified.

## Coverage evidence: SERVER

- Authentication ordering and route agreement: `Verify_Request` runs once at `:6697`, after classification and before any body byte or backend call, over the same target and method strings the application classifies, so the signed target and the executed bucket, key and query cannot diverge; every arm runs after the `Authenticated` check.
- Pre-authentication classification was probed directly and refuted as a disclosure concern: an unauthenticated request gets 403 `AccessDenied` for existing and absent buckets and keys, unknown and implemented subresources, and an object-only subresource on a bucket; only a target the parser rejects (400 `InvalidURI`) and `OPTIONS`/`PATCH` (501) answer earlier, both purely syntactic and independent of stored state, and nothing reaches a backend.
- Exception containment was measured over the loopback listener: a signed PutObject declaring `Content-Length: 16` with only 4 body bytes produces no escaping exception and no deadlock — the server waits for the missing bytes and closes, the next request on the listener is served normally, and in process the same shape is answered 400 `InvalidRequest`.
- Request bodies: every buffered `Request_Source` sets a `Maximum`; `Request_IO.Read` rejects over- and under-length bodies against `Content-Length` and verifies `x-amz-content-sha256`, Content-MD5, header and trailer checksums before `Finished`, and every commit path asserts `Source.Completed`, so a backend cannot commit an unverified body.
- Response framing: `Begin_Object` validates the backend's announced range against the snapshot, emits a quoted ETag, IMF-fixdate `Last-Modified`, `Accept-Ranges`, exact 64-bit `Content-Length` and 206/200; `Write` enforces the announced length; unsatisfiable ranges return 416 with `Content-Range: bytes */size`.
- Conditional reads: duplicate, empty and malformed `If-*` headers are 400; precedence is delegated to the core evaluators; 304 responses carry ETag and `Last-Modified`; CopyObject source conditions map `Not_Modified` to 412.
- Error XML and containment: `Send_Error` always emits Code, Message, Resource and RequestId; the status mapping never sends a second response once the wire has started (`Wire_Response_Started`/`Mark_Failed`), and every unexpected Ada exception is converted rather than escaping `Handle`.
- Header emission safety: PutObject, CopyObject and CreateMultipartUpload metadata values and `response-*` overrides are validated more strictly than `flyology_http`'s own check, so no stored value can make `Set_Header` raise on read.
- Multipart, DeleteObjects, listings and copy: part-number bounds and initiation reconciliation; quiet mode, request-order results and the 1,000-key bound; `max-keys`/`max-parts`/`max-uploads`/`max-buckets` mapping with no `Constraint_Error` path, v1 `NextMarker` only with a delimiter, v2 `KeyCount` including common prefixes and continuation-token validation; `x-amz-copy-source` parsed by the same strict target parser with the copy version headers emitted on success.
- Resource bounds: object bodies stream through 16 KiB reads and backend sinks with no whole-object buffering; every backend call receives the cancellation token and deadline; cancellation and timeout re-raise after `Mark_Failed` and are handled by closing the connection.

## Observations not counted: SERVER

- `Apps.Request_Scheme` is always `Plain_HTTP` because neither `server/src/flyology_object_storage_server_runtime.adb:168-170` nor `tests/src/s3_server_harness.adb:89-91` passes a `Scheme`, so `UNSIGNED-PAYLOAD` is always answered 400, and the WriteGetObjectResponse admission at `:6733` and the SSE gate at `:5371` can never be satisfied by this repository's own server; consistent with a crate that ships no TLS listener, but worth writing down.
- SigV4 presigned (query-string) authentication is not implemented and such requests get 403 `AccessDenied`; documented as planned and not claimed at `docs/compatibility/s3.md:78`.
- `OPTIONS` and `PATCH` on any target are 501 rather than 405 or 403, and a target the parser rejects is 400 `InvalidURI` where AWS answers 403; a deliberate deviation from AWS's uniform 403 that discloses only route recognition.
- HeadObject with a satisfiable `Range` answers 200 with the range's `Content-Length` and no `Content-Range`, which matches the pinned model's HeadObject `Range` documentation.
- CopyObject with the default COPY metadata directive plus any replacement metadata header answers 400 `InvalidRequest` (`:14396-14411`), and CopyObject onto itself with COPY is accepted; both AWS comparisons are from memory and unverified.
- CreateMultipartUpload rejects user metadata, cache and content headers, storage class, tagging and object-lock headers with 501, so `aws s3 cp --metadata ...` above the multipart threshold fails; documented capability rejection at `docs/compatibility/s3.md:71`.
- CreateBucket on an existing bucket returns 409 `BucketAlreadyOwnedByYou`, where AWS us-east-1 returns 200 for the owner and MinIO returns 409.
- GetObjectAttributes never emits `StorageClass` even when requested (`:16305-16330`); omitted rather than fabricated, per the documented profile.
- PutObjectTagging answers 501 `NotImplemented` to any SDK checksum (`:15889`); folded into SERVER-1 rather than counted separately, because it is the same client-facing failure with a different status code.
- The 400 for PutBucketVersioning came back with `Connection: close` while the otherwise identical 400 for DeleteObjects came back with `Connection: keep-alive`, over keep-alive connections neither of which asked for a close; botocore reconnected transparently, so this is an inconsistency rather than a defect.
- Per-request budget is `Timeout => 60.0` in both the harness and the runtime, so a 5 GiB PutObject must complete within 60 s; a policy value.
- `Read_Document` appends byte-by-byte into an `Unbounded_String`, bounded by each route's `Maximum` (at most 2 MiB); performance rather than correctness.
- `flyology_http` answers 204 when a handler returns without responding; no arm was found that returns silently, but the fallback would mask such a regression as a success.
- PutObject `If-Match` against a missing key yields 412 where the model documents 404 `NoSuchKey` for the DeleteObject case (and, from memory and unverified, the same for PutObject); the evaluator lives in the core package, outside this area.
