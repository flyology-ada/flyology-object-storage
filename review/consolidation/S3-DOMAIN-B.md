### S3-DOMAIN-B-1: DeleteObjects rejects a namespace-free `<Delete>` body, so `mc` and `s3cmd` cannot batch-delete anything

**Severity:** P0 (the discovery report said P1, with High confidence in the code path and the model but only Medium confidence, from memory, about which stock clients omit `xmlns`). The verifier raised it after driving both named clients at the real application and capturing their bodies off the wire: `mc` RELEASE.2025-08-13T08-35-41Z (minio-go v7.0.90) and s3cmd 2.4.0 both send a namespace-free `<Delete>` **with a correct Content-MD5** by default and are answered `400 MalformedXML`, while MinIO `RELEASE.2025-09-07T16-13-09Z` answers `200` for the identical bytes. That is the rubric's "interop-breaking protocol violation that a stock client or server rejects": batch delete is completely unavailable from these clients and nothing is deleted.

**Location:** `src/flyology-object_storage-s3-deletions.adb:66-79` (`Delete_Handler.Start_Element_Details`, which raises `Malformed_Delete` unless `Namespace_URI = "http://s3.amazonaws.com/doc/2006-03-01/"`; it is an override on the handler, so it runs for **every** element and not only the root) and `:380-393` (`Parse_Request` calls `XML.Parse` then `Validate`, and the handler exception surfaces through the `when XML.XML_Error` branch as `Malformed_Delete "malformed DeleteObjects XML"`); `src/flyology-object_storage-server-s3_applications.adb:17730-17741`, where the request body is passed verbatim to `Deletions.Parse_Request` with no namespace normalisation anywhere in between, and `:17959-17964`, `when Deletions.Malformed_Delete => Send_Error (X, 400, "MalformedXML", ...)`; the contract that promises no such rule, `src/flyology-object_storage-s3-deletions.ads:76-82` ("Parse one bounded DeleteObjects request document"); the pinned model, in which the `Delete` shape carries no `xmlNamespace` and only the `DeleteObjectsRequest.Delete` member does; the existing assertion of the wrong behaviour at `tests/src/object_storage_test_cases.adb:11450-11452`, `Must_Reject_Request ("<Delete><Object><Key>k</Key></Object></Delete>", …)`.

**Repro:** `tests/repros/src/repro_s3_domain_b_1.adb`, exit status 1, five failed expectations.

**What is wrong:** `Delete_Handler.Start_Element_Details` requires the exact S3 namespace URI on every element of a DeleteObjects request body. In the pinned model the namespace is a *serializer* trait on the `DeleteObjectsRequest.Delete` member, not a constraint on the `Delete` shape, so receivers must not demand it, and AWS and MinIO do not. minio-go marshals `<Delete><Quiet>false</Quiet><Object><Key>m1</Key></Object><Object><Key>m2</Key></Object><Object><Key>m3</Key></Object></Delete>` with `Content-Md5: 31pfUAHQbxJHn3iLLTGlGg==`, and s3cmd concatenates `<Delete><Object><Key>k1</Key></Object><Object><Key>k2</Key></Object></Delete>` with `Content-MD5` present; both were captured off the wire from `mc rm --recursive --force` and `s3cmd rm --recursive --force` against this server, and both are answered `400 MalformedXML`. `mc rm --recursive`, `mc rb --force` and `s3cmd rm --recursive` therefore cannot delete anything from a Flyology endpoint, while the same commands work against MinIO and AWS. The rejection was isolated to the namespace by replaying the same bytes over plain HTTP with a correct SigV4 header signature, a real payload hash and `Content-MD5` (botocore `SigV4Auth`), so that neither SERVER-1 nor the UNSIGNED-PAYLOAD rule applies: `DeleteObjects mc body (no xmlns): 400 <Code>MalformedXML</Code>`, `same body + xmlns: 200 <DeleteResult ...><Deleted><Key>m1</Key></Deleted></DeleteResult>`, `s3cmd DeleteObjects body (no xmlns): 400 <Code>MalformedXML</Code>`. The same namespace-free body sent to MinIO answers `200 <DeleteResult xmlns="http://s3.amazonaws.com/doc/2006-03-01/"><Deleted><Key>single-crc</Key></Deleted></DeleteResult>`. The program creates a bucket and `k1`/`k2`/`k3`, calls `Deletions.Parse_Request` on `mc`'s captured document (which raises `Malformed_Delete: malformed DeleteObjects XML`), then sends `mc`'s `<Delete><Quiet>false</Quiet><Object><Key>k1</Key></Object></Delete>` and s3cmd's `<Delete><Object><Key>k2</Key></Object></Delete>` as signed `POST /domain-b1?delete` requests with a correct `Content-MD5`, both answered `400` with `<Code>MalformedXML</Code><Message>The XML provided was not well-formed or did not validate against the published schema</Message>`; the boto3/aws-cli control `<Delete xmlns="http://s3.amazonaws.com/doc/2006-03-01/"><Object><Key>k3</Key></Object><Quiet>false</Quiet></Delete>` passes with `200` and a `<Deleted><Key>k3</Key></Deleted>` entry, which is what isolates the namespace inside the program as well. It is deterministic and fires on every batch.

**Notes:** This finding and S3-DOMAIN-B-2 are the same change class as S3-DOMAIN-A-5, the server-side PutBucketVersioning body parser that is the only request codec rejecting an unqualified root: three request codecs in two areas enforce a namespace the pinned model places on the member as a serializer instruction, and a single decision about receiver-side namespace tolerance settles all three, so they should be sequenced together. This finding also meets SERVER-1 on the same route, and the order of rejection matters for both fixes: current boto3 and aws-cli send `x-amz-checksum-crc32` instead of `Content-MD5`, so SERVER-1's integrity gate stops them one step *earlier* and they never reach the namespace check, while `mc` and `s3cmd` do send `Content-MD5`, so for them the namespace check is the first and only rejection. Today no client can batch-delete at all; fixing SERVER-1 alone would still leave `mc` and `s3cmd` broken here, and fixing this alone would still leave boto3 and aws-cli broken there. `docs/qualification/delete-objects.md` documents the strictness, so it is deliberate rather than accidental, but it is not an S3 protocol rule and MinIO accepts what this server refuses, so it is not a documented limitation. `tests/src/object_storage_test_cases.adb:11450-11452` pins the wrong behaviour and would have to be inverted with the fix. The maintainer decision a fix needs is equivalent to the one already taken for bucket tagging: either accept an absent namespace on request parsing along the `Allow_Empty_Namespace` pattern of `tagging.adb:434-448`, which would be a new public parameter or a second entry point, or accept it unconditionally; foreign namespaces and attributes can remain invalid either way. Refutation attempts that failed: there is no tolerant request-side entry point in `Deletions` analogous to `Tagging.Parse_Bucket_Response`; the XML layer does not supply the S3 namespace implicitly for an unqualified document, which the program's unit-level call shows; and the rejection is not some other property of those bodies (`<Quiet>` first, or no `<Quiet>` at all), because adding only `xmlns` turns each of them into a `200`.

### S3-DOMAIN-B-2: PutBucketTagging rejects a namespace-free `<Tagging>` body that PutObjectTagging accepts

**Severity:** P0 (the discovery report said P1 with Medium confidence, the stock-client claim being from memory). The verifier raised it for the same interop reason as S3-DOMAIN-B-1 and confirmed the client sub-claim directly: minio-go really does marshal `<Tagging>` with no namespace, captured off the wire from `mc tag set` for **both** the bucket and the object form, as `<Tagging><TagSet><Tag><Key>team</Key><Value>storage</Value></Tag></TagSet></Tagging>`. That `mc`'s default PutBucketTagging body is rejected *for the namespace* was proven by replaying its exact bytes with a valid signature and `Content-MD5` (`400 <Code>MalformedXML</Code>`) and then adding only `xmlns` (`200`); MinIO accepts the identical body with `200`.

**Location:** `src/flyology-object_storage-s3-tagging.adb:434-448` (`Bucket_Tagging_Handler.Start_Element_Details`, which rejects an empty `Namespace_URI` unless `Allow_Empty_Namespace` is set) and `:574-586` (`Parse_Bucket` uses `Allow_Empty_Namespace => False`, `Parse_Bucket_Response` uses `True`, both through `Parse_Bucket_Document` at `:550-586`); `src/flyology-object_storage-server-s3_applications.adb:8261-8271`, where the server calls the strict `Tagging.Parse_Bucket`, and `:8284-8294`, which maps `Malformed_Tagging` to `400 MalformedXML` and `Invalid_Tag` to `400 InvalidTag`; `src/flyology-object_storage-s3-tagging.adb:43-89`, where the object `Tagging_Handler` overrides no `Start_Element_Details` at all, so `PutObjectTagging` accepts any namespace including none; `src/flyology-object_storage-s3-tagging.ads:48-52`, which grants the tolerance to the *response* decoder only; the pinned model, in which the `Tagging` shape carries no `xmlNamespace`; the UNSIGNED-PAYLOAD gate `src/flyology-object_storage-server-s3_applications.adb:1903-1906`; the existing assertions at `tests/src/object_storage_test_cases.adb:11268-11270` (the rejection) and `:11233-11243` (the response decoder accepting the same string).

**Repro:** `tests/repros/src/repro_s3_domain_b_2.adb`, exit status 1, two failed expectations.

**What is wrong:** the crate already has the tolerant behaviour — the `Allow_Empty_Namespace` flag threaded through `Parse_Bucket_Document` — and grants it only to the response decoder. The result is a server that accepts a document on `PUT /bucket/key?tagging` and rejects the identical document on `PUT /bucket?tagging`, deterministically, for any client that does not emit `xmlns`; minio-go is such a client, on both resources. The program compares `Parse_Bucket` with `Parse_Bucket_Response` on `mc`'s captured document — `Parse_Bucket_Response` accepts it with `tags=1`, `Parse_Bucket` raises `FLYOLOGY.OBJECT_STORAGE.S3.TAGGING.MALFORMED_TAGGING: malformed bucket tagging XML` — then sends that document as a signed `PUT …?tagging` with a correct `Content-MD5` to both resources: `PUT /domain-b2/k?tagging` is answered `200`, `PUT /domain-b2?tagging` is answered `400` with `<Code>MalformedXML</Code>`, and the boto3/aws-cli control carrying `xmlns="http://s3.amazonaws.com/doc/2006-03-01/"` on the bucket resource is answered `200`. The plain-HTTP caveat is stated plainly: over the plain-HTTP test endpoint `mc tag set` is stopped one step earlier, because minio-go signs this body as `UNSIGNED-PAYLOAD`, which the crate refuses without TLS (`s3_applications.adb:1903-1906`, `400 InvalidRequest` "UNSIGNED-PAYLOAD requires a secure transport"), so the namespace check is not reached over that endpoint; on the HTTPS endpoint a real deployment uses, that gate passes and the namespace check is what remains, which is why the isolating replay was signed with a real payload hash rather than driven through `mc`.

**Notes:** With S3-DOMAIN-B-1 this is the same change class as S3-DOMAIN-A-5, the server-side PutBucketVersioning root check in another area; one decision on receiver-side namespace tolerance settles all three sites. Here the crate is already inconsistent with itself in two directions — the object request path and the bucket *response* path both accept what the bucket request path refuses — and the test suite currently asserts that inconsistency, `tests/src/object_storage_test_cases.adb:11268-11270` pinning the rejection and `:11233-11243` pinning the acceptance of the same string by the response decoder, so the first would have to be inverted with the fix. `docs/qualification/bucket-tagging.md` documents "strict namespace-aware XML", but the model imposes no such rule and MinIO accepts the body, so the same reasoning as S3-DOMAIN-B-1 applies and it is not a documented limitation. The fix is one Boolean: flipping `Parse_Bucket`'s `Allow_Empty_Namespace` to `True` brings the request path in line with the response path and with the object path, and needs no new public declaration; the maintainer decision is only whether "foreign namespaces remain invalid" should stay, which it can, because only the *empty* namespace is at issue. Refutation attempts that failed: there is no other tolerant request path (`Parse_Bucket_Response` is called only from `client-low_level.adb:392`, `Decode_Get_Bucket_Tagging_Response`); the object path does not enforce a namespace either, which would at least have made the server self-consistent; and no other property of `mc`'s body is at fault, since adding only `xmlns` turns the request into `200`.

### S3-DOMAIN-B-3: The ListObjectAnnotations query codec binds camelCase names the model, the generated descriptor and this crate's own client do not use

**Severity:** P1 (unchanged). This is a self-interop failure: the crate's own client cannot use a prefix, a result limit, or pagination against the crate's own server. It is not P0 because `ListObjectAnnotations` is a Flyology extension operation, so no third-party SDK is involved; it is a wrong result on valid input via a reachable path.

**Location:** `src/flyology-object_storage-s3-annotations.adb:137-172`, where `Parse_Query` matches `annotationPrefix`, `maxAnnotationResults` and `continuationToken` and falls through to `raise Malformed_Annotation_Request with "unsupported annotation query parameter"`; the pinned model's `ListObjectAnnotationsRequest` querystring members, `VersionId → versionId`, `MaxAnnotationResults → max-annotation-results`, `AnnotationPrefix → annotation-prefix`, `ContinuationToken → continuation-token`; the generated descriptor `src/flyology-object_storage-s3-model.adb:45588-45599`, which carries the same hyphenated names; `src/flyology-object_storage-client-low_level.adb:11605-11624`, where `Prepare_List_Object_Annotations` adds `MaxAnnotationResults`, `AnnotationPrefix` and `ContinuationToken` by member name, and `:1216-1222`, which emits `SigV4.Pair (Model.Member_Location_Name (Input_Shape, Member), …)`, that is, the hyphenated spelling; `src/flyology-object_storage-server-s3_applications.adb:6505-6529`, where the route sniff uses the model-conformant `&annotationName=` but any `Malformed_Annotation_Request` sets `Annotation_Query_Invalid`, and `:7015-7019`, which answers `400 InvalidArgument` "The object annotation request query is invalid"; the in-tree gate asserting the non-model names at `tests/src/s3_server_application_corpus.adb:13552` and `:13588`.

**Repro:** `tests/repros/src/repro_s3_domain_b_3.adb`, exit status 1, three failed expectations.

**What is wrong:** `Annotations.Parse_Query` hard-codes camelCase names for the three list-only query members, while every other part of the crate — the pinned model, the generated descriptor read through `Model.Member_Location_Name`, and `Client.Low_Level.Prepare_List_Object_Annotations` which reads that descriptor — uses the hyphenated names. A Flyology client that asks for a prefix, a page size, or the next page therefore gets `400 InvalidArgument` from a Flyology server, deterministically; only the degenerate "list everything, one page" call works. The program prints the compiled model's query location names for the operation (`MaxAnnotationResults -> "max-annotation-results"`, `AnnotationPrefix -> "annotation-prefix"`, `ContinuationToken -> "continuation-token"`, `VersionId -> "versionId"`, each annotated "what Client.Low_Level puts on the wire"), creates an object with the annotations `alpha` and `beta`, then issues signed `GET /domain-b3/obj?annotation&<name>=<value>` requests in both spellings. The camelCase controls pass: `maxAnnotationResults=1` is answered `200` with a `<NextContinuationToken>fos1.5073ca3abd4a8ffc65e51385fca7513b2c3a2c5015c9debcaa3ecaf577636496.616c706861</NextContinuationToken>`, and `annotationPrefix=al` is answered `200` with `<AnnotationPrefix>al</AnnotationPrefix><AnnotationCount>1</AnnotationCount>`. The model's spellings `max-annotation-results=1`, `annotation-prefix=al` and `continuation-token=fos1.5073ca3a…` are each answered `400 <Code>InvalidArgument</Code>`, the last of them driven by a real `NextContinuationToken` taken from the preceding page, so pagination is impossible in the model's spelling. The two singular annotation verbs are correct (`annotationName`, `versionId`), so only these three names are wrong.

**Notes:** This is a self-interop failure between the generated descriptor and the hand-written codec, and the direction of the fix follows from which side is generated. `src/flyology-object_storage-s3-model.adb:45588-45599` is generated from the pinned model and agrees with it — the program reads the location names out of the *compiled* model and prints the hyphenated forms, so descriptor and pinned JSON are not in conflict — and the "Ada source style" section of the repository rules forbids hand-editing generated sources, so the hand-written `Annotations.Parse_Query` is the side that must change: either compare against `Model.Member_Location_Name`, as `multipart_uploads.adb` already does for enumerations, or correct the three literals. No new public declaration is needed. `tests/src/s3_server_application_corpus.adb:13552` and `:13588` send the camelCase names and would have to be updated with the fix; the qualification lane `tests/src/s3_list_object_annotations_qualification.adb:50-83` adds the optional members only when environment inputs are set, which is why the default lane never noticed. Refutation attempts that failed: the descriptor did not come from a different model revision; there is no second parser accepting the hyphenated spellings, since `continuation-token` appears only in the ListObjectsV2 and ListBuckets parsers; and the optional members are not unreachable in practice, because the program drives them end to end.

### S3-DOMAIN-B-4: URL-encoded ListMultipartUploads cursors are compared bytewise, so page 2 of a valid `encoding-type=url` listing is 500 InternalError

**Severity:** P1 (unchanged), and cheaper to hit than the discovery estimated: no non-ASCII key is needed, because `%` (16#25#) sorts below every unreserved byte, so the ASCII keys `a9` and `a:` suffice. A valid, backend-answered request ends as `500 InternalError`, and the crate's own client maps the same exception to `Invalid_Response`. Not P0: no data is lost and nothing hangs.

**Location:** `src/flyology-object_storage-s3-multipart_uploads.adb:655-667`, where the "next cursor does not advance" predicate compares `US.To_String (Value.Next_Key_Marker) < US.To_String (Value.Key_Marker)`, and `:773-795` and `:823-828`, where `Validate` runs inside both `Parse_List_Multipart_Uploads` (client) and `Serialize_List_Multipart_Uploads` (server); `src/flyology-object_storage-server-s3_applications.adb:11199-11204`, where the local `Encoded` function applies `Encoding.URI_Encode (Value, Encode_Slash => False)` when `Request.URL_Encoding`, and `:11218-11220` and `:11240-11244`, which fill `Key_Marker` and `Next_Key_Marker` with `Encoded (...)` while `Upload_ID_Marker` and `Next_Upload_ID_Marker` stay raw; `:11279-11286`, where the handler catches only `Multipart_Uploads.Malformed_List_Request`, so `Malformed_Upload_Listing` escapes to the final `when others` and becomes `500 InternalError`; `src/flyology-object_storage-s3-sigv4_encoding.adb:10-46`, where `Unreserved` is `A-Z a-z 0-9 - . _ ~` plus `/` when `Encode_Slash => False`, every one of those bytes being above `%`; `src/flyology-object_storage-client-low_level.adb:13405` and `:13423-13426`, which map `Malformed_Upload_Listing` to `Invalid_Response`, with the supported URL-encoding parameter at `:13477-13484`.

**Repro:** `tests/repros/src/repro_s3_domain_b_4.adb`, exit status 1, three failed expectations.

**What is wrong:** `Multipart_Uploads.Validate` treats `Next_Key_Marker < Key_Marker` as proof that a page's cursor went backwards, but the server has already percent-encoded both markers when `encoding-type=url` was requested, and percent-encoding is not order-preserving: `a9 < a:` raw, while `a%3A < a9` encoded. Any truncated page whose next key first differs from the previous marker at a byte that encodes — `:` `[` `=` `&` `?` `#`, a space, or any non-ASCII byte — trips the check inside `Serialize_List_Multipart_Uploads`, and because the handler catches only `Malformed_List_Request` the exception escapes to the generic handler, so the caller sees `500 InternalError` for a request the backend answered correctly. Keys containing `:` are ordinary (timestamps, URNs, `a:b` namespacing), so this is deterministic and not exotic. The program creates multipart uploads for `a9`, `a:` and `az`, decodes a conforming truncated URL-encoded page through the client decoder — which raises `Malformed_Upload_Listing: ListMultipartUploads next cursor does not advance` — then pages the real server with `encoding-type=url&max-uploads=1`. Page 1 is `200` with `<NextKeyMarker>a9</NextKeyMarker>` and `<IsTruncated>true</IsTruncated>`; page 2, `GET /domain-b4?uploads&encoding-type=url&max-uploads=1&key-marker=a9&upload-id-marker=…`, is `500` with `<Code>InternalError</Code><Message>We encountered an internal error</Message>` instead of the expected encoded `a%3A` next marker. The control, the same paging without `encoding-type`, is `200` with `<KeyMarker>a9</KeyMarker><NextKeyMarker>a:</NextKeyMarker>`, which isolates the encoding as the cause. The client decoder is affected symmetrically, so any conforming server that URL-encodes `NextKeyMarker` — AWS included — makes `Parse_List_Multipart_Uploads` raise `Invalid_Response`.

**Severity:** P2 (unchanged). It needs a non-Flyology server that reports the parts container for a single-part object; the crate's own server never does, which the program shows, so there is no self-interop failure and the severity is not raised. ### S3-DOMAIN-B-8: The GetObjectAttributes decoder bounds the response's `MaxParts` echo by `Core.Page_Size'Last`, and MinIO echoes 10000

**Severity:** P2 (new; the verifier found it while verifying S3-DOMAIN-B-7, because MinIO's real response was rejected before the checksum rule was even reached). **Location:** `src/flyology-object_storage-s3-attributes.adb:551-576`, where `Finish_Field` raises `Malformed_Attributes "invalid object part scalar"` when `Item.Field = Max_Parts_Field and then Parsed.Value > Core.Page_Size'Last`, and, because that runs inside the SAX handler, `Parse_Result`'s `when XML.XML_Error` arm rewrites it to the misleading "malformed GetObjectAttributes XML"; `:786-790`, where `Validate` applies the same `Core.Page_Size'Last` bound a second time; `src/flyology-object_storage-s3-core.ads:28`, `subtype Page_Size is Natural range 0 .. 1_000;`; the pinned model, in which `GetObjectAttributesParts.MaxParts` has shape `MaxParts`, which is `{'type': 'integer'}` with **no** `min` or `max`, the request-side member being the equally unbounded `x-amz-max-parts` header.

**What is wrong:** the decoder constrains the *response's* `MaxParts` echo to `Core.Page_Size'Last` (1000), a bound that exists for Flyology's own pagination policy and that the pinned model does not place on this member. - `Copies.Validate` (`copies.adb:336-340`) requires both `ETag`, strong and quoted, and `LastModified`, strict ISO-8601, although every `CopyObjectResult` member is optional in the model, so SeaweedFS's bare `ETag` is rejected. Confirmed as stated and confirmed to be deliberate: `docs/qualification/copy-object.md:215` says "the production decoder continues to require one strong quoted entity-tag". A documented limitation.
- Object `Tagging.Parse` requires `<Key>` before `<Value>` inside `<Tag>` (`tagging.adb:78`: the `Value` arm tests `Item.Seen_Key`), while the bucket parser accepts either order (`tagging.adb:485`: the `Value` arm tests only `not Item.Seen_Value`). Re-derived from source and confirmed as an internal inconsistency, but every SDK serialises in model order and every captured client body above does, so no reachable client is affected.
- `Multipart_Uploads.Parse_List_Multipart_Uploads_Query` rejects `max-uploads` outside 1..1000 with `InvalidArgument`, documented at `multipart_uploads.ads:33-35` ("max-uploads is in 1 .. 1_000"). MinIO accepts and echoes both `0` and `5000`, so the divergence is real, but no captured client sends such a value. A documented limitation.
- `Object_Reads.Parse_Conditional_Date` and the `Ada.Calendar` limits: out-of-range values yield `Valid => False`, which callers treat as an ignorable invalid HTTP-date per RFC 9110. Harmless.
- `Multipart_Uploads.Validate:642-654` rejects a non-truncated page that carries next markers, and a truncated ungrouped page without `NextUploadIdMarker`. Not reproducible against MinIO, which emits empty `<NextKeyMarker></NextKeyMarker>` elements on a non-truncated page; those decode to zero-length strings and pass. Separately noted from the same run: MinIO answered `max-uploads=1` with three `<Upload>` entries and `<MaxUploads>1</MaxUploads><IsTruncated>false</IsTruncated>`, which `Validate` correctly rejects on its first branch — a MinIO defect rather than a crate defect, though it does mean the crate's client cannot list multipart uploads against this MinIO release.
- `Annotations.Parse_List` requires the root `ListObjectAnnotationsOutput` although the model gives that output no `locationName`. Confirmed as stated; both sides of the crate agree on that root, so it is consistent today, and S3-DOMAIN-B-3 shows that agreement on the root is not evidence of general model conformance for this operation.
- `Annotations.Decode_Continuation:246-250`, a candidate `Constraint_Error` on tokens shorter than 70 bytes: refuted and re-verified. `Core.Valid_Listing_Continuation_Syntax` (`s3-core.adb:8-23`) rejects any token shorter than the 70-byte header before the slices are taken.
- `Deletions.Serialize_Request` emits `ETag` before `Key` (`deletions.adb:407-412`), out of model member order. Re-derived from source; receivers are order-insensitive — the crate's own `Parse_Request` is, and MinIO accepted `mc`'s body whose `<Quiet>` comes first.
- Mandatory `Content-MD5` on DeleteObjects is out of area (SERVER-1) and is not counted here. It was independently re-observed in this area: current boto3 1.43.89 and aws-cli 2.36.34 send `x-amz-checksum-crc32` instead of `Content-MD5` and are answered `400 InvalidRequest` "DeleteObjects requires one valid Content-MD5 header". The same gate applies to PutBucketTagging ("PutBucketTagging requires a valid Content-MD5"), which the SERVER report may want to note.
- MinIO's lowercase `getObjectAttributesResponse` root, which `attributes.adb:405-408` rejects, is already a documented exclusion: `tests/scripts/test-minio.sh:64,74` sets `FLYOLOGY_GET_OBJECT_ATTRIBUTES_ORACLE_MODE=minio-2025-lowercase-root`, "a non-AWS lowercase root element". Not a new finding, but it is the reason both S3-DOMAIN-B-7 and S3-DOMAIN-B-8 were never exercised in-tree, and the reason both programs re-root MinIO's captured bytes under the AWS root.
