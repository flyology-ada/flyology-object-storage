## BACKEND-MEMORY: memory backend, backend interface and the shared listing builders (BACKEND-MEMORY-1 .. BACKEND-MEMORY-3)

The area covers `src/flyology-object_storage-backends-memory.ad?`, `src/flyology-object_storage-backends.ad?`, `-backends-listing.ad?`, `-backends-bucket_listing.ad?`, `-backends-multipart_listing.ad?` and `docs/architecture/memory-backend.md`, with `src/flyology-object_storage.ads` for the public `Status` and information types, the identical self-copy predicates in the files and SQLite backends, the ListMultipartUploads and CopyObject arms of `src/flyology-object_storage-server-s3_applications.adb`, the qualification documents, and the pinned botocore model.

### BACKEND-MEMORY-1: ListMultipartUploads paired cursor skips same-key uploads whose SHA-256 upload IDs sort against initiation order

**Severity:** P1 (the discovery report also said P1).

**Location:** `src/flyology-object_storage-backends-multipart_listing.adb:84-91`, where the exclusive marker test is `Candidate_Key = After_Key and then (After_ID'Length = 0 or else Candidate_ID <= After_ID)` — purely lexical on the upload ID, with no reference to `Initiated`; the page order at `:17-30`, which sorts same-key candidates by `Initiated` first and breaks equal-time ties with the upload ID; the cursor construction from the last returned candidate at `:141-149`; the SHA-256 upload-ID derivation at `src/flyology-object_storage-backends-memory.adb:2830-2833` and the whole-second clock at `:207-208`; the server's straight pass-through of the markers at `src/flyology-object_storage-server-s3_applications.adb:11186-11196` and `:11240-11246`; the contract stating the two rules independently at `src/flyology-object_storage-backends.ads:2711-2715`; the requirement the behaviour violates at `docs/qualification/list-multipart-uploads-preparation.md:42-45`.

**Repro:** `tests/repros/src/repro_backend_memory_1.adb` with helper `tests/repros/src/repro_backend_memory_support.ad?`, exit status 1, eleven failed expectations — 5 of 6 uploads lost at the backend interface and 4 of 6 over the wire.

**What is wrong:** The builder sorts same-key candidates by initiation time, filters them by lexical upload ID, and builds the continuation cursor from the last returned candidate; the three rules are mutually inconsistent whenever the two orders disagree, which for this backend is the normal case, because upload IDs are SHA-256 digests and carry no relation to creation order. A client that paginates ListMultipartUploads with the markers the service itself returned silently loses every same-key upload whose ID sorts at or before the marker, and the pages report `IsTruncated false`, so nothing tells the client anything is missing. Anyone using `max-uploads` on a key with several concurrent uploads hits it — multi-writer retry loops, orphan-upload sweepers and lifecycle cleanup are exactly the callers that paginate — and `max-uploads` is a modelled request member from 1 through 1,000, so the page bound is not unusual input. It is fully deterministic for a given bucket, key and counter triple, and invisible only when all same-key uploads land in the same wall-clock second. The qualification document explicitly forbids this: a service-produced marker pair "must always resume without skipping, repeating, or looping".

**Notes:** Existing coverage passes while asserting a weaker property: `tests/src/object_storage_test_cases.adb:3318-3328` creates all five uploads in one tight loop, so the two same-key uploads share an `Initiated` value and the page order falls through to the upload-ID tie break, which coincides with the marker rule, and the marker assertion at `:3379-3389` deliberately uses smaller and larger IDs rather than creation order. No test creates same-key uploads across a second boundary, and no server-side reconciliation exists. The shared builder is also used by the files and SQLite backends, so a fix belongs in `multipart_listing.adb` rather than in one store. A fix needs a maintainer decision on which of the two S3 rules wins: either the page order for a shared key becomes lexical upload ID, which matches the marker but diverges from AWS's stated initiation-time ordering and from the sentence at `backends.ads:2712-2714`, or the marker filter resolves `After_ID` to its initiation time and compares on the same `(Initiated, Upload_ID)` key the page order uses, which matches AWS's ordering but makes the marker meaningful only while the referenced upload still exists — raising the same unknown-cursor policy question already pinned for `ListObjectVersions` at `memory.adb:2687-2690`.

### BACKEND-MEMORY-2: Same-key CopyObject with an exact or null source selector (version restore) is rejected as `Invalid_Request`

**Severity:** P1 (the discovery report also said P1; its confidence was Medium only because AWS acceptance of a versioned self-copy was from memory, and that has now been measured against a real server).

**Location:** `src/flyology-object_storage-backends-memory.adb:4977-4986`, the guard that compares source and destination bucket and key and the four directive fields and returns `Invalid_Request` before `Fetch_For_Copy` at `:4988`, never consulting `Options.Source_Selector`; the identical predicate, verbatim, at `src/flyology-object_storage-backends-files.adb:7602-7611` and `sqlite/src/flyology-object_storage-backends-sqlite.adb:2436-2445`; the server parsing that hands the selector through unaltered at `src/flyology-object_storage-server-s3_applications.adb:14080-14101`; the `Copy_Object` contract, which states no self-copy rule at all, at `src/flyology-object_storage-backends.ads:1969-2010`; the published claim at `docs/compatibility/s3.md:61` and the requirement at `docs/qualification/copy-object.md:39`.

**Repro:** `tests/repros/src/repro_backend_memory_2.adb`, exit status 1, eight failed expectations, covering the exact-version and null-version restores at the backend interface and the same restore over the in-process S3 application; the control that a same-key copy with no selector is still `Invalid_Request` passes, matching AWS and MinIO.

**What is wrong:** The self-copy guard compares only the source and destination bucket and key and the four directive fields and never looks at the source selector, so the operation S3 clients use to restore a previous version — CopyObject with `x-amz-copy-source: /bucket/key?versionId=OLD` and the same destination bucket and key — is answered `Invalid_Request` and HTTP 400 before the source snapshot is even fetched, and no generation is published. Every version-aware caller hits it: `aws s3api copy-object`, the AWS console's restore-previous-version action, and any lifecycle or rollback tooling built on the same idiom. It is fully deterministic and identical in all three backends, so the published compatibility claim of "retained exact source generations" with a "repeated six-server byte oracle" is not met for this input. Measured on the pinned MinIO release: a same-key copy naming `versionId=<v1>`, `versionId=null` or `versionId=<the current version>` all return 200, while a same-key copy with no version named returns 400 `InvalidRequest` — so the reference server's rule is "reject only when no source version is named", exactly the discriminator this predicate omits.

**Notes:** The MinIO evidence comes from the image digest pinned by `tests/scripts/test-minio.sh`, started by hand as a single detached container and driven with the `aws` CLI; the script itself was not run, so no `alr -n build` was triggered. No existing test asserts the wrong behaviour, the case is simply uncovered: `tests/src/copy_object_conformance.adb` uses no selector, and `tests/src/versioned_object_conformance.adb:335-345` and `:810-825` copy exact and null sources only to a different bucket and key. A fix is a maintainer decision about the guard's scope rather than a mechanical change: the narrow reading measured on MinIO is "reject only when `Options.Source_Selector.Kind = Current_Version`", which also permits an explicit copy of the current version onto itself, while a stricter reading would additionally reject an exact selector that resolves to the current generation. The choice is externally visible policy and belongs in the `Copy_Object` contract at `backends.ads:1969-2010`. Because the predicate is duplicated verbatim in the files and SQLite backends, one decision must be applied at all three sites together.

### BACKEND-MEMORY-3: Backend read contracts cannot report a selected delete marker, so GET/HEAD of a marker are plain `Not_Found`

**Severity:** P2 (the discovery report also said P2). This is the backend half of SERVER-2, which is the primary finding and carries the P1 severity assigned at the wire level; the backend-interface half is P2 on its own because both cases are wrong diagnostics rather than a wrong success or failure outcome.

**Location:** `src/flyology-object_storage-backends-memory.adb:318-329` (`Selected_Object_Index` returns 0 when the selected generation `Is_Delete_Marker`, for every selector kind including `Exact_Version`, and every read goes through it); `Head` at `:1729-1746`, `Attributes` at `:1748-1760` and `Fetch` at `:1562-1566`, all setting an empty record and `Not_Found`; the public types with no channel for the fact at `src/flyology-object_storage.ads:39-52` (`Status`) and `:554-562` (`Object_Information`); the read contracts at `src/flyology-object_storage-backends.ads:2049-2117`; the information that does exist in the store, `Listed_Version.Is_Delete_Marker` at `src/flyology-object_storage-backends.ads:98-104`, populated at `src/flyology-object_storage-backends-memory.adb:2671`; the tag, legal-hold, retention and attribute surfaces sharing the same blind spot at `:2016-2240` and `:1748-1794`; `GetObjectOutput.DeleteMarker` and `HeadObjectOutput.DeleteMarker` in `review/baseline/service-2.json`.

**Repro:** duplicate of SERVER-2, which is primary; it nonetheless contributes `tests/repros/src/repro_backend_memory_3.adb`, exit status 1, four failed expectations, and the pinned MinIO oracle. SERVER-2's own evidence is the wire-level `repro_server_2`.

**What is wrong:** `Selected_Object_Index` folds a delete marker into "no object" before any read can see it, and neither `Status` nor `Object_Information` can carry the fact, so the backend interface has no way to tell an adapter that the generation it selected is a marker. A caller cannot distinguish "this key is hidden by a delete marker" from "this key never existed", nor "this exact version is a marker" from "this version ID is unknown", through `Head_Object`, `Get_Object` or `Get_Object_Attributes`. Over HTTP that surfaces as a 404 with no `x-amz-delete-marker: true` for the current read and a 404 instead of a 405 with `Last-Modified` for an exact marker read. Anyone writing version-aware tooling hits it — bucket replication, backup and sync reconciliation, and anything that must reproduce delete markers keys on that header — and it is deterministic. The pinned model states both behaviours verbatim, and the pinned MinIO container answers exactly that way: HEAD of a marker-hidden key returns 404 with `x-amz-delete-marker: true` and `x-amz-version-id: <marker>`, and HEAD and GET of the exact marker version return 405.

**Notes:** This is an interface gap, not a memory-backend coding slip: the listing surface reports `Is_Delete_Marker` correctly (the repro's passing control), so the information exists in the store and only the read contracts cannot carry it. Neither the `.ads` contracts nor `docs/compatibility/s3.md` nor `docs/qualification/list-object-versions.md:139-140` promises or excludes the S3 behaviour, so this is contract drift against the pinned model rather than an `.ads` violation. An existing test asserts the current behaviour: `tests/src/versioned_object_conformance.adb` requires a simple delete to make marker reads `Not_Found`, so a fix must update that expectation. A fix is a public-interface decision — either a new `Status` value whose `Info` still carries `Modified` and `Version`, or an `Is_Delete_Marker` field on `Object_Information` — and either way it is a visible addition to `src/flyology-object_storage.ads`, must be reflected in the read contracts at `backends.ads:2049-2117`, and must be implemented identically in the files and SQLite backends. See SERVER-2 for the wire-level disposition.

## Coverage evidence: BACKEND-MEMORY

- `Owned_Bytes`: `Adjust` deep-copies, `Move` transfers ownership and zeroes the source, `Append` and `Reserve_Capacity` guard `Natural'Last`, and no aliasing exists between the store and returned snapshots.
- Reservation protocol: every path in `Put_Object_Internal`, `Put_Multipart_Part`, `Put_Object_Annotation`, `Copy_Object`, `Copy_Multipart_Part` and `Get_Object` releases exactly `Data.Capacity`; after a successful commit the buffer is moved so no double release is possible, and failed commits leave the reservation for the caller.
- `Commit`: conditions are evaluated against the current non-marker generation inside the protected action, overwrite capacity is computed correctly, the publication order is burned before the first mutation, and the unconfigured, suspended and enabled paths match the contract.
- Delete paths: unversioned physical delete, enabled marker append (also for absent keys, as S3 does), suspended null-marker replacement releasing the null generation's bytes, exact and null removal with legal-hold and retention refusal, MFA gating, and a full slot reset on every removal; batch behaviour matches the architecture document.
- Versioning transitions: `Merge_Bucket_Versioning` never returns to unconfigured, suspension is refused under Object Lock, and Object Lock, legal hold and retention all require enabled versioning.
- Listing builders apart from BACKEND-MEMORY-1: bytewise key ordering, prefix filter, delimiter projection, multi-byte delimiters, key-equals-prefix listed as an object, deduplicated common prefixes, exclusive `After` on the projected key, and the smallest `Maximum + 1` retention that makes `Is_Truncated` exact; `List_Versions` key-ascending, publication-descending, `Is_Latest` across markers, and paired-marker resume.
- Multipart lifecycle: unique per-store upload IDs, part overwrite releasing the old capacity, strictly-after `List_Parts` with exact truncation, completion validating ascending unique numbers, existence, ETag and checksum match, the 5 MiB non-final minimum and the destination conditions before publishing atomically, and `Delete_Bucket` refusing with active uploads.
- `Get_Object`: the snapshot is copied under the lock so a concurrent overwrite or delete cannot change the streamed bytes, `Resolve_Range` clamps and rejects as documented, and `Begin_Object` is called exactly once.
- Bucket configuration byte accounting: every put charges base plus incoming and every delete and bucket delete subtracts the same lengths, with no asymmetric path found; and no potentially blocking operation appears inside the protected object, with every compound operation a single protected action.
- Probe `tests/repros/src/repro_backend_memory_probe.adb`, exit status 0 (PASS): `Bytes_Used` returned to exactly the retained baseline after three successful GETs, a GET whose sink raised in `Begin_Object`, a GET whose sink raised in `Write`, a conditional GET rejected after reservation, an unsatisfiable-range GET, a copy followed by a delete, a conditional PUT rejected at publication, a capacity-rejected PUT and a multipart stage-then-abort, and to 0 after teardown — so the `Adjust` accounting anomaly below has no reachable underflow or leak.

## Observations not counted: BACKEND-MEMORY

- Documented policy: an overwrite, multipart completion or CopyObject needs coexistence headroom and every nonempty GET or copy reserves a full body snapshot, so reads can return `Capacity_Exceeded` near the byte cap (`docs/architecture/memory-backend.md`, asserted at `tests/src/object_storage_test_cases.adb:5230-5240`).
- Documented policy: unknown-length sources are charged allocator capacity through `Growth_Capacity` rather than logical size, and `Bytes_Used` reflects it.
- An unknown, stale or prefix-excluded paired `ListObjectVersions` cursor is `Invalid_Request` (`memory.adb:2675-2690`), pinned at `tests/src/versioned_object_conformance.adb:776` and named in `docs/qualification/list-object-versions.md:167`; measured, a client whose own cursor generation is permanently deleted between pages gets 400 and must restart the listing, while MinIO returns the remaining versions — but MinIO is a weak oracle here, because its `NextKeyMarker` is an opaque internal token rather than an AWS-shaped key marker, so settling this needs a real AWS account.
- A missing bucket is `Not_Found` from `Head`, `Attributes`, `List`, `List_Versions`, `List_Uploads` and `Start_Multipart` but `Bucket_Not_Found` from `Fetch`, tags, annotations and the delete paths; the contract requires the distinction only for `Delete_Object_Tags` (`backends.ads:2620-2622`) and the routes that care call `Head_Bucket` first, so it is contract drift with no reachable wrong answer today.
- In-place replacement does not reset a reused slot's `Legal_Hold` and `Retention` while a freed slot is fully reset; unreachable, because in-place replacement happens only under unconfigured or suspended versioning while a hold requires enabled versioning — worth a defensive reset if Object Lock is ever permitted under suspension.
- `Adjust` sets `Capacity := Length` before allocating, so a `Storage_Error` there could make the caller's `Release_Buffer` release a second time, either tripping the "memory reservation underflow" guard or silently borrowing a concurrent operation's accounting; re-derived precisely and shown unreachable by the probe above, since provoking it needs a real allocation failure at one specific instruction.
- `Include_Part_Digest` raises `Constraint_Error` for a part ETag that is not 32 hex characters (`memory.adb:219-241`); unreachable, because part ETags are always `GNAT.MD5.Digest` output, so it is an internal assertion.
- `List_Objects` and `List_Object_Versions` re-raise only cancellation and timeout and map everything else, including a `Program_Error` from an internal invariant, to `Backend_Unavailable`; that hides invariant failures behind a retryable status, a debugging and operability concern rather than a wrong answer.
- Linear scans in the index lookups and the O(n^2) `List_Versions` insertion are performance characteristics of a bounded reference oracle; they were not measured, since the host's power profile was not established.
