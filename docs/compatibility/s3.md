# S3 compatibility matrix

This matrix is an engineering gate, not a blanket compatibility claim.
“Backend” means the HTTP-independent primitive is implemented and covered by
the shared black-box suite. “Wire” requires an independent S3 protocol corpus.

| Area | Backend | Wire/client | Qualification |
|---|---:|---:|---|
| Create/Head bucket | memory, files, SQLite | client partial; authenticated path-style server | client oracle matrix + server raw-wire corpus |
| Delete bucket | memory, files, SQLite | client partial; authenticated path-style server | client oracle matrix + server raw-wire corpus |
| Put/Get/Head object | memory, files, SQLite | client partial; authenticated streaming server | backend + server raw-wire corpora |
| CopyObject | memory, files, SQLite | typed core client + authenticated path-style server partial | backend, signed raw-wire, typed six-server byte oracle, and s3t matrix |
| Delete object | memory, files, SQLite | client partial; authenticated path-style server | client oracle matrix + server raw-wire corpus |
| Single byte range | memory, files, SQLite | server bounded/open/suffix; client partial | backend + server raw-wire corpora |
| ListObjects v1 | memory, files, SQLite | generic client projection; authenticated path-style server partial | backend, signed raw-wire, and five-server s3t matrix |
| ListObjectsV2 | memory, files, SQLite | typed client + authenticated path-style server partial | backend, signed raw-wire, and six-server matrix |
| Multi-delete | composed from backend DeleteObject | typed request + authenticated server partial | strict server corpus + benchmark matrix |
| Multipart upload | memory, files, SQLite | typed signed client primitives + authenticated streaming server partial | backend persistence, loopback, and six-server forced-multipart byte oracle |
| UploadPartCopy | memory, files, SQLite | typed signed client + authenticated path-style server partial | backend, signed raw-wire, typed six-server byte oracle, and s3t matrix |
| SigV4 header signing | n/a | canonical signer | AWS published vectors |
| SigV4 presigning | n/a | planned | not claimed |
| Versioning, lifecycle, tags, lock | planned | planned | not claimed |

The wider wire gate will draw from Ceph s3-tests, AWS SDK integration tests,
MinIO/Mint-compatible cases, AWS SigV4 published examples, and project-owned
adversarial malformed-input corpora. Exact revisions and allowlists are pinned
as each lane becomes executable.

The machine-readable source of truth is
[coverage/aws-s3-operations.tsv](../../coverage/aws-s3-operations.tsv). It
contains every operation in the pinned botocore S3 model and distinguishes
traditional general-purpose S3 from extended and specialized APIs. Run
tools/verify-coverage.sh to validate the ledger. Immutable upstream revisions
are recorded in coverage/corpora.lock.toml.

`partial` in the machine ledger is not a compatibility claim. ListObjectsV2
has exact request signing, Flyology execution, bounded body consumption,
status/header handling, typed success/error decoding, project-owned
adversarial tests, and a raw-loopback HTTP socket gate exercised from both
native and Flyology lightweight tasks. Its basic path also passes against
digest-pinned RustFS, SeaweedFS and MinIO servers. Multipart initiation and
completion have strict request/result codecs, exact signed targets, checksummed
body validation, embedded HTTP-200 error handling, and the same
native/lightweight raw-loopback gate. UploadPart borrows rather than retains
its source, signs an explicit SHA-256 payload hash, and covers every modeled
checksum header. Each external lane uploads one 6 MiB object per task kind
from 997-byte source chunks, completes and lists each object through this
library, then re-reads both with digest-pinned s5cmd and checks a fixed SHA-256
oracle. The full matrix repeats all three lanes three times. RustFS and
SeaweedFS are Apache-2.0 and s5cmd is MIT; MinIO is a supplemental AGPL test
runtime, not the oracle. The cleanup phase deletes both objects through this
library, deletes the bucket, and requires s5cmd to observe the bucket as gone.
The setup phase creates the bucket through this library, heads it from both
native and Flyology lightweight tasks, and requires s5cmd to observe it; no
server lane receives pre-created bucket state. CreateBucket models every
pinned header and nested configuration field, and HeadBucket models every
pinned input and output field.
DeleteObject models every pinned request field and success response header;
DeleteBucket models its pinned owner precondition. These operations remain
partial until broader error, versioning, retention, and requester-pays
interoperability cases pass. The streaming operations remain partial until
broader option/header variants, trailer-based checksums, and HTTP/2 and HTTP/3
server streaming qualification pass. UploadPartCopy supports whole sources
and strict bounded byte ranges, quoted source ETag conditions, exact 5 GiB
part limits, immutable backend source snapshots, and fixed-length XML results.
Source versions, date conditions, encryption, ACLs, and replacement metadata
are rejected rather than silently ignored.
The typed client projects all 19 modeled request members, enforces complete
SSE-C header groups and the inclusive 5 GiB range ceiling, signs the exact
copy-source headers, decodes every modeled result header and CopyPartResult
checksum, and recognizes embedded HTTP-200 S3 errors. Its basic whole-source
path copies the deterministic 6 MiB multipart object in both native and
Flyology lightweight tasks on RustFS, SeaweedFS, supplemental MinIO, and all
three Flyology backends; digest-pinned s5cmd verifies the copied bytes.

Every one of the 116 pinned operations now has exhaustive generated-model
request projection and can execute through the generic low-level boundary,
which returns Flyology HTTP's limited streaming response without retaining an
arbitrary body. The projector covers modeled method, URI labels and fixed
queries, query/header/header-map members, required top-level members, scalar
enums and bounds, addressing, SigV4, and retained raw payloads. Accordingly,
the client ledger records `partial` for this exact common substrate. It does
not mean an operation has its typed body codec, typed response decoder,
streaming request-source path, semantic policy, or independent interoperability
corpus; those remain required before any operation becomes `complete`.

The server `partial` entries cover authenticated path-style requests. The
project-owned raw-wire corpus signs real SigV4 requests and
checks authentication before `100 Continue`, fixed-length and chunked PUT,
payload-hash mismatch rollback, whole and suffix GET, unsatisfiable range
metadata, cancellation/deadline propagation, ETags, and lifecycle cleanup.
A shared digest-pinned s5cmd slice now creates a bucket; uploads empty,
deterministic 4 KiB, deterministic 2 MiB, and forced two-part 6 MiB objects;
exercises a nested key
containing a space, plus sign, and percent escape; and overwrites a small
object with the large payload. It heads and re-reads every object with exact
SHA-256 checks, then requires a wrong secret, an unknown access key, and an
unexpected session token to be rejected. The identical slice passes against
RustFS, SeaweedFS, supplemental MinIO, and the Flyology memory, files, and
SQLite servers.
DeleteObjects accepts the exact `delete` subresource forms, validates a
bounded 1,000-key REST/XML document and payload hash, supports quiet results,
and reports unsupported version IDs per key without deleting current data.
It remains partial pending a typed response decoder/client operation,
Content-MD5/checksum policy, versioned backends, and broader error oracles.
This is evidence only for those operations; broader AWS SDK corpora and
reference-behavior differentials remain pending. Indexed
`flyology_http=0.1.2` provides 64-bit request accounting, a 50 TB streaming
ceiling, per-route `Body_Size` limits, and exact-length response streaming;
GET and HEAD framing is qualified against that release.

CopyObject uses one immutable backend-owned source snapshot and atomic
destination publication; it does not retain the object in the HTTP
application. The qualified slice covers zero-byte and 16 MiB copies, same- and
cross-bucket targets, content-type preservation, missing source bucket/key,
metadata-preserving self-copy rejection, and quoted source ETag conditions.
The typed core client signs source conditions, Content-Type, metadata
directive, requester-pays, and expected-owner fields; decodes every modeled
output header and CopyObjectResult checksum; and recognizes embedded HTTP-200
S3 errors. Both task models copy the deterministic 6 MiB object on the two
permissive references, supplemental MinIO, and all three Flyology backends,
with digest-pinned s5cmd verifying the destination bytes.
The high-level `Client.Transfers.Copy_Object` path repeats that matrix from a
source key containing spaces, plus, and percent bytes; it owns copy-source
encoding/signing and returns compact copy metadata or the structured S3 error.
User metadata, ACLs, source date conditions, source versions, and replacement
metadata beyond Content-Type are rejected rather than silently discarded.

ListObjects v1 and v2 use the same bounded backend page contract across
memory, files, and SQLite. Both provide bytewise lexical ordering, prefix
filtering, delimiter/CommonPrefixes grouping, max-keys 0..1000, URL-encoded
response fields, 64-bit sizes, quoted ETags, and fixed-length XML responses.
V1 implements exclusive markers and delimiter-scoped NextMarker; v2
implements exclusive StartAfter and opaque continuation tokens bound to
bucket/prefix/delimiter.
The strict corpus covers malformed and duplicate queries, invalid and
cross-scope tokens, pagination, cancellation/deadline propagation, missing
buckets, and exact counts. The shared s5cmd slice passes against RustFS,
SeaweedFS, MinIO, and all three Flyology backends. It remains partial pending
owner projection, requester-pays/expected-owner policy, version-aware
listing, broader AWS SDK differentials, and performance tuning at large
namespace sizes.

The checked [`s3t` allowlist](../../coverage/s3t-allow.txt) adds 113
Ceph-compatible AWS SDK v2 tests for bucket lifecycle and HEAD, ListObjects v1
and v2 prefix/delimiter/marker/max-keys/encoding behavior, object
overwrite/read/delete/HEAD and absent-bucket handling, basic CopyObject across
buckets and zero/16 MiB bodies with ETag source conditions, bounded/open/
suffix/empty and invalid ranges, multipart create/abort/complete/error paths,
and UploadPartCopy whole/ranged/special-key/percent-encoded/multi-size paths.
The runner requires
the exact pinned s3t revision, rejects dirty binaries, runs four workers, and
retains JSON. Memory, files, and SQLite pass 113/113. RustFS passes 112 with one
pinned xfail for returning `InvalidArgument` instead of `NoSuchUpload`;
SeaweedFS 4.43 passes 107 with
pinned xfails for accepting deletion of a nonempty bucket, accepting PutObject
to an absent bucket, and reversing special-character common-prefix order under
URL encoding in both listing generations, plus accepting invalid and inverted
UploadPartCopy source ranges.
Supplemental MinIO passes 106 with seven exact pinned xfails: its empty multipart
completion error code, two internal legacy-marker exposures, an explicitly
empty v2 continuation token, and URL encoding of spaces in both listing
generations, plus returning `InvalidArgument` instead of `InvalidRange` for an
out-of-bounds UploadPartCopy range. It remains a compatibility target rather than an oracle because
the test runtime is AGPL-3.0-only.
Any other failure or an unexpected pass fails qualification. This corpus
exposed and closed AWS SDK `x-id` routing failures, the previously collapsed
multipart error codes `InvalidPartOrder`, `InvalidPart`, and `EntityTooSmall`,
incorrect `max-keys=0` truncation, `NoSuchKey` in place of `NoSuchBucket` for
PutObject, and slash-overencoding in v1 listing responses. The separate
special-key naming and return-data nodes remain outside this allowlist because
they proceed into object ACL operations, which are not yet implemented and
are not emulated as no-ops.
