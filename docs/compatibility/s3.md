“Backend” means the HTTP-independent primitive is implemented and covered by
the shared black-box suite. “Wire” requires an independent S3 protocol corpus.

The wider wire gate will draw from Ceph s3-tests, AWS SDK integration tests,
MinIO/Mint-compatible cases, AWS SigV4 published examples, and project-owned
adversarial malformed-input corpora. Exact revisions and allowlists are pinned
as each lane becomes executable.

The machine-readable source of truth is
[coverage/aws-s3-operations.tsv](../../coverage/aws-s3-operations.tsv). It
contains every operation in the pinned botocore S3 model and distinguishes
traditional general-purpose S3 from extended and specialized APIs. Run
tools/verify-coverage.sh to validate the ledger. Immutable upstream revisions
are recorded in coverage/corpora.lock.toml.

PutBucketVersioning and GetBucketVersioning cover configuration state only.
Unconfigured, Enabled, and Suspended remain distinct, and memory, files, and
SQLite update that state atomically. The strict 4 KiB XML codec, query/header
validation, Content-MD5, all ten modeled concrete checksum algorithms and
physical trailers, expected-owner authorization, typed low-level calls, and
status-only plus complete-configuration convenience calls are gated by unit,
signed in-process, fragmented socket, restart, crash-barrier, race, and
independent implementation tests. MFA Delete uses a pluggable bounded
root-owner/device verifier, requires HTTPS, fails closed when the verifier is
absent or unavailable, and rechecks the current MFA requirement inside the
backend publication boundary. External server lanes cannot exercise MFA Delete
without their bucket owner's physical MFA device; the deterministic signed
application corpus covers valid, missing, invalid, duplicate, overlong,
insecure, non-root, unavailable, null, and raising verifier paths. This
configuration evidence alone does not claim a retained-generation data plane.
ListObjectVersions additionally has bounded retained-generation and
delete-marker state machines in memory, files, and SQLite plus authenticated
memory-backed and SQLite-backed server routes. SQLite qualifies ordinary
version-aware PUT, current/null/exact reads, tags and part attributes,
enabled/suspended markers, exact deletion, retained multipart completion,
reopen recovery, and one authenticated black-box generation/marker lifecycle
that is repeated across an authenticated server process restart. Files uses
immutable per-key retained files, bounded-memory listing, durable marker and
null replacement, generation-bound reopen reads, and pre/post barrier crash
oracles. Each backend snapshot collapses every
delimiter-scoped generation group into one common prefix, counts versions,
delete markers, and common prefixes against the same page maximum, and binds
truncated continuation to the last underlying generation hidden by the
returned prefix.

ListObjects v1 accounts for all nine modeled inputs, the top-level
request-charged output, and all nested Object members, including flattened
checksum algorithms, checksum type, owner, and restore status. FetchOwner is
not an input in the pinned v1 model. ListObjects v1 and v2 have exact
request signing, Flyology execution, bounded body consumption, status/header
handling, typed success/error decoding, project-owned adversarial tests, and
a raw-loopback HTTP socket gate exercised from both native and Flyology
lightweight tasks. V1 also exposes an owner-driven operation with typed
failure/admission normalization, exact prepared-response binding, restart
after Finish, and a synchronous parameter-record wrapper that waits on that
same state machine. Its convenience marker fallback runs only after the typed
response completes. V2 additionally preserves absent versus present-empty
continuation tokens and absent versus explicit-false fetch-owner requests,
and accounts for all 11 modeled inputs and all 13 top-level outputs. Their
basic paths also pass against digest-pinned RustFS,
SeaweedFS and MinIO servers. The three pinned external servers publish a
non-model `NextMarker` on truncated v1 pages without a delimiter. The strict
no-delimiter continuation assertion is therefore excluded only for those
external lanes; Flyology memory, files, and SQLite pass the AWS fallback rule
through native and lightweight clients. Multipart initiation and
completion have strict request/result codecs, exact signed targets, checksummed
body validation, embedded HTTP-200 error handling, and the same
native/lightweight raw-loopback gate. ListParts has a typed signed client for
all ten request members, all three response headers, and a bounded result
codec for every modeled XML member, including every checksum,
owner/initiator identity, and strict pagination invariants. The public
one-page API binds bucket, key, upload ID, marker, and maximum to the prepared
request; raw native/lightweight sockets independently mutate each echo and
physical singleton rule. Its implementation matrix passes three repetitions
against digest-pinned RustFS, MinIO, and Flyology memory/files/SQLite servers.
The Flyology general-purpose server enforces matching owner, strict
requester-pays, complete SSE-C, HTTPS, and key/digest admission before it
parses the listing query or observes multipart state. Valid but unavailable
billing and SSE-C policies return authenticated `NotImplemented`. It returns
persisted multipart checksum algorithm/type and stored part checksums.
MinIO also returns those checksum members in the live checksum corpus. The
pinned RustFS and SeaweedFS releases accept the configured SHA-256 multipart
upload but omit the upload algorithm/type and per-part checksum from
ListParts; their runners report and narrowly exclude those missing members.
Pinned SeaweedFS 4.43 also repeats a part at or below the supplied marker on a
second page, so its real continuation oracle is excluded rather than weakening
the monotonic decoder. RustFS, supplemental MinIO, and all Flyology backends
pass the two-part, two-page continuation check. The Flyology response omits
optional lifecycle and owner/initiator fields because those policies are not
configured; directory buckets remain outside this path-style claim.

The checksum corpus creates a true 5 MiB + 1 MiB SHA-256/COMPOSITE upload,
sends and verifies each raw part checksum, completes with the raw whole-object
integrity assertion plus exact object size, and requires the canonical
`base64-2` completed-object value from conforming lanes. Flyology memory,
files, and SQLite retain that value and the raw part values across ListParts,
HeadObject, and GetObjectAttributes. Completion failures preserve both the
active upload and any prior destination. SeaweedFS 4.43 accepts the checksum
assertions but omits checksum/type members from CompleteMultipartUpload and
GetObjectAttributes as well as ListParts; its high-level checksummed-upload
oracle is therefore disabled rather than accepting unverifiable success.
RustFS 1.0.0-rc.3 returns the completed object checksum, but its
GetObjectAttributes response incorrectly repeats the whole `base64-2` value
for an individual part. The oracle verifies the overall checksum separately,
then requires the ObjectParts request to hit the strict decoder's
`Invalid_Response` path; the raw-part decoder is not weakened for that
response. SeaweedFS's GetObjectAttributes response is safely decoded and must
retain the exact observed absence of both overall and per-part checksums.
ListMultipartUploads has a bounded codec for all 12 REST/XML body members of
its pinned output shape and all eight members of each nested upload, including
independent owner/initiator presence, checksum algorithm/type, common prefixes,
encoding type, and both marker pairs. Its strict corpus rejects duplicate or
incomplete structures, invalid timestamps and enums, conflicting checksum
policy, combined-page overflow, grouped-upload duplication, and stale marker
pairs. The typed request, response header, and bounded execution layers cover
all nine modeled inputs and the sole response header. The public page API
binds every echoed scope field and preserves its paired cursor; native and
lightweight raw-loopback tests mutate those bindings independently. All three
backends now return an atomic,
bounded active-upload snapshot with key and initiation-time ordering, exact
upload-ID marker filtering, prefix/delimiter grouping, initiation metadata,
and completion/abort visibility; files and SQLite preserve the listing across
reopen. The authenticated general-purpose server implements strict query
parsing, bounded pagination, delimiter grouping, URL encoding, expected-owner
enforcement, and typed errors. It accepts only the modeled `requester` billing
token and returns authenticated `NotImplemented` because Requester Pays bucket
policy is not configured; invalid and duplicate values fail before the backend
listing. Directory buckets remain outside this path-style claim. Native and
lightweight clients pass active/retired-upload checks against RustFS,
supplemental MinIO, and Flyology memory/files/SQLite. RustFS omits the
model-optional StorageClass field, which the client now preserves as absent.
Pinned SeaweedFS 4.43 is explicitly excluded from this operation's positive
oracle: a fresh exact-limit response reports truncation but omits
NextKeyMarker, and also omits initiation metadata, so it cannot supply a valid
continuation contract. Other SeaweedFS operation gates remain enabled.

UploadPart borrows rather than retains its forward-only source, signs an
explicit SHA-256 payload hash, and covers every modeled checksum header and all
17 modeled response headers. Rewindable sources are rejected before HTTP
admission and the client never transparently retries. Any exception other than
the wrapper's pre-admission Invalid_Request is conservatively ambiguous and
requires exact upload-ID/part-number reconciliation through ListParts. Each
external lane uploads one 6 MiB object per task kind through the public
synchronous API from 997-byte source chunks, completes and lists each object
through this library, then re-reads both with digest-pinned s5cmd and checks a
fixed SHA-256 oracle. The full matrix repeats all three lanes three times.
The additive composable form instead moves an acquired bounded buffer token
into an owner-driven operation and restores the exact token at typed Finish.
Its synchronous buffer overload waits on that same state machine. A complete
validated 200 proves the part was staged; definite non-admission proves it was
not staged; every other terminal state remains unknown and requires ListParts.
The socket corpus gates successful token restoration, pre-admission
cancellation, exact lost-response `Possibly_Admitted` certainty, and read-only
reconciliation without replay.
CompleteMultipartUpload likewise owns its exact serialized XML in a one-shot
owner-driven operation, and the synchronous typed overload waits on that same
state machine. Only a complete validated success is conclusive. All complete
service rejections—including error XML embedded in HTTP 200—and every failure
after possible admission remain unknown. The socket corpus drops an accepted
completion response and then proves the exact published bytes through whole
Get without replaying completion; callers must also reconcile the exact upload
before selecting retry or abort.
AbortMultipartUpload uses the same owner-driven one-shot boundary with a
non-rewindable empty source. Only a complete validated 204 proves acceptance;
every complete rejection and every failure after possible admission remains
unknown. The socket corpus proves pre-admission cancellation, restart,
physical singleton response-header validation, and a lost accepted response
followed immediately by exact-upload ListParts reconciliation rather than a
replayed DELETE.
RustFS and
SeaweedFS are Apache-2.0 and s5cmd is MIT; MinIO is a supplemental AGPL test
runtime, not the oracle. The cleanup phase deletes both objects through this
library, deletes the bucket, and requires s5cmd to observe the bucket as gone.
The setup phase creates the bucket through this library, heads it from both
native and Flyology lightweight tasks, and requires s5cmd to observe it; no
server lane receives pre-created bucket state. CreateBucket models every
pinned header and nested configuration field. Its strict bounded parser
rejects unknown, duplicate, misplaced, incomplete, oversized, or invalid
configuration members, including duplicate and excessive tags. The
convenience client creates a general-purpose bucket and supplies the signing
region as LocationConstraint when AWS requires it. Native and lightweight
clients use that API for setup in three repeated runs across RustFS,
SeaweedFS, supplemental MinIO, and all three Flyology backends. The Flyology
server implements the general-purpose private/BucketOwnerEnforced subset,
normalizes the legacy EU constraint, enforces endpoint-region compatibility,
and mutates backend state only after validation. Directory buckets, tags,
grants, public ACLs, Object Lock, non-enforced ownership, and bucket namespace
controls return explicit NotImplemented errors instead of being silently
discarded. Empty or malformed controls are rejected before those capability
decisions and before backend mutation.
HeadBucket is complete end to end: the server returns its configured region on
successful, forbidden, and missing-bucket responses, enforces the
expected-owner precondition, and rejects duplicate owner fields. The typed
client validates bodylessness, region syntax, location types and bounded
headers while preserving every pinned output. The convenience API falls back
to the request's signing region when a compatible server omits the optional
response header, a measured RustFS 1.0.0-rc.3 behavior. Native and lightweight
clients pass three repeated runs across RustFS, SeaweedFS, supplemental MinIO,
and all three Flyology backends.
The additive composable client owns the signed request, retains no borrowed
request input after initiation, validates complete response metadata through
the same decoder as the blocking path, and preserves HTTP admission and typed
failure state. Its parameter-record synchronous overload waits that same
owner-driven operation; the established convenience overload now uses the same
state machine. Native and lightweight socket lanes gate fragmented metadata,
bodyless rejection identifiers, duplicate singleton rejection, pre-admission
cancellation and deadline behavior, and same-owner restart.
GetBucketLocation is complete end to end. The server checks bucket existence,
uses the configured SigV4 region, and emits AWS's null scalar for us-east-1.
The bounded client parser preserves strict root, nesting, size, depth, and
enumeration checks while accepting two measured compatibility spellings:
RustFS 1.0.0-rc.3 returns literal us-east-1, and SeaweedFS 4.43 returns one
LocationConstraint inside a CreateBucketConfiguration wrapper. The
convenience API normalizes empty and literal us-east-1 to us-east-1, and EU to
eu-west-1, while preserving the observed legacy constraint. Native and
lightweight typed clients pass against both permissive references,
supplemental MinIO, and all three Flyology backends.
The provider-owned composable form retains the signed request and bounded XML
response through terminal drain, preserves typed HTTP failure and admission
state, and supports same-owner restart after `Finish`. Its parameter-record
synchronous overload waits on that same operation, and the convenience form
applies its compatibility normalization only after typed completion. The
signed native/lightweight socket corpus gates fragmented success, owner-header
binding, modeled rejection, and reusable operation restart.
DeleteBucket is complete end to end. The shared server owner policy rejects
mismatched and duplicate expected-owner fields, the route rejects request
bodies, nonempty buckets remain intact with BucketNotEmpty, and success is an
empty 204. Its limited constructor, operation-last reusable initiation, typed
Finish, and parameter-record synchronous overload share one non-replaying
state machine. Failures after possible admission require caller-selected
HeadBucket reconciliation before retry. The typed and convenience clients delete every matrix-created
bucket after independent s5cmd confirms object cleanup. DeleteObject models
every pinned request field and success response header. Its shared strict
query parser bounds and decodes versionId and the SDK operation ID, rejects
duplicates and unknowns after authentication, and shares one 1,024-byte,
NUL-free version rule with multi-delete and response validation. The
convenience client exposes ordinary deletion and all modeled controls, including
version selection, If-Match, owner preconditions, Requester Pays, MFA,
governance bypass, and directory-bucket predicates. All matrix cleanup runs
through the convenience API. The Flyology server supports idempotent current,
null, and exact-generation deletion, marker publication, atomic If-Match,
expected-owner policy, and pluggable secure-transport MFA verification. It
distinguishes an absent bucket from an absent key atomically in every backend
and rejects bodies before mutation. Requester Pays and a true
governance-retention bypass return explicit NotImplemented errors; a false

AWS's primary request model exposes both `partNumber` and `Range` and states no
mutual exclusion. Flyology's explicit, corpus-gated composition resolves the
range within the selected part.
For multipart `Range` reads without `partNumber`, both HeadObject and GetObject
deliberately omit checksum response headers: the current bounded backend
snapshot cannot map an arbitrary or exactly aligned range to all retained part
boundaries atomically.
GetObject part selection, non-null versions, and encrypted SSE-C objects remain
explicit cross-cutting exclusions.

ListObjects v1 and v2 use the same bounded backend page contract across
memory, files, and SQLite. Both provide bytewise lexical ordering, prefix
filtering, delimiter/CommonPrefixes grouping, max-keys 0..1000, URL-encoded
response fields, 64-bit sizes, quoted ETags, and fixed-length XML responses.
Both response decoders share the entity-safe SAX boundary with explicit
document, nesting, element, and text ceilings; the v1 decoder additionally
checks delimiter-scoped NextMarker consistency before publishing a page.
V1 implements exclusive markers and delimiter-scoped NextMarker. Without a
delimiter, the convenience client derives the next exclusive marker from the
last returned object key; URL-encoded cursors are strictly decoded before the
next request signs and encodes them again. V2
implements exclusive StartAfter and opaque continuation tokens bound to the
bucket, prefix, delimiter, and exclusive cursor. A backend call takes one
atomic namespace snapshot, so page construction cannot mix states; a later
page deliberately observes later mutations while the scoped cursor prevents
duplicates at or before its boundary.

The ListObjects v1 server projects the authenticated principal into each
returned object owner. Both listing servers enforce expected-owner, accept a
syntactically valid Requester Pays input as an authenticated owner request
without fabricating a charged header, and accept `RestoreStatus` while
omitting it for the supported non-archival objects. The ListObjectsV2 server
projects the authenticated principal only when `fetch-owner=true`. Optional
request and response members preserve presence independently, including
explicit false, zero, and empty values where AWS accepts them. The strict
corpus covers malformed and duplicate queries, invalid and cross-scope tokens,
pagination under mutation, multi-character delimiters,
cancellation/deadline propagation, missing buckets, exact counts, response
headers, and convenience-client token propagation. Native and Flyology
lightweight clients repeat the operation against RustFS, SeaweedFS, MinIO,
and all three Flyology backends. The five-server v1 and v2 benchmarks
independently require exact ordered 64-key raw XML pages before and after
measurement. The v1 oracle additionally excludes v2-only `KeyCount` and
continuation-token elements and requires the v1 `Marker` shape.

This covered row is scoped to current objects in general-purpose buckets. It
does not claim directory-bucket sessions, archival restore state, object
version history, or requester-billing bucket policy; unavailable fields and
headers are omitted rather than fabricated. Those are separate storage or
service features, not weakened pagination behavior.
