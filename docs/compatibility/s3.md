“Backend” means the HTTP-independent primitive is implemented and covered by
the shared black-box suite. “Wire” requires an independent S3 protocol corpus.

The wider wire gate will draw from Ceph s3-tests, AWS SDK integration tests,
MinIO/Mint-compatible cases, AWS SigV4 published examples, and project-owned
adversarial malformed-input corpora. Exact revisions and allowlists are pinned
as each lane becomes executable.

The machine-readable source of truth is
[coverage/aws-s3-operations.tsv](../../coverage/aws-s3-operations.tsv). It
contains every operation in the pinned botocore S3 model and distinguishes
traditional general-purpose S3 from extended and specialized APIs. Run
tools/verify-coverage.sh to validate the ledger. Immutable upstream revisions
are recorded in coverage/corpora.lock.toml.

PutBucketVersioning and GetBucketVersioning cover configuration state only.
Unconfigured, Enabled, and Suspended remain distinct, and memory, files, and
SQLite update that state atomically. The strict 4 KiB XML codec, query/header
validation, Content-MD5, all ten modeled concrete checksum algorithms and
physical trailers, expected-owner authorization, typed low-level calls, and
status-only plus complete-configuration convenience calls are gated by unit,
signed in-process, fragmented socket, restart, crash-barrier, race, and
independent implementation tests. MFA Delete uses a pluggable bounded
root-owner/device verifier, requires HTTPS, fails closed when the verifier is
absent or unavailable, and rechecks the current MFA requirement inside the
backend publication boundary. External server lanes cannot exercise MFA Delete
without their bucket owner's physical MFA device; the deterministic signed
application corpus covers valid, missing, invalid, duplicate, overlong,
insecure, non-root, unavailable, null, and raising verifier paths. This
configuration evidence alone does not claim a retained-generation data plane.
ListObjectVersions additionally has bounded retained-generation and
delete-marker state machines in memory and SQLite plus authenticated
memory-backed and SQLite-backed server routes. SQLite qualifies ordinary
version-aware PUT, current/null/exact reads, tags and part attributes,
enabled/suspended markers, exact deletion, retained multipart completion,
reopen recovery, and one authenticated black-box generation/marker lifecycle
that is repeated across an authenticated server process restart. Files
retained generations remain absent. The memory
snapshot collapses every
delimiter-scoped generation group into one common prefix, counts versions,
delete markers, and common prefixes against the same page maximum, and binds
truncated continuation to the last underlying generation hidden by the
returned prefix.

ListObjects v1 accounts for all nine modeled inputs, the top-level
request-charged output, and all nested Object members, including flattened
checksum algorithms, checksum type, owner, and restore status. FetchOwner is
not an input in the pinned v1 model. ListObjects v1 and v2 have exact
request signing, Flyology execution, bounded body consumption, status/header
handling, typed success/error decoding, project-owned adversarial tests, and
a raw-loopback HTTP socket gate exercised from both native and Flyology
lightweight tasks. V2 additionally preserves absent versus present-empty
continuation tokens and absent versus explicit-false fetch-owner requests,
and accounts for all 11 modeled inputs and all 13 top-level outputs. Their
basic paths also pass against digest-pinned RustFS,
SeaweedFS and MinIO servers. The three pinned external servers publish a
non-model `NextMarker` on truncated v1 pages without a delimiter. The strict
no-delimiter continuation assertion is therefore excluded only for those
external lanes; Flyology memory, files, and SQLite pass the AWS fallback rule
through native and lightweight clients. Multipart initiation and
completion have strict request/result codecs, exact signed targets, checksummed
body validation, embedded HTTP-200 error handling, and the same
native/lightweight raw-loopback gate. ListParts has a typed signed client for
all ten request members, all three response headers, and a bounded result
codec for every modeled XML member, including every checksum,
owner/initiator identity, and strict pagination invariants. The public
one-page API binds bucket, key, upload ID, marker, and maximum to the prepared
request; raw native/lightweight sockets independently mutate each echo and
physical singleton rule. Its implementation matrix passes three repetitions
against digest-pinned RustFS, MinIO, and Flyology memory/files/SQLite servers.
The Flyology general-purpose server enforces matching owner, strict
requester-pays, complete SSE-C, HTTPS, and key/digest admission before it
parses the listing query or observes multipart state. Valid but unavailable
billing and SSE-C policies return authenticated `NotImplemented`. It returns
persisted multipart checksum algorithm/type and stored part checksums.
MinIO also returns those checksum members in the live checksum corpus. The
pinned RustFS and SeaweedFS releases accept the configured SHA-256 multipart
upload but omit the upload algorithm/type and per-part checksum from
ListParts; their runners report and narrowly exclude those missing members.
Pinned SeaweedFS 4.43 also repeats a part at or below the supplied marker on a
second page, so its real continuation oracle is excluded rather than weakening
the monotonic decoder. RustFS, supplemental MinIO, and all Flyology backends
pass the two-part, two-page continuation check. The Flyology response omits
optional lifecycle and owner/initiator fields because those policies are not
configured; directory buckets remain outside this path-style claim.

The checksum corpus creates a true 5 MiB + 1 MiB SHA-256/COMPOSITE upload,
sends and verifies each raw part checksum, completes with the raw whole-object
integrity assertion plus exact object size, and requires the canonical
`base64-2` completed-object value from conforming lanes. Flyology memory,
files, and SQLite retain that value and the raw part values across ListParts,
HeadObject, and GetObjectAttributes. Completion failures preserve both the
active upload and any prior destination. SeaweedFS 4.43 accepts the checksum
assertions but omits checksum/type members from CompleteMultipartUpload and
GetObjectAttributes as well as ListParts; its high-level checksummed-upload
oracle is therefore disabled rather than accepting unverifiable success.
RustFS 1.0.0-rc.3 returns the completed object checksum, but its
GetObjectAttributes response incorrectly repeats the whole `base64-2` value
for an individual part. The oracle verifies the overall checksum separately,
then requires the ObjectParts request to hit the strict decoder's
`Invalid_Response` path; the raw-part decoder is not weakened for that
response. SeaweedFS's GetObjectAttributes response is safely decoded and must
retain the exact observed absence of both overall and per-part checksums.
ListMultipartUploads has a bounded codec for all 12 REST/XML body members of
its pinned output shape and all eight members of each nested upload, including
independent owner/initiator presence, checksum algorithm/type, common prefixes,
encoding type, and both marker pairs. Its strict corpus rejects duplicate or
incomplete structures, invalid timestamps and enums, conflicting checksum
policy, combined-page overflow, grouped-upload duplication, and stale marker
pairs. The typed request, response header, and bounded execution layers cover
all nine modeled inputs and the sole response header. The public page API
binds every echoed scope field and preserves its paired cursor; native and
lightweight raw-loopback tests mutate those bindings independently. All three
backends now return an atomic,
bounded active-upload snapshot with key and initiation-time ordering, exact
upload-ID marker filtering, prefix/delimiter grouping, initiation metadata,
and completion/abort visibility; files and SQLite preserve the listing across
reopen. The authenticated general-purpose server implements strict query
parsing, bounded pagination, delimiter grouping, URL encoding, expected-owner
enforcement, and typed errors. It accepts only the modeled `requester` billing
token and returns authenticated `NotImplemented` because Requester Pays bucket
policy is not configured; invalid and duplicate values fail before the backend
listing. Directory buckets remain outside this path-style claim. Native and
lightweight clients pass active/retired-upload checks against RustFS,
supplemental MinIO, and Flyology memory/files/SQLite. RustFS omits the
model-optional StorageClass field, which the client now preserves as absent.
Pinned SeaweedFS 4.43 is explicitly excluded from this operation's positive
oracle: a fresh exact-limit response reports truncation but omits
NextKeyMarker, and also omits initiation metadata, so it cannot supply a valid
continuation contract. Other SeaweedFS operation gates remain enabled.

UploadPart borrows rather than retains its forward-only source, signs an
explicit SHA-256 payload hash, and covers every modeled checksum header and all
17 modeled response headers. Rewindable sources are rejected before HTTP
admission and the client never transparently retries. Any exception other than
the wrapper's pre-admission Invalid_Request is conservatively ambiguous and
requires exact upload-ID/part-number reconciliation through ListParts. Each
external lane uploads one 6 MiB object per task kind through the public
synchronous API from 997-byte source chunks, completes and lists each object
through this library, then re-reads both with digest-pinned s5cmd and checks a
fixed SHA-256 oracle. The full matrix repeats all three lanes three times.
RustFS and
SeaweedFS are Apache-2.0 and s5cmd is MIT; MinIO is a supplemental AGPL test
runtime, not the oracle. The cleanup phase deletes both objects through this
library, deletes the bucket, and requires s5cmd to observe the bucket as gone.
The setup phase creates the bucket through this library, heads it from both
native and Flyology lightweight tasks, and requires s5cmd to observe it; no
server lane receives pre-created bucket state. CreateBucket models every
pinned header and nested configuration field. Its strict bounded parser
rejects unknown, duplicate, misplaced, incomplete, oversized, or invalid
configuration members, including duplicate and excessive tags. The
convenience client creates a general-purpose bucket and supplies the signing
region as LocationConstraint when AWS requires it. Native and lightweight
clients use that API for setup in three repeated runs across RustFS,
SeaweedFS, supplemental MinIO, and all three Flyology backends. The Flyology
server implements the general-purpose private/BucketOwnerEnforced subset,
normalizes the legacy EU constraint, enforces endpoint-region compatibility,
and mutates backend state only after validation. Directory buckets, tags,
grants, public ACLs, Object Lock, non-enforced ownership, and bucket namespace
controls return explicit NotImplemented errors instead of being silently
discarded. Empty or malformed controls are rejected before those capability
decisions and before backend mutation.
HeadBucket is complete end to end: the server returns its configured region on
successful, forbidden, and missing-bucket responses, enforces the
expected-owner precondition, and rejects duplicate owner fields. The typed
client validates bodylessness, region syntax, location types and bounded
headers while preserving every pinned output. The convenience API falls back
to the request's signing region when a compatible server omits the optional
response header, a measured RustFS 1.0.0-rc.3 behavior. Native and lightweight
clients pass three repeated runs across RustFS, SeaweedFS, supplemental MinIO,
and all three Flyology backends.
GetBucketLocation is complete end to end. The server checks bucket existence,
uses the configured SigV4 region, and emits AWS's null scalar for us-east-1.
The bounded client parser preserves strict root, nesting, size, depth, and
enumeration checks while accepting two measured compatibility spellings:
RustFS 1.0.0-rc.3 returns literal us-east-1, and SeaweedFS 4.43 returns one
LocationConstraint inside a CreateBucketConfiguration wrapper. The
convenience API normalizes empty and literal us-east-1 to us-east-1, and EU to
eu-west-1, while preserving the observed legacy constraint. Native and
lightweight typed clients pass against both permissive references,
supplemental MinIO, and all three Flyology backends.
DeleteBucket is complete end to end. The shared server owner policy rejects
mismatched and duplicate expected-owner fields, the route rejects request
bodies, nonempty buckets remain intact with BucketNotEmpty, and success is an
empty 204. The typed and convenience clients delete every matrix-created
bucket after independent s5cmd confirms object cleanup. DeleteObject models
every pinned request field and success response header. Its shared strict
query parser bounds and decodes versionId and the SDK operation ID, rejects
duplicates and unknowns after authentication, and shares one 1,024-byte,
NUL-free version rule with multi-delete and response validation. The
convenience client exposes ordinary deletion and all modeled controls, including
version selection, If-Match, owner preconditions, Requester Pays, MFA,
governance bypass, and directory-bucket predicates. All matrix cleanup runs
through the convenience API. The Flyology server supports idempotent unversioned
deletion, atomic If-Match, expected-owner policy, and pluggable secure-transport
MFA verification. It distinguishes an absent bucket from an absent key
atomically in every backend and rejects bodies before mutation. Object-version
deletion, Requester Pays, and a true governance-retention bypass return explicit
NotImplemented errors; a false bypass value is a no-op. Directory-only
modification-time and size conditions are parsed strictly and rejected as
InvalidArgument until directory buckets exist. A configured bucket versioning
or MFA Delete state prevents current-object removal at the backend publication
boundary. Low- and high-level DeleteObject calls use a one-shot empty HTTP
source so the HTTP method's nominal idempotency cannot replay an accepted
conditional delete after a lost response. A transport, timeout, or cancellation
exception is consequently publication-ambiguous and requires exact-key or
generation reconciliation before retry. The low-level client decodes
structured 409 Conflict responses,
while Flyology's serialized atomic backend need not synthesize 409 instead of
its exact success, not-found, or precondition result. Requester Pays, governance
retention enforcement, and directory-bucket predicates remain explicit typed
capability exclusions. PutObject and UploadPart remain partial until broader
option/header variants, trailer-based checksums, and HTTP/2 and HTTP/3 server
streaming qualification pass. CompleteMultipartUpload is separately qualified
for its bounded buffered manifest and atomic backend publication boundary.
UploadPartCopy supports
whole sources
and strict bounded byte ranges, quoted source ETag conditions, exact 5 GiB
part limits, immutable backend source snapshots, and fixed-length XML results.
Source versions, date conditions, encryption, ACLs, and replacement metadata
are rejected rather than silently ignored.

PutObjectTagging, GetObjectTagging, and DeleteObjectTagging operate on one
complete tag set and preserve wire order. The shared backend contract replaces,
reads, or clears tags under the same publication boundary used for the current
object, distinguishes missing buckets from missing keys, and clears stale tags
when PutObject or multipart completion publishes a replacement. The strict XML
boundary permits at most ten unique keys, applies AWS Unicode code-point limits
and repertoire rules, rejects DTDs and unknown or duplicate structure, and caps
documents at 16 KiB. Query parsing is bounded, percent-decodes version IDs, and
rejects unknown, duplicate, or mismatched SDK operation controls after
authentication. PutObjectTagging requires Content-MD5 over the exact XML body;
all tagging body/query/header and owner checks occur after SigV4 authentication,
and rejected mutations leave the previous set intact. Typed clients model every
pinned request member, validate bounded responses and version IDs, and are
wrapped by synchronous `Put_Tags`, `Get_Tags`, and `Delete_Tags` convenience
calls. The authenticated server routes current, explicit `null`, and opaque
exact selectors through the same backend publication snapshot and returns its
selected identity in `x-amz-version-id`; memory and SQLite retain opaque
generations, while files rejects them explicitly and supports only its current
and null aliases. Native and lightweight clients exercise the lifecycle against
RustFS, SeaweedFS, supplemental MinIO, and Flyology memory/files/SQLite.
Configured Requester Pays accounting and SDK checksum execution remain explicit
server capability exclusions. Their exact tokens, duplicates, and malformed
values are nevertheless authenticated and typed before any mutation, so no
modeled member is silently ignored.

The typed client projects all 19 modeled request members, enforces complete
SSE-C header groups and the inclusive 5 GiB range ceiling, signs the exact
copy-source headers, decodes every modeled result header and CopyPartResult
checksum, and recognizes embedded HTTP-200 S3 errors. Its basic whole-source
path copies the deterministic 6 MiB multipart object in both native and
Flyology lightweight tasks on RustFS, SeaweedFS, supplemental MinIO, and all
three Flyology backends; digest-pinned s5cmd verifies the copied bytes.
The client gate signs all source entity/date conditions, both source and
destination SSE-C groups, range, requester-pays, and both owner preconditions
in one exhaustive request. Result validation covers the modeled encryption and
request-charged enums, SSE-C algorithm/digest, bucket-key boolean, every XML
checksum width, required ETag/time, embedded errors, and bounded malformed XML.
Together with the already qualified backend, server, and oracle corpora, this
closes UploadPartCopy end to end in the operation ledger.

AbortMultipartUpload projects all six pinned request members and the sole
`x-amz-request-charged` output member. Its explicit convenience call retains
the typed rejection rather than hiding cleanup failures. Memory, files, and
SQLite compare `x-amz-if-match-initiated-time` with the stored upload timestamp
under the same publication lock or database transaction that retires every
part, so a failed precondition cannot race with deletion. The authenticated
server rejects duplicate or malformed initiation-time, expected-owner, and
request-payer headers before touching storage; Requester Pays remains an
explicit `NotImplemented` response because this server has no billing policy.

PutObject has complete typed client handling for all 46 modeled inputs. The
backend, client, and corpus ledger cells are covered; the server cell remains
partial. The frozen request inventory has 28 implemented semantic members,
one qualified `STANDARD` no-op, and 17 members that receive authenticated
`NotImplemented`. The 22-position result inventory has 14 server projection or
omission contracts and eight externally decoded provider positions. The
bounded convenience single-part uploader projects retained metadata, tags,
direct checksums, conditions, and owner policy without retaining or replaying
the caller's one-shot source. See the
[PutObject qualification](../qualification/put-object.md) for the exact
disposition and evidence.

The server's ordinary complete-object PutObject route maps strict,
single-valued `If-Match` and `If-None-Match` headers into the backend write
contract. Memory checks the current generation in its protected commit,
pure-files checks it under the publication gate immediately before rename,
and SQLite checks it inside the catalog transaction immediately before
upsert. A failed predicate returns `PreconditionFailed` without changing any
part of the body/information/metadata/tag/checksum tuple. HeadObject and
GetObject project the retained metadata from the same immutable information
snapshot; HEAD 304 keeps validators while 412 and 416 do not inherit stored
representation headers. An accepted mutation whose response is lost remains
outcome-unknown and is reconciled by an exact generation-bound read, never a
transparent replay.

Successful PutObject returns its version identity from the same backend
publication snapshot as the body and metadata. The server omits the header for
unversioned publication, emits the exact opaque identity for enabled
memory/SQLite publication, and emits `x-amz-version-id: null` for suspended
memory/files/SQLite publication. Files has no retained-generation data plane
and rejects enabled publication before rename rather than overwriting history.

The authenticated server requires every physical `x-amz-*` request header to
be named in SigV4 `SignedHeaders`; duplicate physical fields are reconstructed
in wire order for canonical verification. It intentionally also requires the
mandatory `x-amz-content-sha256` field to be signed. AWS S3 permits that one
field to be omitted from `SignedHeaders` because its value is already the
canonical request payload hash, so this stricter rule remains an explicit
server-compatibility boundary. SigV4 streaming `aws-chunked` payloads are also
rejected before reading the source until a signature-chain decoder is
available; ordinary application content encodings remain supported verbatim.

Every one of the 116 pinned operations now has exhaustive generated-model
request projection and can execute through the generic low-level boundary,
which returns Flyology HTTP's limited streaming response without retaining an
arbitrary body. The projector covers modeled method, URI labels and fixed
queries, query/header/header-map members, required top-level members, scalar
enums and bounds, addressing, SigV4, and retained raw payloads. Accordingly,
the client ledger records `partial` for this exact common substrate. It does
not mean an operation has its typed body codec, typed response decoder,
streaming request-source path, semantic policy, or independent interoperability
corpus; those remain required before any operation becomes `complete`.

The server `partial` entries cover authenticated path-style requests. The
project-owned raw-wire corpus signs real SigV4 requests and
checks authentication before `100 Continue`, fixed-length and chunked PUT,
payload-hash mismatch rollback, whole and suffix GET, unsatisfiable range
metadata, cancellation/deadline propagation, ETags, and lifecycle cleanup.
A shared digest-pinned s5cmd slice now creates a bucket; uploads empty,
deterministic 4 KiB, deterministic 2 MiB, and forced two-part 6 MiB objects;
exercises a nested key

ListBuckets authenticates before backend access and uses the same atomic,
bounded prefix/cursor page contract on all three backends. Its server rejects
bodies and malformed or duplicate query members, applies the configured-region
filter, returns owner and per-bucket metadata, and binds opaque continuation

on pinned RustFS, SeaweedFS, supplemental MinIO, and the Flyology memory,

same visibility before object traffic begins.
DeleteObjects accepts the exact `delete` subresource forms, validates a
bounded 1,000-key REST/XML document and payload hash, and requires canonical
Content-MD5 over the exact admitted body. It also verifies each of the ten
modeled SDK checksum algorithm/header pairs. Malformed or inconsistent
checksum groups are `InvalidRequest`; well-formed digest mismatches are
`BadDigest`. The namespace-aware request parser rejects attributes, unknown or
duplicate members, malformed scalars, and out-of-order structures before any
backend mutation. Quiet responses suppress successes but retain errors in
request order; unconditioned missing keys remain idempotent successes.

The backend boundary evaluates one ordered batch rather than composing
single-object deletes. Memory publishes the batch in one protected operation,
and SQLite commits all catalog removals in one transaction before reclaiming
retired payloads. The pure-files backend validates the whole request first and
serializes publication, but cannot promise cross-file power-loss atomicity:
an I/O failure, cancellation, or deadline during its removal loop can leave an
idempotently retryable request prefix applied. The compatibility claim does
not hide that boundary.

The typed client models every request member, always generates and signs
Content-MD5, and can additionally generate CRC32, CRC32C, CRC64NVME, SHA1,
SHA256, SHA512, MD5, XXHASH64, XXHASH3, or XXHASH128. Its result model retains
all Deleted and Error members. The authenticated server accepts valid
requester-pays and governance-bypass headers as policy-inactive no-ops and
enforces expected owner, exact quoted/unquoted or wildcard ETag conditions,
and strict HTTP-date syntax. LastModifiedTime and Size are reported as
directory-bucket-only; this server currently exposes general-purpose buckets.
Omitted, `null`, and opaque VersionId members map to current, null, and exact
backend selectors. Memory and SQLite publish current delete markers, remove
selected data or markers, echo requested version identities, and return
created/removed marker identities. MFA-enabled permanent deletion requires a
verified `x-amz-mfa` credential carried into the atomic batch boundary. Files
reports exact-generation entries as `NotImplemented` while allowing
independently representable current/null entries. The optional
required-unversioned state is also checked inside each backend's batch
publication boundary, so concurrent PutBucketVersioning cannot race legacy
current-object semantics. The files retained-generation, durability, and
directory-bucket boundaries keep backend and server coverage partial.

PutBucketTagging, GetBucketTagging, and DeleteBucketTagging use one
HTTP-independent tag model on memory, files, and SQLite. Validation counts
Unicode scalars in strict UTF-8, enforces AWS's L/Z/N plus
`_ . : / = + - @` character set, rejects reserved `aws:` keys and duplicate
case-sensitive keys, and bounds a bucket to 50 tags. Memory publishes one
protected snapshot; files replace a versioned binary tag record through a
synced temporary file and directory rename; SQLite replaces all rows in one
transaction and upgrades historical catalogs without inventing tags. Deletion
takes the same publication locks, syncs the configuration directory, rejects
live and dangling symlinks before following them, and remains idempotent for
an existing untagged bucket. Reopen, migration, and abrupt-crash tests cover
files and SQLite persistence.

The authenticated server routes malformed tagging and operation-specific
`x-id` candidates through authentication before rejecting non-exact queries.
Put requires and verifies Content-MD5 over the exact bounded body before
backend mutation. It accepts each of the ten checksum algorithms in the pinned
model through either its request header or a declared physical HTTP trailer;
ambiguous groups, duplicate fields, noncanonical Base64, and digest mismatches
fail before mutation. Its namespace-aware SAX parser rejects DTD/entity input,
foreign namespaces, attributes, unknown or duplicate fields, excessive
depth/elements/text, invalid UTF-8, malformed structure, and invalid tags with
the appropriate MalformedXML or InvalidTag response. Get returns NoSuchTagSet
separately from NoSuchBucket and serializes one atomic snapshot. Delete returns
an exact empty 204, distinguishes a missing bucket, and is idempotent when the
bucket exists without tags. Expected-owner policy is enforced. All three
operations reject RequestPayer because it is absent from the authoritative
pinned model rather than silently treating it as supported.

The low-level client signs every modeled control, generates Content-MD5 and
the selected checksum through the shared checksum engine, accepts the primary
Put response syntax's 200 and the AWS example's 204, requires Delete's exact
empty 204, and decodes bounded typed tag documents and structured S3 errors.
Response decoding accepts the official S3 namespace or no namespace, as
emitted by pinned MinIO, while rejecting foreign namespaces and attributes.
The convenience API provides `Put_Tags`, `Get_Tags`, and `Delete_Tags`, all
with cancellation and whole-operation deadlines. Unit, signed in-memory
application, physical-trailer, choppy real-socket, backend conformance,
durability, migration, and native/lightweight six-server implementation lanes
execute the complete put/get/replace/delete/no-tag/idempotent-delete lifecycle.
The dedicated persistent-client benchmark runs the same correctness-checked
lifecycle against all six implementations; MinIO remains supplemental rather
than a permissively licensed performance baseline.

This is evidence only for those operations; broader AWS SDK corpora remain

The established GET and HEAD framing evidence predates the composable client;
the composable rollout is qualified separately against indexed HTTP/QUIC
0.1.3-dev at reviewed source commit

CopyObject uses one immutable backend-owned source snapshot and atomically
publishes body, object information, system and user metadata, tags, and the
recomputed full-object checksum; it does not retain the object in the HTTP
application. The shared memory, files, and SQLite suite covers zero-byte and
large copies, same- and cross-bucket targets, same-key and concurrent source
mutation, exact 5 GiB policy bounds, condition precedence, failed-source
nonmutation, reopen/migration, and durability or rollback boundaries.
Memory and SQLite additionally select current, null, or exact retained source
generations and return both source and destination identities from those same
boundaries. Files aliases current and null and rejects opaque exact selection.

The complete typed client projects all 42 non-destination request members,
with destination bucket and key supplied explicitly, and preserves all 11
top-level output members plus the 13-member `CopyObjectResult`. Its strict
decoder recognizes embedded HTTP-200 S3 errors and rejects malformed dates,
weak, wildcard, multiple, or unquoted result ETags, invalid checksums, and
incoherent output combinations. The high-level
`Client.Transfers.Copy_Object` path owns copy-source encoding/signing and
returns both compact metadata and the complete typed result. It accepts the
full options record; callers needing a raw version-specific `CopySource` use
the low-level operation because the convenience overload deliberately derives
that header from its source bucket and key arguments.

The server's remaining partial label describes its explicit authenticated,
path-style capability profile, not silently omitted modeled
members. Every one of the 44 pinned request members is persisted, strictly
validated as an inapplicable no-op, or rejected as authenticated
`NotImplemented`; all 24 output positions are emitted or deliberately omitted
according to the qualification disposition. Native and lightweight clients
copy deterministic 6 MiB objects against RustFS, SeaweedFS, supplemental
MinIO, and all three Flyology backends, with independent whole-object byte and
deletion checks.
Strict signed server cases select retained and null copy sources, require
`x-amz-copy-source-version-id` and destination `x-amz-version-id` from the
same successful operation, and reject malformed or unsupported source
selectors before mutation.

The high-level `Client.Transfers.Head_Object` reconciliation path is exercised
from native and lightweight tasks against both permissive references,
supplemental MinIO, and the memory, files, and SQLite Flyology backends. Its
compact aliases sit beside `Details`, the complete validated 43-member result;
all 21 modeled request members are available as named arguments. Successful
decoding rejects payload bytes, transfer coding, duplicate singleton fields,
invalid dates, entity tags, checksums, enums, counts, and incoherent 200/206
range framing. AWS-style range and part responses are 200 with the selected
`Content-Length` and no GET-only `Content-Range`; the decoder additionally
accepts coherent 206 responses from pinned compatible implementations.
Bodyless failures retain request identifiers.

The authenticated server evaluates all four HTTP conditions against the same
immutable attribute snapshot used for the response, including S3's ETag/date
precedence. It supports bounded, open, and suffix ranges; ordinary implicit
part one; exact completed-part selection; `x-amz-mp-parts-count`; all six
response overrides; expected owner; requester acknowledgement; and checksum
mode. Multipart counts and boundaries come from the same canonical FOSOBJ04 or
SQLite `object_parts` snapshot used by GetObjectAttributes; memory uses the
same completed-part vector. FOSOBJ04 retains object and per-part checksum
metadata and safely reads FOSOBJ01 through FOSOBJ03, upgrading an older object
on its next atomic metadata rewrite. The live corpus completes a true 5 MiB + 1 MiB
object and checks both parts, ranges, missing parts, 304, and 412 through both
HTTP task models. Absent and `null` version selectors address the current
unversioned object; real version IDs return `NotImplemented`. Malformed or
duplicate controls fail after authentication. A structurally valid SSE-C
group against the supported unencrypted storage model is rejected rather than
silently ignored; encrypted object storage remains a separately unimplemented
cross-cutting capability.

The implementation oracle records rather than conceals reference differences:
the pinned MinIO release returns 206 and `Content-Range` for valid range and
part requests; SeaweedFS ignores HEAD ranges and reports whole-object length
for valid parts; RustFS additionally ignores response overrides and part
selection and returns 500 for an absent part. All three Flyology backends must
pass the complete AWS profile without a capability mode.

GetObjectAttributes has a complete typed request/output client and a compact
`Client.Objects.Get_Attributes` convenience call. The request projector covers
all 11 modeled members, including independent presence for both pagination
headers and the required five-value selection list. The bounded XML codec
preserves all nine top-level outputs, every pinned checksum family member, and
the complete paginated `ObjectParts` shape. Object checksum validation requires
one algorithm, a legal explicit algorithm/type pair, canonical raw or
`base64-positive-part-count` form, and exact agreement with PartsCount.
Individual part checksums are raw, single-algorithm, and homogeneous. Direct
objects may report raw FULL_OBJECT values for every modeled algorithm;
multipart FULL_OBJECT remains CRC-only and multipart COMPOSITE excludes
CRC64NVME. The codec rejects duplicate, misplaced, overflowing,
malformed-base64, mixed-algorithm, or invalid-enum fields while allowing an
empty success document when the only requested optional attribute is
unavailable.

The backend call returns object metadata and a bounded completed-part page from
one immutable object-generation snapshot selected as current, null, or by an
opaque exact version ID. Memory retains that metadata at
multipart publication; the pure-files format remains backward-readable while
persisting it in its current generation; SQLite schema version 8 stores part
rows and their checksums under the object foreign key and migrates earlier
catalogs, including the
version-4 tag-only/versioning-only and both version-5 layouts. Ordinary puts
and copies clear stale part metadata atomically. The authenticated server
strictly parses the `attributes` query and all modeled headers only after

pagination, and omits unavailable additional checksums and STANDARD storage
class rather than inventing values. Exact version IDs are routed to the

single-generation files backend reports `NotImplemented` for opaque IDs.
Valid Requester Pays and valid HTTPS SSE-C policy receive explicit

key/digest-mismatched controls are rejected before backend access. Other
encryption controls also fail explicitly. Directory buckets and configured

The Flyology server evaluates strong `If-Match`, weak `If-None-Match`, and all
three HTTP-date forms atomically against the same immutable object snapshot as
the returned bytes. It implements S3's entity-tag/date precedence, rejects
malformed or duplicate conditions before backend access, applies all six
response-header overrides after authentication, enforces expected-owner, and
accepts requester-pays/checksum-mode controls without silently accepting

duplicates at or before its boundary.
