# S3 compatibility matrix

This matrix is an engineering gate, not a blanket compatibility claim.
“Backend” means the HTTP-independent primitive is implemented and covered by
the shared black-box suite. “Wire” requires an independent S3 protocol corpus.

| Area | Backend | Wire/client | Qualification |
|---|---:|---:|---|
| CreateBucket | memory, files, SQLite | complete typed and convenience clients; authenticated general-purpose path-style server partial | strict XML/header/region/state corpus plus native/lightweight clients across RustFS, SeaweedFS, MinIO, and all Flyology backends |
| HeadBucket | memory, files, SQLite | complete typed and convenience clients; authenticated path-style server | strict header/body/owner corpus plus native/lightweight clients across RustFS, SeaweedFS, MinIO, and all Flyology backends |
| GetBucketLocation | memory, files, SQLite | complete typed and convenience clients; authenticated path-style server | strict bounded XML/query corpus plus native/lightweight clients across RustFS, SeaweedFS, MinIO, and all Flyology backends |
| ListBuckets | memory, files, SQLite | complete typed and paginated convenience clients; authenticated server | atomic backend pagination, strict presence/query/XML and signed socket/server corpora, plus native/lightweight clients and s5cmd across the six-server matrix |
| DeleteBucket | memory, files, SQLite | complete typed and convenience clients; authenticated path-style server | strict empty/nonempty/body/owner corpus plus cleanup through RustFS, SeaweedFS, MinIO, and all Flyology backends |
| PutBucketTagging / GetBucketTagging | memory, files, SQLite | typed and convenience clients; authenticated path-style server partial | atomic backend conformance and crash gates, strict XML/MD5/query/header corpora, signed sockets, and typed six-server matrix |
| Put/Get/Head object | memory, files, SQLite | typed Get/Head client; authenticated streaming server | backend + typed six-server client + server raw-wire corpora |

| Single byte range | memory, files, SQLite | server bounded/open/suffix; client partial | backend + server raw-wire corpora |

| Multipart upload | memory, files, SQLite | typed signed client primitives + authenticated streaming server partial | backend persistence, loopback, and six-server forced-multipart byte oracle |
| AbortMultipartUpload | memory, files, SQLite | complete typed and convenience client; authenticated path-style server | atomic initiation-time condition, strict owner/payer/date/duplicate corpus, durability faults, and six-server typed-client oracle |
| ListParts | memory, files, SQLite | complete typed client + authenticated path-style server partial | bounded backend pagination, strict query/XML corpora, and typed six-server matrix |
| ListMultipartUploads | memory, files, SQLite | complete typed client + authenticated path-style server partial | backend pagination/persistence, strict signed-wire corpus, and typed five-server matrix |
| UploadPartCopy | memory, files, SQLite | complete typed signed client + authenticated path-style server | backend, signed raw-wire, typed six-server byte oracle, and s3t matrix |
| SigV4 header signing | n/a | canonical signer | AWS published vectors |
| SigV4 presigning | n/a | planned | not claimed |
| Versioning, lifecycle, Object Lock | planned | planned | not claimed |

The wider wire gate will draw from Ceph s3-tests, AWS SDK integration tests,
MinIO/Mint-compatible cases, AWS SigV4 published examples, and project-owned
adversarial malformed-input corpora. Exact revisions and allowlists are pinned
as each lane becomes executable.

The machine-readable source of truth is
[coverage/aws-s3-operations.tsv](../../coverage/aws-s3-operations.tsv). It
contains every operation in the pinned botocore S3 model and distinguishes
traditional general-purpose S3 from extended and specialized APIs. Run
tools/verify-coverage.sh to validate the ledger. Immutable upstream revisions
are recorded in coverage/corpora.lock.toml.

`partial` in the machine ledger is not a compatibility claim. ListObjects v1
accounts for all nine modeled inputs, the top-level request-charged output,
and all nested Object members, including flattened checksum algorithms,
checksum type, owner, and restore status. ListObjects v1 and v2 have exact
request signing, Flyology execution, bounded body consumption, status/header
handling, typed success/error decoding, project-owned adversarial tests, and
a raw-loopback HTTP socket gate exercised from both native and Flyology
lightweight tasks. V2 additionally preserves absent versus present-empty
continuation tokens and absent versus explicit-false fetch-owner requests,
and accounts for all 11 modeled inputs and all 13 top-level outputs. Their
basic paths also pass against digest-pinned RustFS,
SeaweedFS and MinIO servers. Multipart initiation and
completion have strict request/result codecs, exact signed targets, checksummed
body validation, embedded HTTP-200 error handling, and the same
native/lightweight raw-loopback gate. ListParts has a typed signed client for
all ten request members, all three response headers, and a bounded result
codec for every modeled XML member, including every checksum,
owner/initiator identity, and strict pagination invariants. Its independent
matrix passes three repetitions against digest-pinned RustFS, SeaweedFS,
MinIO, and Flyology memory/files/SQLite servers. The Flyology server currently
omits optional lifecycle, owner/initiator, and checksum fields and rejects
SSE-C because server-side encryption is not implemented.
ListMultipartUploads has a bounded codec for all 12 REST/XML body members of
its pinned output shape and all eight members of each nested upload, including
independent owner/initiator presence, checksum algorithm/type, common prefixes,
encoding type, and both marker pairs. Its strict corpus rejects duplicate or
incomplete structures and invalid modeled enums while preserving valid
directory-bucket ordering and AWS marker variance. The typed request, response
header, and bounded execution layers now cover all nine modeled inputs and the
sole response header, with exact canonical-signature, structured-error, and
native/lightweight raw-loopback tests. All three backends now return an atomic,
bounded active-upload snapshot with key and initiation-time ordering, exact
upload-ID marker filtering, prefix/delimiter grouping, initiation metadata,
and completion/abort visibility; files and SQLite preserve the listing across
reopen. The authenticated server implements strict query parsing, bounded
pagination, delimiter grouping, URL encoding, and typed errors. Native and
lightweight clients pass active/retired-upload checks against RustFS,
supplemental MinIO, and Flyology memory/files/SQLite. RustFS omits the
model-optional StorageClass field, which the client now preserves as absent.
Pinned SeaweedFS 4.43 is explicitly excluded from this operation's positive
oracle: a fresh exact-limit response reports truncation but omits
NextKeyMarker, and also omits initiation metadata, so it cannot supply a valid
continuation contract. Other SeaweedFS operation gates remain enabled.

UploadPart borrows rather than retains
its source, signs an explicit SHA-256 payload hash, and covers every modeled
checksum header. Each external lane uploads one 6 MiB object per task kind
from 997-byte source chunks, completes and lists each object through this
library, then re-reads both with digest-pinned s5cmd and checks a fixed SHA-256
oracle. The full matrix repeats all three lanes three times. RustFS and
SeaweedFS are Apache-2.0 and s5cmd is MIT; MinIO is a supplemental AGPL test
runtime, not the oracle. The cleanup phase deletes both objects through this
library, deletes the bucket, and requires s5cmd to observe the bucket as gone.
The setup phase creates the bucket through this library, heads it from both
native and Flyology lightweight tasks, and requires s5cmd to observe it; no
server lane receives pre-created bucket state. CreateBucket models every
pinned header and nested configuration field. Its strict bounded parser
rejects unknown, duplicate, misplaced, incomplete, oversized, or invalid
configuration members, including duplicate and excessive tags. The
convenience client creates a general-purpose bucket and supplies the signing
region as LocationConstraint when AWS requires it. Native and lightweight
clients use that API for setup in three repeated runs across RustFS,
SeaweedFS, supplemental MinIO, and all three Flyology backends. The Flyology
server implements the general-purpose private/BucketOwnerEnforced subset,
normalizes the legacy EU constraint, enforces endpoint-region compatibility,
and mutates backend state only after validation. Directory buckets, tags,
grants, public ACLs, Object Lock, non-enforced ownership, and bucket namespace
controls return explicit NotImplemented errors instead of being silently
discarded; this is why server coverage remains partial.
HeadBucket is complete end to end: the server returns its configured region on
successful, forbidden, and missing-bucket responses, enforces the
expected-owner precondition, and rejects duplicate owner fields. The typed
client validates bodylessness, region syntax, location types and bounded
headers while preserving every pinned output. The convenience API falls back
to the request's signing region when a compatible server omits the optional
response header, a measured RustFS 1.0.0-rc.3 behavior. Native and lightweight
clients pass three repeated runs across RustFS, SeaweedFS, supplemental MinIO,
and all three Flyology backends.
GetBucketLocation is complete end to end. The server checks bucket existence,
uses the configured SigV4 region, and emits AWS's null scalar for us-east-1.
The bounded client parser preserves strict root, nesting, size, depth, and
enumeration checks while accepting two measured compatibility spellings:
RustFS 1.0.0-rc.3 returns literal us-east-1, and SeaweedFS 4.43 returns one
LocationConstraint inside a CreateBucketConfiguration wrapper. The
convenience API normalizes empty and literal us-east-1 to us-east-1, and EU to
eu-west-1, while preserving the observed legacy constraint. Native and
lightweight typed clients pass against both permissive references,
supplemental MinIO, and all three Flyology backends.
DeleteBucket is complete end to end. The shared server owner policy rejects
mismatched and duplicate expected-owner fields, the route rejects request
bodies, nonempty buckets remain intact with BucketNotEmpty, and success is an
empty 204. The typed and convenience clients delete every matrix-created
bucket after independent s5cmd confirms object cleanup. DeleteObject models
every pinned request field and success response header. Its shared strict
query parser bounds and decodes versionId and the SDK operation ID, rejects
duplicates and unknowns after authentication, and shares one 1,024-byte,
NUL-free version rule with multi-delete and response validation. The
convenience client exposes ordinary deletion, version selection, If-Match,
owner preconditions, and Requester Pays while leaving MFA and governance
bypass explicit at the typed low-level layer. All matrix cleanup runs through
the convenience API. The Flyology server supports idempotent unversioned
deletion and expected-owner policy, distinguishes an absent bucket from an
absent key atomically in every backend, and rejects bodies before mutation.
Versioning, If-Match, directory-only conditions, retention bypass, MFA, and
Requester Pays return explicit NotImplemented errors instead of being silently
ignored, so server coverage remains partial. The streaming operations remain
partial until broader option/header variants, trailer-based checksums, and
HTTP/2 and HTTP/3 server streaming qualification pass. UploadPartCopy supports
whole sources
and strict bounded byte ranges, quoted source ETag conditions, exact 5 GiB
part limits, immutable backend source snapshots, and fixed-length XML results.
Source versions, date conditions, encryption, ACLs, and replacement metadata
are rejected rather than silently ignored.

PutObjectTagging, GetObjectTagging, and DeleteObjectTagging operate on one
complete tag set and preserve wire order. The shared backend contract replaces,
reads, or clears tags under the same publication boundary used for the current
object, distinguishes missing buckets from missing keys, and clears stale tags
when PutObject or multipart completion publishes a replacement. The strict XML
boundary permits at most ten unique keys, applies AWS Unicode code-point limits
and repertoire rules, rejects DTDs and unknown or duplicate structure, and caps
documents at 16 KiB. Query parsing is bounded, percent-decodes version IDs, and
rejects unknown, duplicate, or mismatched SDK operation controls after
authentication. PutObjectTagging requires Content-MD5 over the exact XML body;
all tagging body/query/header and owner checks occur after SigV4 authentication,
and rejected mutations leave the previous set intact. Typed clients model every
pinned request member, validate bounded responses and version IDs, and are
wrapped by synchronous `Put_Tags`, `Get_Tags`, and `Delete_Tags` convenience
calls. Native and lightweight clients exercise the lifecycle against RustFS,
SeaweedFS, supplemental MinIO, and Flyology memory/files/SQLite. Versioned
objects, Requester Pays, and SDK checksum algorithms remain explicitly
NotImplemented on the Flyology server, so its ledger entry remains partial.

The typed client projects all 19 modeled request members, enforces complete
SSE-C header groups and the inclusive 5 GiB range ceiling, signs the exact
copy-source headers, decodes every modeled result header and CopyPartResult
checksum, and recognizes embedded HTTP-200 S3 errors. Its basic whole-source
path copies the deterministic 6 MiB multipart object in both native and
Flyology lightweight tasks on RustFS, SeaweedFS, supplemental MinIO, and all
three Flyology backends; digest-pinned s5cmd verifies the copied bytes.
The client gate signs all source entity/date conditions, both source and
destination SSE-C groups, range, requester-pays, and both owner preconditions
in one exhaustive request. Result validation covers the modeled encryption and
request-charged enums, SSE-C algorithm/digest, bucket-key boolean, every XML
checksum width, required ETag/time, embedded errors, and bounded malformed XML.
Together with the already qualified backend, server, and oracle corpora, this
closes UploadPartCopy end to end in the operation ledger.

AbortMultipartUpload projects all six pinned request members and the sole
`x-amz-request-charged` output member. Its explicit convenience call retains
the typed rejection rather than hiding cleanup failures. Memory, files, and
SQLite compare `x-amz-if-match-initiated-time` with the stored upload timestamp
under the same publication lock or database transaction that retires every
part, so a failed precondition cannot race with deletion. The authenticated
server rejects duplicate or malformed initiation-time, expected-owner, and
request-payer headers before touching storage; Requester Pays remains an
explicit `NotImplemented` response because this server has no billing policy.

PutObject now has complete typed handling for all 46 modeled inputs: body
and content length remain owned by the borrowed HTTP source, while every other
member is explicit in the policy record. Exhaustive signing tests cover KMS,
SSE-C, checksums, user metadata, ACL grants, Object Lock, tagging, conditional
headers, and write offsets, including negative cross-field policy cases. The
22-member result decoder validates all modeled headers and bounded error XML;
the convenience single-part uploader uses it without retaining the source.
It remains partial pending broader option combinations, trailer checksums, and
versioning/Object-Lock interoperability.

Every one of the 116 pinned operations now has exhaustive generated-model
request projection and can execute through the generic low-level boundary,
which returns Flyology HTTP's limited streaming response without retaining an
arbitrary body. The projector covers modeled method, URI labels and fixed
queries, query/header/header-map members, required top-level members, scalar
enums and bounds, addressing, SigV4, and retained raw payloads. Accordingly,
the client ledger records `partial` for this exact common substrate. It does
not mean an operation has its typed body codec, typed response decoder,
streaming request-source path, semantic policy, or independent interoperability
corpus; those remain required before any operation becomes `complete`.

The server `partial` entries cover authenticated path-style requests. The
project-owned raw-wire corpus signs real SigV4 requests and
checks authentication before `100 Continue`, fixed-length and chunked PUT,
payload-hash mismatch rollback, whole and suffix GET, unsatisfiable range
metadata, cancellation/deadline propagation, ETags, and lifecycle cleanup.
A shared digest-pinned s5cmd slice now creates a bucket; uploads empty,
deterministic 4 KiB, deterministic 2 MiB, and forced two-part 6 MiB objects;
exercises a nested key
containing a space, plus sign, and percent escape; and overwrites a small
object with the large payload. It heads and re-reads every object with exact
SHA-256 checks, then requires a wrong secret, an unknown access key, and an
unexpected session token to be rejected. The identical slice passes against
RustFS, SeaweedFS, supplemental MinIO, and the Flyology memory, files, and
SQLite servers.
ListBuckets authenticates before backend access and uses the same atomic,
bounded prefix/cursor page contract on all three backends. Its server rejects
bodies and malformed or duplicate query members, applies the configured-region
filter, returns owner and per-bucket metadata, and binds opaque continuation
tokens to both prefix and requested region. Native and lightweight typed
clients exercise fragmented success and structured S3 error responses over
real sockets. The request and response models preserve explicit empty prefix
and continuation members, enforce the 1,024-byte token boundary, and omit
general-purpose ARN and unrequested region metadata. The convenience client
defaults to bounded 1,000-bucket pages. Native and lightweight clients require
a bucket created through this library to appear through that high-level path
on pinned RustFS, SeaweedFS, supplemental MinIO, and the Flyology memory,
files, and SQLite servers. The s5cmd server slice independently requires the
same visibility before object traffic begins.
DeleteObjects accepts the exact `delete` subresource forms, validates a
bounded 1,000-key REST/XML document and payload hash, supports quiet results,
and reports unsupported version IDs per key without deleting current data.
Its bounded result codec covers every modeled deleted-object field and
per-object error, rejects duplicate or incomplete entries, and tolerates
unknown extension elements. The typed client generates and signs Content-MD5
from the exact serialized document, models MFA, requester-pays, governance
bypass, and expected-owner policy, and deletes two independently verified keys
from both task models on all six servers. It remains partial pending optional
SDK checksum-algorithm/trailer policy, versioned backends, and broader error
oracles.

PutBucketTagging and GetBucketTagging use one HTTP-independent tag model on
memory, files, and SQLite. Validation counts Unicode scalars in strict UTF-8,
enforces AWS's L/Z/N plus `_ . : / = + - @` character set, rejects reserved
`aws:` keys and duplicate case-sensitive keys, and bounds a bucket to 50 tags.
Memory publishes one protected snapshot; files replace a versioned binary tag
record through a synced temporary file and directory rename; SQLite replaces
all rows in one transaction and upgrades v1-v3 catalogs directly to schema 6;
both historical version-4 tag-table layouts and both version-5 attributes/tag
layouts are preserved. The
filesystem crash matrix proves each replacement is old-or-new across all three
publication barriers, and reopen tests cover files and SQLite persistence.

The authenticated server recognizes only the exact `tagging` subresource and
matching SDK x-id forms. Put requires and verifies Content-MD5 over the exact
bounded body before backend mutation. Its namespace-aware SAX parser rejects
DTD/entity input, foreign namespaces, attributes, unknown or duplicate fields,
excessive depth/elements/text, invalid UTF-8, malformed structure, and invalid
tags with the appropriate MalformedXML or InvalidTag response. Get returns
NoSuchTagSet separately from NoSuchBucket and serializes one atomic snapshot.
Expected-owner policy is enforced; requester-pays and optional SDK checksum
groups are validated but explicitly NotImplemented rather than ignored.

The low-level client signs every implemented modeled control, generates
Content-MD5 automatically unless an explicit test digest is supplied, validates
success metadata, and decodes bounded typed tag documents and structured S3
errors. Response decoding accepts the official S3 namespace or no namespace,
as emitted by pinned MinIO, while rejecting foreign namespaces and attributes.
ChecksumAlgorithm remains explicitly rejected until its paired checksum
header can be calculated. The convenience API reduces the common paths to
`Put_Tags` and `Get_Tags`. Unit, signed in-memory application, choppy real-socket,
backend conformance, durability, migration, and native/lightweight six-server
implementation lanes all execute the slice. These explicit checksum and
requester-pays exclusions keep client and server ledger states partial.

This is evidence only for those operations; broader AWS SDK corpora and
reference-behavior differentials remain pending. Indexed
`flyology_http=0.1.2` provides 64-bit request accounting, a 50 TB streaming
ceiling, per-route `Body_Size` limits, and exact-length response streaming;
GET and HEAD framing is qualified against that release.

CopyObject uses one immutable backend-owned source snapshot and atomic
destination publication; it does not retain the object in the HTTP
application. The qualified slice covers zero-byte and 16 MiB copies, same- and
cross-bucket targets, content-type preservation, missing source bucket/key,
metadata-preserving self-copy rejection, and quoted source ETag conditions.
The typed core client signs source conditions, Content-Type, metadata
directive, requester-pays, and expected-owner fields; decodes every modeled
output header and CopyObjectResult checksum; and recognizes embedded HTTP-200
S3 errors. Both task models copy the deterministic 6 MiB object on the two
permissive references, supplemental MinIO, and all three Flyology backends,
with digest-pinned s5cmd verifying the destination bytes.
The high-level `Client.Transfers.Copy_Object` path repeats that matrix from a
source key containing spaces, plus, and percent bytes; it owns copy-source
encoding/signing and returns compact copy metadata or the structured S3 error.
User metadata, ACLs, source date conditions, source versions, and replacement
metadata beyond Content-Type are rejected rather than silently discarded.

The high-level `Client.Transfers.Head_Object` reconciliation path is exercised
from native and lightweight tasks against both permissive references,
supplemental MinIO, and the memory, files, and SQLite Flyology backends. The
shared corpus checks the completed multipart object's exact 64-bit size,
nonempty ETag and modification time, and a missing-key 404. The deterministic
signed socket corpus additionally covers special-character key encoding,
content/version metadata, a valid SHA-256 checksum, bodyless error request IDs,
and rejection of a malformed checksum. The convenience result is deliberately
compact; the typed low-level client projects all 21 modeled HeadObject request
members and decodes all 43 modeled outputs, including repeated user metadata,
the complete pinned checksum family, optional counts/booleans, storage and lock
state, encryption, and replication fields. Semantic validation is layered over
the generated model, and SSE-C request keys require HTTPS. The deterministic
socket corpus executes this typed path with the full response-header families;
both task models also execute it on all six oracle-matrix servers. The server
now authenticates before strictly parsing all HeadObject query members: valid
version, part, and response-override controls receive an explicit
`NotImplemented`, while duplicate, unknown, malformed, oversized, and
control-byte-bearing fields receive `InvalidArgument` without backend access.
For ordinary objects it also enforces expected-owner and ETag conditions and
serves satisfiable single ranges with exact `Content-Range` and bodyless 206
framing; malformed, duplicate, and unsatisfiable ranges are distinguished.
Date conditions, requester-pays, checksum mode, and complete SSE-C requests are
explicitly unsupported instead of being ignored, while malformed policy and
encryption header groups are rejected before backend access.

GetObjectAttributes has a complete typed request/output client and a compact
`Client.Objects.Get_Attributes` convenience call. The request projector covers
all 11 modeled members, including independent presence for both pagination
headers and the required five-value selection list. The bounded XML codec
preserves all nine top-level outputs, every pinned checksum family member, and
the complete paginated `ObjectParts` shape. It rejects duplicate, misplaced,
overflowing, malformed-base64, or invalid-enum fields while allowing an empty
success document when the only requested optional attribute is unavailable.

The backend call returns object metadata and a bounded completed-part page from
one immutable object-generation snapshot. Memory retains that metadata at
multipart publication; the pure-files format remains backward-readable while
persisting it in its current generation; SQLite schema version 6 stores part
rows under the object foreign key and migrates earlier catalogs, including the
version-4 tag-only and both version-5 layouts. Ordinary puts
and copies clear stale part metadata atomically. The authenticated server
strictly parses the `attributes` query and all modeled headers only after
SigV4 admission, returns selected ETag, object size, and completed-part
pagination, and omits unavailable additional checksums and STANDARD storage
class rather than inventing values. Concrete version IDs, valid Requester Pays,
and valid SSE-C policy receive explicit `NotImplemented`; malformed or
incomplete controls are rejected before backend access.

The native implementation corpus exercises the typed and convenience paths on
the pinned Apache-2.0 RustFS and SeaweedFS references and on Flyology memory,
files, and SQLite. It checks completed-multipart size, ETag, optional part
metadata, pagination, and missing-key behavior. RustFS 1.0.0-rc.3 passes the
positive attributes paths but its missing-key XML omits the required Error
Message member; that one negative oracle is narrowly excluded and reported by
the runner. SeaweedFS and all three Flyology backends pass the full operation
corpus. Supplemental MinIO is excluded for this operation because its pinned
response uses `getObjectAttributesResponse` instead of AWS's case-sensitive
`GetObjectAttributesResponse` root. Deterministic unit, authenticated
in-process, fragmented real-socket, and live backend tests additionally cover
malformed requests, unavailable
selected fields, structured errors, and both public client levels.

GetObject uses the same complete 21-member typed request projection and
HTTPS-only SSE-C policy. Its typed response-head decoder covers all 42 modeled
non-body outputs, including repeated metadata, the complete pinned checksum
family, 64-bit content length, counts, encryption, storage, replication, and
object-lock state. The limited Flyology HTTP response remains owned by the
caller, so successful representations stream without an object-sized retained
buffer. The high-level atomic file downloader now runs through this typed
path in both task models on both permissive references, supplemental MinIO,
and all three Flyology backends. It exposes version, all four HTTP conditions,
a single byte range, expected-owner, requester-pays, and checksum mode. Whole
downloads require 200; ranged downloads require 206 plus an exact single
`Content-Range` consistent with `Content-Length` and received bytes. Its
deterministic socket gate additionally covers choppy body reads, successful
ranges, bodyless 304, non-XML 412, truncated bodies, missing/inverted/mismatched
range framing, and refusal to publish an unsolicited 206 or Content-Range.
All failures preserve the existing destination and remove temporary files.

The Flyology server evaluates strong `If-Match`, weak `If-None-Match`, and all
three HTTP-date forms atomically against the same immutable object snapshot as
the returned bytes. It implements S3's entity-tag/date precedence, rejects
malformed or duplicate conditions before backend access, applies all six
response-header overrides after authentication, enforces expected-owner, and
accepts requester-pays/checksum-mode controls without silently accepting
unknown values. Memory, files, and SQLite run the same condition corpus and do
not invoke a body sink for 304/412. The pinned RustFS, SeaweedFS, and MinIO
matrix repeats valid ranges and 304/412 behavior through both Flyology HTTP task
models. Non-null versions, `partNumber`, and complete SSE-C reads remain
explicitly unsupported, so server coverage remains partial.

ListObjects v1 and v2 use the same bounded backend page contract across
memory, files, and SQLite. Both provide bytewise lexical ordering, prefix
filtering, delimiter/CommonPrefixes grouping, max-keys 0..1000, URL-encoded
response fields, 64-bit sizes, quoted ETags, and fixed-length XML responses.
Both response decoders share the entity-safe SAX boundary with explicit
document, nesting, element, and text ceilings; the v1 decoder additionally
checks delimiter-scoped NextMarker consistency before publishing a page.
V1 implements exclusive markers and delimiter-scoped NextMarker; v2
implements exclusive StartAfter and opaque continuation tokens bound to
bucket/prefix/delimiter.
The strict corpus covers malformed and duplicate queries, invalid and
cross-scope tokens, pagination, cancellation/deadline propagation, missing
buckets, and exact counts. The shared s5cmd slice passes against RustFS,
SeaweedFS, MinIO, and all three Flyology backends. It remains partial pending
owner projection, requester-pays/expected-owner policy, version-aware
listing, broader AWS SDK differentials, and performance tuning at large
namespace sizes.

The checked [`s3t` allowlist](../../coverage/s3t-allow.txt) adds 113
Ceph-compatible AWS SDK v2 tests for bucket lifecycle and HEAD, ListObjects v1
and v2 prefix/delimiter/marker/max-keys/encoding behavior, object
overwrite/read/delete/HEAD and absent-bucket handling, basic CopyObject across
buckets and zero/16 MiB bodies with ETag source conditions, bounded/open/
suffix/empty and invalid ranges, multipart create/abort/complete/error paths,
and UploadPartCopy whole/ranged/special-key/percent-encoded/multi-size paths.
The runner requires
the exact pinned s3t revision, rejects dirty binaries, runs four workers, and
retains JSON. Memory, files, and SQLite pass 113/113. RustFS passes 112 with one
pinned xfail for returning `InvalidArgument` instead of `NoSuchUpload`;
SeaweedFS 4.43 passes 107 with
pinned xfails for accepting deletion of a nonempty bucket, accepting PutObject
to an absent bucket, and reversing special-character common-prefix order under
URL encoding in both listing generations, plus accepting invalid and inverted
UploadPartCopy source ranges.
Supplemental MinIO passes 106 with seven exact pinned xfails: its empty multipart
completion error code, two internal legacy-marker exposures, an explicitly
empty v2 continuation token, and URL encoding of spaces in both listing
generations, plus returning `InvalidArgument` instead of `InvalidRange` for an
out-of-bounds UploadPartCopy range. It remains a compatibility target rather than an oracle because
the test runtime is AGPL-3.0-only.
Any other failure or an unexpected pass fails qualification. This corpus
exposed and closed AWS SDK `x-id` routing failures, the previously collapsed
multipart error codes `InvalidPartOrder`, `InvalidPart`, and `EntityTooSmall`,
incorrect `max-keys=0` truncation, `NoSuchKey` in place of `NoSuchBucket` for
PutObject, and slash-overencoding in v1 listing responses. The separate
special-key naming and return-data nodes remain outside this allowlist because
they proceed into object ACL operations, which are not yet implemented and
are not emulated as no-ops.
